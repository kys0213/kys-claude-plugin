# Decision Graph — 결정 하나 = 그래프 하나 = 소유 파일 하나

> 절차·판정을 서술하는 스킬 문서의 작성·유지 규약. 설계 배경(plan — 시점 기록): `plans/atelier/09-orchestrator-graph-restructure.md`.
> 현재 규약의 신뢰 소스는 이 문서와 `scripts/check-decision-graph.sh` 다.

문서에 **항목(item)** 은 결정(D)·계약(C)·절차(P) 셋뿐이며, 결정만 mermaid 그래프를 갖는다.
산문이 다시 자라면 같은 판정이 사본으로 흩어지고 사본끼리 어긋난다. 그 재증식을 막는 규약이다.

## 원칙

### 1. 새 지침은 노드 또는 엣지로만 추가한다

새로 알게 된 판정 기준은 **기존 결정 그래프의 판정 노드 하나 또는 엣지 하나**로 들어간다.
산문 불릿·안티패턴 항목·체크리스트 한 줄로 덧붙이지 않는다.

### 2. 어느 그래프에도 붙지 않으면 셋 중 하나다

| 상황 | 조치 |
|---|---|
| (a) 판정 축이 틀렸다 | 그래프의 **축을 고친다**. 지침을 축 밖에 매달지 않는다 |
| (b) 그 결정의 주인이 이 스킬이 아니다 | 소유한 스킬을 찾아 그쪽 항목으로 보낸다 |
| (c) 결정이 아니라 계약·절차다 | **id 를 새로 발급**하고 소유 파일을 지정한다 |

"일단 안티패턴에 적어 둔다"는 선택지는 없다. 배출구를 만드는 순간 규약이 무너진다.

### 3. 항목은 정확히 한 파일이 소유한다

새 항목을 만들려면 **넷을 함께** 만든다 — id 발급(`D##`/`C##`/`P##`), 소유 파일 상단
`<!-- owns: … -->` 갱신, 그 파일에 `## D##. 이름` heading, `SKILL.md` 결정 라우팅 표 한 행.
세 집합(`owns:` · heading · 라우팅 표)은 **항상 같은 집합**이어야 한다. 다른 파일에서 그 판정이
필요하면 `→ D##` 로 넘기고 **재요약하지 않는다**.

### 4. 항목 간 참조는 id 로만 한다

스킬 내부 항목 간 참조는 **파일을 가로질러도 링크 없이 bare `→ D##` / `→ C##` / `→ P##`** 로만
쓴다. id → 파일 매핑은 `SKILL.md` 라우팅 표가 유일하게 갖고, 검사 (4)가 id 실존을 본다.
`§절 이름` 참조와 `위 §`·`앞에서` 같은 상대 지시는 드리프트의 원인이므로 쓰지 않는다
(스킬 내부 항목 간에 한한다 — 외부가 지목하는 이름은 §외부 계약 표면).

## 결정 블록의 형식

6요소를 이 순서로 쓴다. 요소를 늘리거나 순서를 바꾸지 않는다 —
`needs:`(heading 바로 아래 HTML 주석) / **입력 신호**(≤5 불릿) /
**mermaid 1개**(`flowchart TD`, 노드 id 는 `D##_` 접두) / **종단별 행동 계약**(종단 수만큼) /
**한 줄 근거**(정확히 1줄, 생략 불가) / **후속**(`→ D##`).
계약(C)·절차(P) 블록은 같은 형태를 쓰되 mermaid 와 종단 계약이 없다 (P02 만 순서 그래프 1개).

판정 노드는 예/아니오 또는 열거로 닫히는 질문만 쓴다("적절히 판단한다" 금지). 한 노드에서 나가는
엣지 라벨은 상호배타 + 전수여야 하고, 종단은 관찰 가능한 행동 1개다("검토한다" 금지).

### 상한은 미관이 아니라 축이 틀렸다는 신호기다 — 늘리지 말고 항목을 쪼갠다

| 대상 | 상한 | 넘으면 |
|---|---|---|
| mermaid 블록 | 15줄 | 결정이 둘이다 → id 를 쪼갠다 |
| 판정 노드 / 종단 / 엣지 | 6 / 6 / 12 | 위와 동일 |
| 결정 블록 전체 | 35줄 | 종단 계약이 계약 본문을 삼켰다 → 계약 절로 내린다 |
| 계약·절차 블록 전체 | 40줄 | 계약이 둘이다 → `C##`/`P##` 를 쪼갠다 |
| 파일 하나 | 260줄 | 클러스터가 둘이다 → 파일을 쪼갠다 |

### 값은 계약에서만, 이름은 어디서나

예산·임계값의 **수치**는 `C04` 표 한 곳에만 둔다. 결정 그래프와 종단 계약은 값 대신
**이름**(`탐색 예산`, `재시도 예산`, `충돌 카운터`)만 쓰고 `→ C04` 를 붙인다.

## 구조 heading 화이트리스트

id 없는 `##` heading 은 아래 6종만 허용하며 **내용을 담지 않는다** — 인덱스·표·그룹 heading 일 뿐이고, 판정 규칙과 계약 본문은 반드시 id 블록 안에 있다 (W6 만 파일 스코프 한두 줄 예외).

| # | heading | 어디에 |
|---|---|---|
| W1 | `## 필수 로드` | SKILL.md |
| W2 | `## 디스패치 전 게이트 인덱스` | SKILL.md |
| W3 | `## 결정 라우팅` | SKILL.md |
| W4 | `## 계약` | 계약을 소유한 파일 |
| W5 | `## 절차` | 절차를 소유한 파일 |
| W6 | `## 머지 대상: epic 브랜치` | 머지 조정 파일 (외부 참조 보존) |

**추가하려면** 검사 스크립트의 화이트리스트 변수와 이 문서의 표를 **같은 PR 에서 함께** 고치고,
왜 id 블록으로 표현할 수 없는지를 근거로 남긴다. 이 마찰이 화이트리스트가 배출구가 되는 것을 막는다.

## 외부 계약 표면

**다른 스킬이 이름으로 지목하는 절 이름과 파일명은 공개 계약이다.**

- 이름을 **링크로 바꾸지 않는다.** 스킬이 개별 설치되는 형태에서는 상대 경로가 깨진다.
- 이름을 바꾸려면 **참조하는 스킬을 같은 PR 에서 함께 고친다.**
- 보존 대상 목록은 **검사 스크립트가 소유한다.** 이 문서에 복사하지 않는다 (사본은 어긋난다).

## 검증

`make validate-ci` 가 `scripts/check-decision-graph.sh`(상시 검사)를 실행한다. 실패로 뜬
**검사 번호가 곧 어긴 규칙**이므로 번호를 보고 해당 항목을 고친다. 목록과 번호는 스크립트가 소유한다.

## DO

엣지케이스를 만나면 **어느 결정의 어느 노드에서 갈리는지 지목**한 뒤 엣지·종단으로 추가한다.

```
관측: hot-spot 이 아닌 overlap 인데도 병렬이 깨졌다
  → D14 의 D14_q1("변경 파일 집합이 disjoint인가") No 갈래에서 갈린다
  → D14_q3 에 엣지 1개 + 종단 1개 추가, 종단 계약 1줄 추가 → 스크립트 통과 확인
  → 사고 배경·실패 사례는 이슈/plan 에, 그래프 아래엔 한 줄 근거만
```

## DON'T

그래프를 건드리지 않고 문서 다른 곳에 지침을 매달지 않는다.

```markdown
## 안티패턴                    ❌ 안티패턴 절 신설 — 규칙의 부정형 사본
- ❌ hot-spot 을 무시하고 병렬…
## 체크리스트                  ❌ 체크리스트 한 줄 — 규칙의 질문형 사본
- [ ] overlap 을 확인했는가?
## D14. 병렬 vs 순차 판정
- 순차 → 재시도 예산 99회까지  ❌ 값 리터럴 — 이름만 쓰고 `→ C04`
```

`SKILL.md` 요지 절에 D14 를 다시 언급하는 것도 같은 위반이다 — 라우팅 표 한 행으로 끝낸다.

## 다른 rules 와의 관계

`plugin-skill.md` 의 "원칙 → 프로세스 → 예시 → 출력 형식" 절 순서는 **라우터형 SKILL.md 에는
적용하지 않는다.** 라우터의 절 구성은 화이트리스트 W1~W3 과 결정 라우팅 표가 정한다.
