# 주석 (Comments)

언어 공통 취향 룰이다. 언어별 룰(Google 스타일 가이드)과 충돌하면 이 룰을 따른다. 특히 "공개 이름에는 모두 문서 주석을 단다"는 가이드 규칙 대신 이 룰을 따른다.

주석은 **코드만 봐서는 알 수 없는 것**만 담는다. 코드·spec·plan·이력에서 알 수 있는 내용을 주석에 복제하면, 원본이 바뀔 때 주석이 함께 고쳐지지 않아 곧 틀린 설명이 된다. 애매하면 쓰지 않는다.

이 룰은 구현 주석, 문서 주석(doc 주석), 테스트 코드의 주석에 모두 적용한다.

## DO — 남기는 것

- **why**: 자명하지 않은 선택의 이유. 다른 방법이 더 자연스러워 보이는데 이 방법을 쓴 이유.
- **gotcha**: 다음 사람이 반드시 한 번은 겪을 함정. 외부 도구·라이브러리·OS 의 비직관적 동작과 그 회피. 확인한 사실만 적는다.
- **비자명한 제약**: 시그니처가 말하지 못하는 전제조건·불변식, 실패하거나 프로그램을 중단시키는 입력, 호출 순서 제약.

```
-- 재시도 1회: 이 클라이언트는 idle 5분 뒤 첫 호출에서 연결이 살아 있어도 EOF 를 낸다
-- 빈 값은 "지정 안 함"으로 취급한다
```

## DON'T — 적지 않는 것

- **spec·정책 복제**: "정책상 관리자만 삭제할 수 있으므로" — 정책은 spec 이 말한다. 코드가 하는 일(`관리자만 통과`)까지만 적는다.
- **변경 이력**: "이전엔 X 였다", "v2 부터", 작성자·날짜.
- **티켓·이슈·PR 번호**: TODO 에도 붙이지 않는다. 할 일의 내용을 적는다.
- **문서 포인터**: plan 경로, spec 절 번호, 다른 문서의 표 번호. 포인터를 지우고 남는 내용이 없으면 그 주석은 통째로 지운다.
- **코드가 말하는 what**: 이름·시그니처·분기 구조를 문장으로 다시 적는 것. 함수 이름을 풀어 쓴 doc 주석("요소를 제거한다")도 여기에 든다.
- **흩어진 계약의 설명**: 여러 곳에 흩어진 로직을 주석으로 이어 붙이지 않는다. 먼저 로직을 한곳으로 모을 수 있는지 보고, 모을 수 있으면 모으고 주석은 쓰지 않는다.

## 문서 주석

- 공개 여부만으로 문서 주석을 의무화하지 않는다. 엔티티·값 타입·자명한 접근자는 선언만 남는 것이 정상이다.
- 문서 주석을 쓸 때도 위 DO 의 내용(사용 계약, 전제조건, 실패 조건, 비자명한 동작)만 담는다.
- 형식(어떤 문법, 어떤 문장 형태)은 언어 관용을 따른다.

## 주석이 붙은 코드를 고칠 때

- 주석이 붙은 코드를 고치면 그 주석을 **유지할지 다시 판단한다**. 여전히 참이고 여전히 코드만으로 알 수 없는 내용일 때만 남긴다.
- 고친 결과 주석이 설명하던 함정이 사라졌으면 주석도 지운다.

## 판별 질문

- 코드는 그대로인데 다른 문서가 바뀌면 이 주석이 틀려지는가? → 복제다. 지운다.
- 이 주석을 지우고 코드만 읽어도 같은 결론에 도달하는가? → what 의 재서술이다. 지운다.
- 이 주석이 없으면 다음 사람이 함정에 빠지는가? → 남긴다.

## 예외

- 도구 디렉티브(lint 억제 등)와 작업 마커(`TODO:`)는 주석 문법을 쓰지만 이 룰의 서술 대상이 아니다. 단, TODO 에도 티켓 번호 대신 내용을 적는다.
- 사용자에게 보이는 출력 문자열은 주석이 아니다.
