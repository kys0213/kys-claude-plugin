# 경계에서 빨리 실패 (Fail-Fast Boundary)

언어 공통 취향 룰이다. 언어별 룰(Google 스타일 가이드)과 충돌하면 이 룰을 따른다.

밖에서 들어오는 값(환경변수, 설정, 외부 응답, 문자열로 된 enum 값)은 **경계 한 곳에서** 타입이 있는 값으로 해석한다. 해석할 수 없으면 그 자리에서 실패시킨다. 잘못된 값이 코어 안쪽까지 흘러 들어가면, 실패가 원인과 먼 곳에서 엉뚱한 모습으로 나타난다.

## 설정 접근

- DO: 환경변수와 설정 파일은 설정 계층 한 곳에서 읽어 타입이 있는 설정 값으로 만든다. 나머지 코드는 그 값을 주입받는다.
- DO: 필수 설정이 없으면 시작 시점에 어떤 설정이 없는지 말하며 실패한다.
- DON'T: 코어 로직이나 깊은 하위 함수에서 환경변수를 직접 읽는다. 어떤 설정이 필요한지 한눈에 보이지 않고, 테스트에서 전역 상태를 바꿔야 한다.
- DON'T: 필수 설정에 기본값을 둔다. 설정 누락이 조용히 "그럴듯한 기본 동작"으로 바뀌어 운영에서야 드러난다. 기본값은 정말로 선택적인 설정에만 둔다.

```
DON'T  timeout = env("TIMEOUT") or 30          -- 필수인데 누락이 숨는다
DO     config  = Config.load()                 -- 누락 시 "TIMEOUT 이 없다"로 실패
       service = Service(config.timeout)
```

## 닫힌 값 집합

- DO: 닫힌 값 집합(상태, 종류, 모드)은 전용 타입으로 정의하고, 그 타입의 술어("종료 상태인가" 류)와 변환(문자열 ↔ 값)을 같은 모듈에 둔다. 값이 하나 늘 때 고칠 곳이 그 모듈 하나가 된다.
- DO: 문자열 등 외부 표현을 값으로 바꿀 때 알 수 없는 값은 오류로 반환한다.
- DO: 값에 따른 분기는 컴파일러(또는 프로젝트의 정적 검사기)가 누락된 경우를 잡는 망라 분기(switch/match)로 쓴다. 새 값을 추가하면 처리하지 않은 분기가 빌드에서 드러난다.
- DON'T: 알 수 없는 값을 기본 분기로 조용히 버리거나 기본값으로 바꾼다.
- DON'T: 닫힌 집합의 분기에 "나머지 전부" 기본 분기를 둬서 누락 검사를 끈다. 정말로 나머지를 같게 처리해야 하면 값을 명시해 나열한다.
- DON'T: 같은 값 집합에 대한 분기·술어를 여러 모듈에 흩어 놓는다. 값이 늘 때 한 곳이 빠진다.

```
DON'T  parse("archived") → Active                     -- 모르는 값을 기본값으로
DO     parse("archived") → error("unknown status: archived")

DON'T  branch status: Active → ... / 그 밖 전부 → ...       -- 새 값이 조용히 "그 밖"으로
DO     branch status: Active → ... / Paused → ... / Done → ...  -- 새 값은 빌드 오류
```

## 외부 경계 데이터

- DO: 외부 경계 데이터(외부 API 응답, 파일, 메시지)는 전용 타입으로 한 번 디코드하고, 형태 검증과 의미 검증을 나눈다. 형태 검증(필드·타입)은 디코드가, 의미 검증(범위·관계·업무 규칙)은 그다음 단계가 맡는다.
- DO: 디코드한 결과만 코어로 넘긴다. 코어는 원시 표현(맵, 동적 값, 원문 문자열)을 다루지 않는다.
- DON'T: 원시 표현을 여러 곳에서 조금씩 꺼내 쓰며 그때그때 검사한다.

## 판별 질문

- 이 값이 잘못되었을 때 실패하는 곳이 값이 들어온 곳인가? 아니라면 경계로 검사를 옮긴다.
- 값 집합에 새 값을 추가하면 처리 누락이 빌드에서 드러나는가? 아니라면 분기 형태를 바꾼다.
