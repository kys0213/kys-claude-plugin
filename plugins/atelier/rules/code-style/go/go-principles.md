# Go 원칙

Go 룰은 Google Go 스타일 가이드(guide·decisions·best-practices)를 옮긴 것이다. decisions 출처 항목은 DO/DON'T, best-practices 출처 항목은 "권장"으로 표기한다.

**언어 공통 룰(common)과 Go 룰이 충돌하면 언어 공통 룰을 따른다.**

## 원칙의 우선순위

출처: guide §Style principles

읽기 좋은 코드의 속성을 중요한 순서로 적용한다. 두 속성이 부딪히면 앞선 것을 고른다.

1. **명료성** — 무엇을, 왜 하는지 읽는 사람이 안다. 쓰기 쉬움보다 읽기 쉬움이 우선이다.
2. **단순성** — 목표를 가장 단순한 방법으로 이룬다. 불필요한 추상화 층이 없다.
3. **간결성** — 신호 대 잡음비가 높다. 반복·군더더기 문법·불투명한 이름이 없다.
4. **유지보수성** — 다음 사람이 올바르게 고치기 쉽다. 결정적인 디테일을 눈에 띄지 않는 곳에 숨기지 않는다.
5. **일관성** — 주변 코드와 같은 모양이다. 앞의 원칙을 뒤집지는 못하고, 동점일 때만 가른다.

한 글자 차이로 의미가 바뀌는 코드는 풀어 쓰거나 주석으로 신호를 키운다.

```go
// DON'T: = 와 := 차이, 가운데 ! 는 놓치기 쉽다
if user, err = db.UserByID(id); err != nil { ... }
leap := (y%4 == 0) && (!(y%100 == 0) || (y%400 == 0))

// DO
u, err := db.UserByID(id)
if err != nil { ... }
user = u

leap4, leap100, leap400 := y%4 == 0, y%100 == 0, y%400 == 0
leap := leap4 && (!leap100 || leap400)
```

## 포맷과 줄 길이

출처: guide §Formatting, §Line length

- DO: 모든 Go 소스는 `gofmt` 출력과 같아야 한다. 생성 코드도 포맷한다.
- DO: 줄 길이 제한은 없다. 줄이 길면 쪼개기보다 리팩토링(지역 변수 추출 등)을 먼저 한다.
- DON'T: 들여쓰기가 바뀌기 직전(함수 선언, 조건문)에서 줄을 나누지 않는다. URL 같은 긴 문자열을 줄 길이 때문에 쪼개지 않는다.

## 최소 메커니즘

출처: guide §Least mechanism

같은 생각을 표현하는 방법이 여럿이면 가장 표준적인 도구를 고른다. 복잡도는 더하기 쉽고 빼기 어렵다.

1. 언어 기본 구성요소(채널, 슬라이스, 맵, 루프, 구조체)로 충분하면 그것을 쓴다.
2. 없으면 표준 라이브러리에서 찾는다.
3. 그다음에야 이미 쓰는 의존성을, 마지막으로 새 의존성을 검토한다.

```go
// DO: 집합 소속 검사는 맵으로 충분하다
seen := map[string]bool{}

// DON'T: 단순 소속 검사에 집합 라이브러리를 들이지 않는다
```

복잡도가 필요하면(성능 등) 의도적으로 넣고, 왜 필요한지와 조심할 점을 남긴다.

## 지역 일관성

출처: guide §Local consistency, decisions §Non-decisions

- DO: 가이드가 말하지 않는 지점은 같은 파일·패키지가 이미 택한 방식을 따른다 (예: 에러 출력에 `%s`/`%v`, 뮤텍스 대신 버퍼 채널).
- DON'T: 지역 일관성을 근거로 가이드 위반을 넓히지 않는다. 기존 위반을 더 많은 파일·공개 API로 번지게 하는 변경이면 먼저 정리한다.
- 다음은 어느 쪽이든 괜찮다. 주변과 맞춘다.
  - `var i int` 와 `i := 0`
  - `&T{}` 와 `new(T)`, `map[K]V{}` 와 `make(map[K]V)`
  - 포맷이 없는 메시지의 `errors.New` 와 `fmt.Errorf`
  - `cmp.Diff` 의 got/want 인자 순서 (실패 메시지에 방향을 적는다)
