# Spec 작성법

spec은 **제품이 무엇이어야 하는가**를 적는 규격이다 — 정책, 계약, 시스템 큰그림, 사용자 시나리오. 작업 지침은 rules에, 시점 의사결정 기록은 plan에 적는다 (구분 기준: CLAUDE.md의 "문서 계층 (Spec / Rules / Plan)" 절).

- **소비자 기준**: 컴포넌트 밖의 소비자(사용자·외부 시스템·타 컴포넌트)가 의존하는 계약만 본문에 담는다. 밖에서 관찰되지 않는 것은 리팩토링에 흔들린다 — spec의 영역이 아니다.
- **코드가 SSOT인 것을 옮겨 적지 않는다**: 비즈니스 로직, 내부 인터페이스·trait 시그니처, enum 정의는 코드에 맡긴다 (그 형태의 설계 컨벤션은 rules가 정한다). 구현 구조 안내·작업 순서는 그 작업 시점의 plan으로 보낸다.
- **리팩토링 리트머스**: 동작·계약이 그대로인 리팩토링에 spec 본문을 고쳐야 한다면 구현 세부에 결합된 것이다 — 계약 수준으로 끌어올리거나 rules로 내린다.
- **결정된 것만 본문에** 적는다. 미확정은 미결(TBD) 섹션으로 격리하고, 해소되면 본문으로 옮기고 섹션에서 지운다 — 남은 항목이 없으면 `없음`으로 적는다. 미결이 남은 spec은 확정 규격이 아니며 자율 구현의 입력이 되지 못한다 (orchestrator가 구현 dispatch 전에 hard stop한다).
- **동기화 의무**: spec이 현실과 어긋나면 drift다 — spec 또는 코드를 고치고, 어긋난 채 두지 않는다.
- 표현은 긴 설명보다 표·다이어그램·예시 우선. 함수 시그니처를 나열하는 표는 쓰지 않는다.
