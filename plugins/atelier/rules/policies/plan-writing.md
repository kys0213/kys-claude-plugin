# Plan 작성법

plan은 **그 시점에 왜 그렇게 결정했는가**를 남기는 기록이다 — 의사결정·구현 계획의 히스토리. 현재 규격은 spec이, 작업 지침은 rules가 담당한다 (구분 기준: CLAUDE.md의 "문서 계층 (Spec / Rules / Plan)" 절).

- **담는 것**: 요구사항 정리, 사이드이펙트 조사, 검토한 대안과 **버린 이유**, 결정과 근거, 구현 계획·작업 순서, 작성 시점의 상태.
- **repo 안에 남긴다**: 저장 경로는 `plans/YYYY-MM-DD-<slug>.md` — 작성일 접두 + 작업을 식별하는 짧은 슬러그의 평면 구조다. 도구가 repo 밖(임시 디렉토리 등)에 만든 계획 파일은 기록이 아니다 — 합의가 끝나면 이 경로로 옮겨 커밋한다. 커밋은 구현 커밋과 분리한다 (`docs` 타입) — 그래야 "이 시점의 결정" 이 git 이력에도 드러난다.
- **작성 시점을 명시한다**: 헤더에 날짜·브랜치·연관 이슈·승인 출처를 남겨 언제의, 누구와의 합의 기록인지 드러낸다. 상태 표기("설계 단계", "구현 전 승인 필요" 등)는 작성 당시의 것이다.

  ```
  # <제목>

  > **Plan — 이 시점의 결정 기록.** 현재 정책의 신뢰 소스가 아니다.
  > 날짜: YYYY-MM-DD · 브랜치: <branch> · 이슈: #<n> (없으면 `없음`) · 승인 출처: 사용자 승인 | grill 합의 | council pass
  ```
- **작성 후에는 고치지 않는다**: 구현이 plan과 달라져도 정상이다 — 기록 보존이 목적이다. 달라진 규격은 spec에, 새로 얻은 지침은 rules에 반영하고 plan은 그대로 둔다.
- **판단 근거로 쓰지 않는다**: plan을 읽고 현재 동작·정책을 판단하지 않는다. 배경·버린 선택지를 이해할 때만 참조하고, 현재 판단은 spec·rules·코드로 내린다.
