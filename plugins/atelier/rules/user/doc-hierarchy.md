# 문서 계층 (Spec / Rules / Plan)

세 종류의 문서는 서로 다른 관점을 서술한다. 역할이 섞이면 작성 시점의 기록을 현재 정책으로 오독하거나, 구현 세부가 상위 문서를 흔든다.

|  | Spec (`spec/` 계층: DESIGN.md, concerns/, flows/) | Rules (CLAUDE.md·AGENTS.md·`.claude/rules/`) | Plan (`plan.md`, `plans/` 등 계획 기록) |
|---|---|---|---|
| 관점 | 제품이 **무엇**이어야 하는가 — 정책·기획·시스템 큰그림·사용자 시나리오 | 작업자가 **어떻게** 일하는가 — 컨벤션·경계 원칙·반복 실수 방지 지침 | 그 시점에 **왜** 그렇게 결정했는가 — 의사결정·구현 계획의 히스토리 |
| 시간이 지나면 | 제품과 동기화 유지 — 어긋나면 drift로 취급해 spec 또는 코드를 고친다 | 작업 방식과 동기화 유지 — 같은 실수가 반복되면 지침을 추가·갱신한다 | 현실과 어긋나도 정상 — 고치지 않는다 (기록 보존) |
| 판단 근거로 | ✅ "지금 어떻게 동작해야 하는가"의 신뢰 소스 | ✅ "지금 어떻게 작업해야 하는가"의 신뢰 소스 | ❌ 쓰지 않는다. 배경·맥락 파악용 |

- 구분 질문: **"이 문서와 현실이 어긋나면 문서를 고쳐야 하는가?"** 고쳐야 하면 spec 또는 rules, 그대로 두면 plan. 고칠 내용이 제품 규격이면 spec, 작업 지침이면 rules.
- **리팩토링 리트머스**: 동작·계약이 그대로인 리팩토링에 spec 본문을 고쳐야 한다면 spec이 구현 세부에 결합된 것이다. 구현 구조·경계에 대한 지속 원칙은 spec이 아니라 rules의 영역이고, 세부는 코드에 맡긴다 (`related_paths` 등 경로 참조 갱신은 메타데이터 정비라 예외).
- 현재 동작·정책 판단은 spec과 코드로, 작업 방식 판단은 rules로 내린다. Plan의 내용이 이들과 다르면 spec·rules·코드가 맞다.
- Plan 안의 상태 표기(예: "설계 단계", "구현 전 승인 필요")는 작성 당시의 상태다. 현재 상태는 코드·이슈·PR에서 확인한다.
- 구현이 plan과 달라져도 plan을 업데이트하지 않는다. 규격이 바뀌었으면 spec에, 지침이 바뀌었으면 rules에 반영한다.
