# 문서 계층 (Plan vs Spec)

Plan과 Spec은 다른 종류의 문서이며 **신뢰 수준이 다르다**. 구분하지 않으면 작성 시점의 기록을 현재 정책으로 오독한다.

|  | Plan (`plan.md`, `plans/` 등 계획·설계 기록) | Spec (`spec/` 계층: DESIGN.md, concerns/, flows/) |
|---|---|---|
| 성격 | 작성 시점의 의사결정 **기록** (히스토리) | 현재 제품의 **규격이자 정책** |
| 시간이 지나면 | 현실과 어긋나도 정상 — 고치지 않는다 (기록 보존) | 구현과 동기화를 유지한다 — 어긋나면 drift로 취급해 spec 또는 코드를 고친다 |
| 판단 근거로 | ❌ 쓰지 않는다. "그때 왜 그렇게 결정했는가"의 배경·맥락 파악용 | ✅ "지금 어떻게 동작해야 하는가"의 신뢰 소스 |

- 구분 질문: **"이 문서와 현실이 어긋나면 문서를 고쳐야 하는가?"** 고쳐야 하면 spec, 그대로 두면 plan.
- 현재 동작·정책 판단은 spec과 코드로 내린다. Plan의 내용이 코드·spec과 다르면 코드·spec이 맞다.
- Plan 안의 상태 표기(예: "설계 단계", "구현 전 승인 필요")는 작성 당시의 상태다. 현재 상태는 코드·이슈·PR에서 확인한다.
- 구현이 plan과 달라져도 plan을 업데이트하지 않는다. 현재 규격이 바뀌었으면 spec에 반영한다.
