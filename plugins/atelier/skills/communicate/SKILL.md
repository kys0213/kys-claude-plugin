# communicate

## 산출물 유형별 규칙 (먼저 확인)

글을 쓰기 전에 **누구에게, 어떤 형태로 내보내는지** 정하고 이 표의 행을 따릅니다.

| 유형 | 예 | 문장 규칙 (ASD-STE100) | 구조·형식 |
|---|---|---|---|
| **외부 채널 공개** | 슬랙 메시지, PR 본문, 리뷰·이슈 코멘트, 위키·노션, 릴리스 노트 | 80% | 그 자리의 양식이 정한다. PR 본문은 `git` 스킬의 섹션 4단, 나머지는 `references/delivery-context.md`. 보내기 전에 §외부 전송 2단계 |
| **사람에게 공유** | `.html` 보고서, `.md` 문서 | **전면** — 절차 15어절 상한, 설명 20어절·문단 6문장 목표 | 보고서는 §보고서는 HTML 레포트 (`references/html-report.md §골격`). `.md` 문서도 같은 섹션 순서를 따른다 |
| **발표자료** | 슬라이드, `.ppt`·`.pptx` | 80% | 문장은 이 스킬의 기준선, 구성·디자인은 Claude 디자인 방식(그 환경의 슬라이드·디자인 도구)을 따른다 |
| **채팅 답변** | 이 대화 | 80% | 결론 먼저. 분량이 구조를 정한다 (output style) |

- Karpathy 가 제안한 대로 문장은 **ASD-STE100 을 빌려 씁니다.** 규칙표와 수준의 뜻은 `references/writing-standards.md §문장` 이 소유합니다.
- **전면**: 규칙표를 모두 지킵니다. 절차 문장의 수치는 상한이고, 설명 문장·문단의 수치는 목표입니다 — 이어지는 생각을 수치에 맞추려고 쪼개지 않습니다. **80%**: 단어·동사·문장·안전 지시 규칙은 지키고, 수치·문단 규칙은 목표로 두며 자리의 양식이 우선합니다. 두 수준 모두 영어 승인 단어 목록만 쓰지 않습니다.
- 문체는 네 유형 모두 해요체입니다 (§기준선).
- 스펙 문서(`spec/`)는 `spec-write` 스킬이 구조를 정합니다. 문장은 "사람에게 공유" 행을 따릅니다.
- 사용자가 형식을 지정하면 그 형식이 이 표보다 우선합니다.

## 이 스킬이 다루는 것

**내가 아는 것을 그 과정을 못 본 사람에게 옮기는** 글쓰기 기준입니다. 보고서·채팅 답변·위키 문서·PR 설명은 포장이 다를 뿐 같은 문제를 풉니다 — *읽는 사람은 우리가 나눈 대화를 보지 못했다.*

자리별 양식은 위 표가 가리키는 문서가 정합니다. 이 문서는 **어디에 놓든 유지되는 기준선**과, 글이 가장 자주 실패하는 두 지점만 담습니다 — 나만 아는 배경을 글에 옮기지 못하는 것(§맥락 이전)과 지워도 되는 문장을 남겨 글이 길어지는 것(§군더더기 제거)입니다. 적용 상세와 자리별 적응은 references 로 분리합니다.

이 skill 은 **무엇을 어떤 문체·깊이로 쓸지의 기준**만 소유합니다. 실제 파일 Write 는 규모에 따라 메인이 직접 하거나, 여러 파일·섹션으로 벌어지면 `orchestrator` skill 로 위임합니다. 위임할 때는 이 기준을 sub-agent prompt 에 실어 보냅니다.

**채팅 답변은 위임하지 않습니다** — Write 가 없으니 기준만 적용해 그 자리에서 답합니다. "쉽게 설명해줘"에 sub-agent 를 띄우지 마세요.

## 기준선 (자리와 무관 — 단일 출처)

PR 본문 규칙을 **모든 글의 기본값으로 승격**한 것입니다. 자리가 바뀌면 포장만 바뀌고 이 여섯은 그대로 갑니다. 문장 규칙의 수준만 위 표를 따릅니다.

| 항목 | 기본값 |
|---|---|
| 독자 | IT 특성화 고등학생도 이해할 수 있는 수준 — 약어·사내용어는 풀어쓴다 |
| 문장·구조 | 문장·문단·절차는 ASD-STE100 규칙표를 따른다. 수준(전면·80%)은 §산출물 유형별 규칙 (`references/writing-standards.md §문장`) |
| 문체 | 친근한 해요체 ("~했어요", "~예요"). 절차 단계까지 한 문서 안에서 어미 통일 |
| 정보 전달 | 서로 별개인 항목은 목록(불릿·번호), 이유·결과처럼 이어지는 생각은 짧은 문단 |
| 분량 | 지워도 정보가 사라지지 않는 문장은 지운다. 같은 정보는 한 자리에 한 번만 |
| 언어 | 한국어. 코드·명령·식별자는 원문 유지. 유행어는 쉬운 말로 바꾼다 ("딥다이브" → "깊게 살펴보기") |

- 격식이 필요한 대외·공식 문서만 평서체("~했다")로 쓴다. 어떤 문체든 한 문서 안에서는 통일한다.
- PR 본문은 **섹션 4단이 고정**이다. 양식은 `git` 스킬이 정한다.

## 보고서는 HTML 레포트 (기본 형식)

분석·조사 결과, 장애 원인 분석, 진행 보고, 설계 검토처럼 **남아서 읽히는 보고서**는 단일 파일 HTML 레포트로 만들어요. Karpathy 의 형식 사다리(STE100 문장 → 다이어그램 → HTML)에서 1~3단을 한 파일에 담는 형식이에요.

- 사람에게 공유하는 글이라 **ASD-STE100 을 전면 수준으로 빌려 써요.** 섹션도 STE100 의 구분(설명·절차·안전 지시)을 따라요: 결론 → 대상 설명 → 주의할 점 → 확인 절차 → 결정과 버린 선택지 → 근거. PR 본문 4단을 골격으로 쓰지 않아요 (`references/html-report.md §골격`).
- 템플릿 `${CLAUDE_PLUGIN_ROOT}/skills/communicate/assets/report-template.html` 을 채워요.
- 다이어그램은 Mermaid 로 쓰고, 전달 전에 `node "${CLAUDE_PLUGIN_ROOT}/scripts/report/render-report.mjs" <파일>` 로 렌더링을 검증해요. 검증하지 못했으면 "미검증"이라고 알려요.
- 채팅·PR 본문·리뷰 코멘트·슬랙 메시지·릴리스 노트는 그 자리의 형식을 지켜요. 레포트가 있으면 경로만 붙여요.
- 사용자가 다른 형식을 지정하면 그 형식이 우선이에요.

## 외부 전송 2단계 (draft → send)

Slack·Confluence·이슈 코멘트처럼 **이 대화 밖으로 나가는 쓰기**는 항상 2단계로 진행해요. 전송은 되돌리기 어렵고, 잘못된 스레드나 오류 있는 내용이 나가면 정정 비용이 글쓰기 비용보다 커요.

1. **draft 먼저**: 전송하지 않고 draft를 사용자에게 제시해요. 주장에는 인용 가능한 근거(citation — 링크·파일 경로·메시지 출처)를 붙여요.
2. **명시적 승인 후 전송**: "보내줘"·"발행해줘" 같은 명시적 승인이 있을 때만 전송해요.

- "정리해줘"·"답변 만들어줘"류 요청의 기본값은 **draft**예요 — 글을 만들어 달라는 요청이지 전송 승인이 아니에요.
- 어디로 보내는지(채널·스레드·페이지)가 확정되지 않았으면 draft 단계에서 함께 확인해요.
- 위임된 sub-agent에도 그대로 적용돼요 — draft 작성 위임에 전송 권한을 얹지 않아요.

## 맥락 이전 (Context Handoff)

가장 자주 실패하는 지점입니다. 대화하며 쌓인 전제·별명·기각된 선택지는 **전부 내 쪽에만** 있습니다. 읽는 사람에게는 결과물만 도착합니다.

### 옮겨야 할 네 가지

PR 본문의 4단(왜 / 무엇을 / 어떻게 / 확인 방법)이 원형입니다. 자리가 달라도 질문은 같습니다. 네 질문은 **빠뜨리면 안 되는 정보의 점검 목록**이지 섹션 제목이 아닙니다 — 섹션 구조는 자리의 양식(PR 본문은 `git` 스킬, 로컬 보고서는 `references/html-report.md §골격`)이 정합니다.

| 질문 | 내용 | 빠뜨렸을 때 |
|---|---|---|
| **왜** | 계기·문제 상황·배경 | 읽는 사람이 "이걸 왜 지금?"에서 막힌다 |
| **무엇을** | 실제로 바뀐 것 (파일·모듈·동작 단위). 바꾼 것이 없는 조사·설명 글이면 찾은 것 | 변경 범위를 각자 추측한다 |
| **어떻게** | 고른 접근과 **버린 선택지 + 이유** (우리가 내린 결정일 때. 남이 만든 코드의 의도를 추정해 채우지 않는다) | 나중에 "왜 이렇게 했지?"가 복원 불가능해진다 |
| **확인 방법** | 읽는 사람이 따라할 수 있는 검증 단계 | 믿을지 말지를 판단할 수 없다 |

- 자리가 좁으면 **줄이되 순서는 지킨다** — "왜"가 없는 공유는 거의 항상 되묻는 질문을 부른다.
- **버린 선택지는 특히 잘 사라진다.** 길게 논의하고 접은 안은 결과물에 흔적이 없다. 한 줄이라도 남긴다.

### 대화 잔재 제거

| 잔재 | 문제 | 고침 |
|---|---|---|
| 지시어 ("아까 그 이슈", "그 파일") | 독자에겐 가리킬 대상이 없다 | 이름·경로·링크로 치환 |
| 대화에서만 쓰던 별명 | 무엇인지 모른다 | 정식 이름 + 한 줄 설명 |
| 합의된 전제 ("어차피 그건 안 쓰니까") | 합의 자체를 못 봤다 | 전제를 문장으로 드러낸다 |
| 시간 순서 서술 ("처음엔 A로 했다가 B로 바꾸고…") | 과정은 독자의 관심사가 아니다 | 결론 먼저, 과정은 필요한 만큼만 |

> **자가 점검**: 위에서부터 읽으며 "이 문장을 이해하려면 우리 대화를 봤어야 하는가?"를 묻는다. 걸리는 문장은 아직 옮겨지지 않은 것이다.

## 군더더기 제거 (Decluttering)

맥락 이전 다음으로 자주 실패하는 지점입니다. 4요소를 채우라는 것은 정보를 빠뜨리지 말라는 뜻이지 길게 쓰라는 뜻이 아닙니다 — 각 요소는 한두 문장이면 충분할 때가 많습니다.

**초안은 결과물이 아닙니다.** 다 쓴 뒤 "더 간결하게 해달라"는 요청을 이미 받았다고 치고 한 번 줄입니다 — 줄인 결과만 내보냅니다. 독자가 간결화를 되청해야 하는 글은 이 단계를 건너뛴 것입니다.

| 군더더기 | 왜 생기는가 | 고침 |
|---|---|---|
| 메타 서술 ("이 문서는 ~을 정리한 거예요", "아래에서 설명할게요") | 글의 지도를 그려주고 싶어서 | 지운다 — 제목과 구조가 이미 지도다 |
| 같은 정보의 반복 (요약에서 말하고 본문에서 또, 끝에서 또) | 강조하고 싶어서 | 가장 잘 보이는 자리 한 곳에만 쓴다 |
| 예고·정리 문장 ("정리하면 다음과 같아요", "결론적으로") | 개조식으로 넘어가는 관성 | 지운다 — 불릿이 곧 정리다 |
| 과잉 구조 (3줄 내용에 섹션 제목·표·구분선) | 격식을 갖추고 싶어서 | 분량이 구조를 정한다. 불릿 몇 개로 끝나면 제목 없이 쓴다 |

> **자가 점검**: 문장을 지워도 독자가 잃는 정보가 없으면 군더더기다. 정보를 잃으면 남긴다 — 줄이는 대상은 문장이지 정보가 아니다 (`references/writing-standards.md §문장`).

## References (필요할 때만 로드)

문장을 실제로 고치거나 놓을 자리가 정해지면 읽는다. 무엇이 들어 있는지만 적는다 — 여기 요약해 두면 reference 를 열지 않게 된다.

| 파일 | 언제 읽을지 |
|---|---|
| `references/writing-standards.md` | 문장을 쓰거나 고칠 때 — 작문 철학, **읽기 수준(용어를 영향으로 환산)**, 용어 처리, 문장(ASD-STE100 규칙표·전면/80% 수준·어절 상한)·어미, 청중별 우선순위 |
| `references/delivery-context.md` | 놓을 자리가 정해졌을 때 — 성질 축(휘발성·동시성·응답 기대·독자 범위·양식 강제·서식 표현력)별 기준, 판단 순서, 조합 예시, 자리 선택이 틀리는 경우 |
| `references/html-report.md` | 보고서를 HTML 레포트로 만들 때 — 만들지 판단, 형식 사다리, 골격(STE100 설명·절차·안전 지시 구분), Mermaid 규칙, 렌더링 검증과 실패 대응, 저장 경로·전달 |
| `references/worked-example.md` | 규칙이 문장에서 어떻게 달라지는지 안 잡힐 때 — 인수인계 메모 한 편을 before/after 로 끝까지 따라간 예시 |

판단 기준은 **도구가 아니라 성질**이다 — 도구 이름은 바뀌어도 성질은 바뀌지 않는다.

## 품질 체크리스트 (기준선 — 어디에 놓든 적용)

내보내기 전에 확인한다. 자리의 성질에 따른 점검은 `references/delivery-context.md §체크리스트` 가 소유한다.

- [ ] 첫 문단(결론)만 읽어도 핵심을 알 수 있는가?
- [ ] 상대가 할 일이 분명한가? (요청이면 무엇을·언제까지, 통보면 할 일 없음)
- [ ] **우리 대화를 못 본 사람이 읽어도 막히지 않는가?** (지시어·별명·암묵적 전제 제거)
- [ ] 왜 / 무엇을 / 어떻게 / 확인 방법 중 빠진 것이 의도적인가?
- [ ] 버린 선택지와 그 이유가 한 줄이라도 남아 있는가?
- [ ] 초안을 그대로 내보내지 않고 압축 퇴고를 한 번 거쳤는가?
- [ ] 지워도 정보가 사라지지 않는 문장(메타 서술·중복·예고 문장)이 없는가?
- [ ] 전문용어를 **영향으로** 환산했는가? (설명만 붙이고 끝내지 않았는가)
- [ ] 유행어·커뮤니티 은어를 쉬운 말로 바꿨는가? ("딥다이브" → "깊게 살펴보기")
- [ ] 산출물 유형 표의 수준(전면·80%)으로 문장·문단·절차를 썼는가? (전면이면 절차 15어절·설명 20어절·문단 6문장 이하, 절차 단계는 한 단계에 지시 하나)
- [ ] 한 문서 안에서 어미·톤이 일관되는가? (절차 단계 포함)
- [ ] 모든 주장에 검증 가능한 근거가 있는가?
- [ ] 사실과 판단·추정이 구분되는가?
- [ ] 보고서라면 HTML 레포트로 만들고, 렌더링 검증 결과(`OK` 또는 미검증)를 알렸는가?
- [ ] 외부 채널로 나가는 글이면 지금 draft 단계인가? (명시적 승인 없이 전송하지 않았는가)
