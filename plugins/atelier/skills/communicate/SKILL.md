# communicate

**내가 아는 것을 그 과정을 못 본 사람에게 옮기는** 글쓰기 기준입니다. 보고서·채팅 답변·위키 문서·PR 설명은 포장이 다를 뿐 같은 문제를 풉니다 — *읽는 사람은 우리가 나눈 대화를 보지 못했다.*

고정 양식을 강제하지 않습니다. 이 문서는 **어디에 놓든 유지되는 기준선**과 가장 자주 실패하는 지점(맥락 이전)만 담고, 적용 상세와 자리별 적응은 references 로 분리합니다.

이 skill 이 소유하는 것은 **무엇을 어떤 문체·깊이로 쓸 것인가의 기준**입니다. 실제 파일 Write 는 `orchestrator` skill 이 위임하는 sub-agent 가 수행하며, 메인 에이전트는 Write 를 위임할 뿐 직접 실행하지 않습니다.

**산출물이 채팅 답변이면 Write 자체가 없으므로 위임 대상도 아닙니다** — 기준만 적용해 그 자리에서 답합니다. "쉽게 설명해줘"에 답하려고 sub-agent 를 띄우지 마세요.

## 기준선 (자리와 무관 — 단일 출처)

PR 본문 규칙을 **모든 글의 기본값으로 승격**한 것입니다. 놓이는 자리가 바뀌면 포장이 바뀔 뿐 이 넷은 그대로 갑니다.

기준선의 단일 출처는 이 절입니다. `templates/claude-md/CLAUDE.md` 의 요약본이 이 절과 어긋나면 이 절이 우선합니다.

| 항목 | 기본값 |
|---|---|
| 독자 | IT 특성화 고등학생도 이해할 수 있는 수준 — 약어·사내용어는 풀어쓴다 |
| 문체 | 친근한 해요체 단문 ("~했어요", "~예요"). 한 문장은 짧게 |
| 정보 전달 | 개조식(불릿·번호) 우선. 줄글 설명은 최소화 |
| 언어 | 한국어. 코드·명령·식별자는 원문 유지 |

- **격식이 필요한 대외·공식 문서**만 평서체("~했다")로 바꾼다. 어떤 문체를 골랐든 한 문서 안에서는 통일한다.
- PR 본문은 이 기본값이 고정 양식을 만난 경우이며 **섹션 4단이 고정**이다 — 정확한 양식은 `git` 스킬의 `references/cli-reference.md` 가 단일 출처다.

## 맥락 이전 (Context Handoff)

가장 자주 실패하는 지점입니다. 에이전트와 수십 턴을 주고받으며 쌓인 전제·별명·기각된 선택지는 **전부 내 쪽에만** 있습니다. 읽는 사람에게는 결과물만 도착합니다.

### 옮겨야 할 네 가지

PR 본문의 4단(왜 / 무엇을 / 어떻게 / 확인 방법)이 이 네 가지의 원형입니다. 놓이는 자리가 달라도 질문은 같습니다.

| 질문 | 내용 | 빠뜨렸을 때 |
|---|---|---|
| **왜** | 계기·문제 상황·배경 | 읽는 사람이 "이걸 왜 지금?"에서 막힌다 |
| **무엇을** | 실제로 바뀐 것 (파일·모듈·동작 단위) | 변경 범위를 각자 추측한다 |
| **어떻게** | 고른 접근과 **버린 선택지 + 이유** | 나중에 "왜 이렇게 했지?"가 복원 불가능해진다 |
| **확인 방법** | 읽는 사람이 따라할 수 있는 검증 단계 | 믿을지 말지를 판단할 수 없다 |

- 자리가 좁아 넷을 다 못 쓰면 **줄이되 순서는 지킨다** — "왜"가 없는 공유는 거의 항상 되묻는 질문을 부른다.
- **버린 선택지는 특히 잘 사라진다.** 대화에서 길게 논의하고 접은 안은 결과물에 흔적이 없다. 한 줄이라도 남긴다.

### 대화 잔재 제거

| 잔재 | 문제 | 고침 |
|---|---|---|
| 지시어 ("아까 그 이슈", "그 파일") | 독자에겐 가리킬 대상이 없다 | 이름·경로·링크로 치환 |
| 대화에서만 쓰던 별명 | 무엇인지 모른다 | 정식 이름 + 한 줄 설명 |
| 합의된 전제 ("어차피 그건 안 쓰니까") | 합의 자체를 못 봤다 | 전제를 문장으로 드러낸다 |
| 시간 순서 서술 ("처음엔 A로 했다가 B로 바꾸고…") | 과정은 독자의 관심사가 아니다 | 결론 먼저, 과정은 필요한 만큼만 |

> **자가 점검**: 쓴 글을 위에서부터 읽으며 "이 문장을 이해하려면 우리 대화를 봤어야 하는가?"를 묻는다. 하나라도 걸리면 그 문장은 아직 옮겨지지 않은 것이다.

## References (필요할 때만 로드)

기준선을 실제 문장에 적용하거나 놓을 자리가 정해지면 아래를 읽는다. 여기서 요약해 두면 reference 를 열지 않게 되므로, 무엇이 들어 있는지만 적는다.

| 파일 | 언제 읽을지 |
|---|---|
| `references/writing-standards.md` | 문장을 실제로 쓰거나 고칠 때 — 작문 철학, **읽기 수준(용어를 영향으로 환산)**, 용어 처리, 문장·어미·시제, 청중별 우선순위 |
| `references/delivery-context.md` | 놓을 자리가 정해졌을 때 — 성질 축(휘발성·동시성·응답 기대·독자 범위·양식 강제·서식 표현력)별 판단 기준, 판단 순서, 조합 예시, 자리 선택 자체가 틀리는 경우 |
| `references/worked-example.md` | 규칙은 알겠는데 문장에서 뭐가 달라지는지 안 잡힐 때 — 인수인계 메모 한 편을 before/after 로 끝까지 따라간 예시. 성질 축 판단, 판단 순서 적용, 바뀐 지점별 근거, 축을 뒤집었을 때의 차이 |

판단 기준은 **도구가 아니라 성질**이다 — 도구 이름은 바뀌어도 성질은 바뀌지 않기 때문이다.

## 품질 체크리스트 (기준선 — 어디에 놓든 적용)

내보내기 전에 확인한다. 놓을 자리의 성질에 따른 점검은 `references/delivery-context.md §체크리스트` 가 소유한다.

- [ ] 첫 문단(결론)만 읽어도 핵심을 알 수 있는가?
- [ ] 상대가 할 일이 분명한가? (요청이면 무엇을·언제까지, 통보면 할 일 없음)
- [ ] **우리 대화를 못 본 사람이 읽어도 막히지 않는가?** (지시어·별명·암묵적 전제 제거)
- [ ] 왜 / 무엇을 / 어떻게 / 확인 방법 중 빠진 것이 의도적인가?
- [ ] 버린 선택지와 그 이유가 한 줄이라도 남아 있는가?
- [ ] 전문용어를 **영향으로** 환산했는가? (설명만 붙이고 끝내지 않았는가)
- [ ] 한 문서 안에서 어미·시제·톤이 일관되는가?
- [ ] 같은 개념을 같은 단어로 일관되게 부르는가?
- [ ] 모든 주장에 검증 가능한 근거가 있는가?
- [ ] 사실과 판단·추정이 구분되는가?
