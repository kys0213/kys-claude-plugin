# HTML 레포트

보고서 성격 산출물의 기본 형식이다. 문장 기준(독자 수준·해요체·개조식·STE100 전면 수준·맥락 이전 4요소)은 `SKILL.md` 기준선 그대로다. 이 문서는 **그 글을 담는 그릇**(구조·다이어그램·검증)을 정한다.

---

## 언제 만드는가

성질로 판단한다 (`delivery-context.md`). **남는 글 + 브라우저로 여는 자리 + 독자가 읽고 판단하는 글**이면 HTML 레포트다.

| 만든다 | 만들지 않는다 (그 자리의 형식) |
|---|---|
| 분석·조사 결과 | 채팅 답변 ("쉽게 설명해줘" 포함) |
| 장애 원인 분석 | PR 본문·리뷰 코멘트 (`git` 스킬 양식) |
| 진행·주간 보고 | 슬랙 메시지·이슈 코멘트 |
| 설계 검토·선택지 비교 | 릴리스 노트 |
| 인수인계 문서 | 스펙 문서 (`spec-write`)·저장소에 남길 마크다운 문서 |

- 사용자가 다른 형식(마크다운·노션 등)을 지정하면 그 형식이 우선한다.
- 흘러가는 자리에도 알려야 하면 그 자리 형식으로 결론 2~3줄과 레포트 경로를 보낸다.

---

## 형식 사다리

Andrej Karpathy 는 LLM 출력을 이해하기 쉽게 만드는 형식을 네 단으로 제안했다 (X, 2026-10-02): ASD-STE100 문장 → 다이어그램 → 인터랙티브 HTML → 설명 영상. 위로 갈수록 이해하기 쉽다. 이 레포트는 1~3단을 한 파일에 담는다.

| 단 | 레포트에서 | 쓰는 조건 |
|---|---|---|
| 1. 문장 | 본문 전부 (`writing-standards.md §문장`) | 항상 |
| 2. 다이어그램 | Mermaid (§다이어그램) | 관계·흐름·순서·상태를 문장으로 쓰면 3문장을 넘길 때 |
| 3. HTML | 결론 박스·표·접기(`<details>`)·근거 배지 | 상세를 접어야 결론이 묻히지 않을 때 |
| 4. 영상 | 다루지 않는다 | 만들고 검증할 수단이 없다 |

- 낮은 단으로 충분하면 위로 올리지 않는다. 다이어그램과 접기는 독자의 시간을 쓰는 장치다.
- **화면은 근거가 아니다.** 위로 갈수록 읽기는 쉬워지고 검증은 어려워진다. 그래서 모든 주장에 원본 근거 번호를 달고, 사실·추정·미확인을 배지로 구분한다.

## 골격 (S1000D 정보 유형)

이 레포트는 외부 플랫폼(슬랙·GitHub·Confluence)에 올리지 않는 글이라 **항공 기술 문서 컨벤션을 그대로 따른다.** 문장은 ASD-STE100 전면 수준 (`writing-standards.md §문장`), 구조는 항공 기술 문서 표준 S1000D 의 정보 유형이다. S1000D 의 XML 스키마·데이터 모듈 코드는 읽는 시스템이 없어서 쓰지 않는다.

### 유형 고르기

S1000D 는 데이터 모듈 하나에 정보 유형 하나를 담는다. 레포트도 **파일 하나에 주 유형 하나**다. 유형을 먼저 고르고 그 템플릿(`${CLAUDE_PLUGIN_ROOT}/skills/communicate/assets/`)을 복사한다.

| 유형 | 템플릿 | 고르는 경우 | 제목 예 |
|---|---|---|---|
| 설명형 | `report-descriptive.html` | 조사·분석 결과, 설계 검토·선택지 비교, 진행 보고, 인수인계 | `인증 세션 캐시 - 설명` |
| 절차형 | `report-procedural.html` | 독자가 따라 할 작업이 본론일 때. 이전·설치·복구 절차 | `결제 DB - 버전 16 이전 절차` |
| 고장 탐구형 | `report-fault.html` | 장애·버그의 원인 분석. 증상에서 원인을 좁혀 조치까지 | `결제 재시도 큐 - 장애 분석 (2026-10-20)` |

- 유형이 섞이면 주 유형 하나를 고른다. 설명형·고장 탐구형의 "확인 절차"는 절차형 규칙으로 쓰는 짧은 섹션이다. 절차가 본론이면 절차형 레포트를 따로 만들고 경로로 가리킨다.
- **제목은 S1000D 식 "대상 - 정보 유형"이다.** 대상은 검색어가 되는 이름으로 쓴다. `<title>` 과 `<h1>` 을 같게 쓴다.

### 공통 영역 (세 유형 모두)

| 영역 | 담는 것 |
|---|---|
| 머리 | 제목, 절대 날짜, 대상 독자, **적용 대상** (버전·환경·범위 — 이 글이 맞는 조건) |
| 결론 박스 | 결론 2~3문장 + 독자가 할 일 (없으면 "할 일 없음") |
| 상세 (`<details>`) | 필요한 사람만 펼쳐 볼 내용. 없으면 지운다 |
| 근거 | 번호 목록. 본문 주장에서 `[n]` 으로 가리킨다 |

### 유형별 본문 (순서 고정)

| 유형 | 본문 섹션 |
|---|---|
| 설명형 | 대상 설명 → 주의할 점 → 확인 절차 → 결정과 버린 선택지 |
| 절차형 | 사전 요구사항 (필요한 조건 · 필요한 것 · 안전) → 절차 → 완료 후 요구사항 (기대 결과 · 되돌리기) |
| 고장 탐구형 | 고장 설명 (증상 · 영향 · 발생 시점) → 원인 분리 (검사 → 결과 → 판정) → 조치 → 확인 절차 → 결정과 버린 선택지 |

- **대상 설명**: 소제목 하나에 주제 하나. 문단은 주제문 먼저, 문장 6개 이하.
- **안전 지시 (경고·주의·참고)**: `<div class="safety warning|caution|note">` 로 쓴다. 작업 전체에 걸리면 사전 요구사항의 "안전"이나 "주의할 점"에 둔다. 단계 하나에 걸리면 **그 단계 바로 앞**에 둔다. 형식은 `writing-standards.md §문장` 의 안전 지시 규칙이다.
- **절차 단계**: 번호를 붙인다. 한 단계에 지시 하나. 하위 단계는 중첩 번호 목록으로 쓴다.
- **원인 분리**: 검사마다 "무엇을 확인했는가 → 결과 → 다음 검사 또는 판정"으로 쓴다. 판정한 원인에는 `사실` 또는 `추정` 배지를 단다.
- 쓰지 않는 섹션은 통째로 지운다. 순서는 바꾸지 않는다.

### 채우기

- `data-fill` 속성이 붙은 요소는 채울 자리다. 내용을 채우고 속성을 지운다. 남은 `data-fill` 은 검증 스크립트가 잡는다.
- **맥락 이전 4요소(왜·무엇을·어떻게·확인 방법)는 섹션 제목이 아니라 점검 목록이다.** 다 채운 뒤 네 질문의 답이 어딘가에 있는지 확인한다.
- 남이 만든 코드의 의도를 추정해 "버린 선택지"를 채우지 않는다. 추정이 필요하면 대상 설명에 `추정` 배지를 달아 쓴다.
- 근거 배지: `<span class="tag fact">사실</span>`, `<span class="tag guess">추정</span>`, `<span class="tag unknown">미확인</span>`.
- CSS 와 스크립트는 파일 안에 둔다. 외부 이미지·폰트·스크립트를 불러오지 않는다. Mermaid 로더만 예외이고, 검증 단계에서 지워진다.
- 라이트·다크 모드, 인쇄, 모바일 폭은 템플릿 CSS 가 처리한다. 스타일을 새로 짜지 않는다.

## 다이어그램

- `<pre class="mermaid">` 블록에 Mermaid 문법으로 쓴다. 여는 태그는 이 형태로 시작해야 검증 스크립트가 찾는다.
- 블록 안의 `<`, `>`, `&` 는 `&lt;`, `&gt;`, `&amp;` 로 쓴다 — `A --> B` 는 `A --&gt; B`.
- 한 다이어그램에 메시지 하나. 노드는 12개 이하로 둔다.
- 노드·엣지는 **본문에 나온 것만** 쓴다. 다이어그램을 지워도 본문만으로 정보가 전달돼야 한다.
- 다이어그램 바로 앞 문장에서 무엇을 보여 주는지 한 줄로 쓴다.
- 종류: `flowchart`(흐름·분기), `sequenceDiagram`(주체 사이 순서), `stateDiagram-v2`(상태 전이), `timeline`·`gantt`(일정).

## 렌더링 검증 (전달 전 필수)

다이어그램은 실제로 그려져야 전달된다. 파일을 쓴 쪽이 전달 전에 실행한다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/report/render-report.mjs" reports/2026-10-20-payment-retry.html
```

스크립트는 같은 입력에 같은 결과를 낸다.

1. 남은 `data-fill` 이 있으면 실패한다.
2. 헤드리스 Chromium 으로 열어 Mermaid 를 렌더링한다. 문법 오류가 있으면 실패한다.
3. 렌더링된 SVG 를 파일에 구워 넣고 로더를 지운다. Mermaid 원본은 다이어그램 아래 접기에 남는다.
4. 네트워크를 막은 채 다시 열어 외부 요청·스크립트 오류·빈 다이어그램이 없는지 확인한다.
5. 모두 통과해야 원래 파일을 바꾼다.

| 종료 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 `OK` | 네트워크 없이도 다이어그램이 보인다 | 전달한다 |
| 1 `BROKEN` | 고칠 것이 있다 (출력에 위치·이유가 있다) | 고치고 다시 실행한다. 원래 파일은 바뀌지 않았다 |
| 2 `UNVERIFIED` | 검증할 수 없었다 (playwright·Chromium 없음, Mermaid CDN 차단) | 아래 순서로 대응한다 |

`UNVERIFIED` 대응:

1. CDN 이 막힌 환경이면 `npm i mermaid@11.17.2` 로 받은 `node_modules/mermaid/dist` 를 `--mermaid-dist <dir>` 로 지정해 다시 실행한다.
2. playwright·Chromium 이 없으면 설치가 필요하다. 사용자 환경을 바꾸는 일이므로 먼저 사용자에게 묻는다 (`npm i -g playwright`, `npx playwright install chromium`).
3. 그래도 검증하지 못하면 파일은 Mermaid 를 CDN 에서 불러오는 상태로 남는다. 네트워크가 열린 브라우저에서는 그려진다. 이때는 **"다이어그램 렌더링 미검증"을 보고에 쓴다.** 검증한 것처럼 말하지 않는다.

Mermaid 버전은 세 템플릿의 로더에 `mermaid@11.17.2` 로 고정돼 있다. 올릴 때는 세 템플릿과 이 절을 함께 바꾼다.

## 저장과 전달

- **경로**: 사용자가 정하지 않으면 작업 디렉토리의 `reports/YYYY-MM-DD-<주제>.html`. `<주제>` 는 영어 소문자와 하이픈으로 쓴다.
- **커밋**: 사용자가 요청할 때만 한다.
- **채팅 보고**: 파일 경로, 결론 2~3줄, 검증 결과(`OK` 또는 미검증)만 쓴다. 레포트 내용을 채팅에 다시 옮기지 않는다 — 같은 정보는 한 자리에 한 번만.
- **외부 게시**(위키 업로드·슬랙 첨부): `SKILL.md §외부 전송 2단계` 를 따른다. 로컬 파일을 만드는 것은 전송이 아니다.
- **위임**: sub-agent 에 맡길 때는 고른 유형의 템플릿 경로, 저장 경로, 검증 명령을 prompt 에 함께 넣고, 검증 결과를 보고받는다.
