# HTML 레포트

보고서 성격 산출물의 기본 형식이다. 문장 기준(독자 수준·해요체·목록과 문단 구분·STE100 전면 수준·맥락 이전 4요소)은 `SKILL.md` 기준선 그대로다. 이 문서는 **그 글을 담는 그릇**(구조·다이어그램·검증)을 정한다.

---

## 언제 만드는가

성질로 판단한다 (`delivery-context.md`). **남는 글 + 브라우저로 여는 자리 + 독자가 읽고 판단하는 글**이면 HTML 레포트다.

| 만든다 | 만들지 않는다 (그 자리의 형식) |
|---|---|
| 분석·조사 결과 | 채팅 답변 ("쉽게 설명해줘" 포함) |
| 장애 원인 분석 | PR 본문·리뷰 코멘트 (`git` 스킬 양식) |
| 진행·주간 보고 | 슬랙 메시지·이슈 코멘트 |
| 설계 검토·선택지 비교 | 릴리스 노트 |
| 인수인계 문서 | 스펙 문서 (`spec-write`)·저장소에 남길 마크다운 문서 |

- 사용자가 다른 형식(마크다운·노션 등)을 지정하면 그 형식이 우선한다.
- 흘러가는 자리에도 알려야 하면 그 자리 형식으로 결론 2~3줄과 레포트 경로를 보낸다.

## 형식 사다리

Andrej Karpathy 는 LLM 출력을 이해하기 쉽게 만드는 형식을 네 단으로 제안했다 (X, 2026-10-02): ASD-STE100 문장 → 다이어그램 → 인터랙티브 HTML → 설명 영상. 위로 갈수록 이해하기 쉽다. 이 레포트는 1~3단을 한 파일에 담는다.

| 단 | 레포트에서 | 쓰는 조건 |
|---|---|---|
| 1. 문장 | 결론·캡션·한 문장 이유·안전 지시 (`writing-standards.md §문장`) | 표·다이어그램이 담지 못하는 것 |
| 2. 다이어그램 | Mermaid (§다이어그램) | 내용의 모양이 흐름·순서·상태일 때 (§형식 선택) |
| 3. HTML | 결론 박스·수치 카드·탭·카드 배치·표·단계 흐름·경고 상자·근거 링크와 배지 | 항상 (템플릿이 제공) |
| 4. 영상 | 다루지 않는다 | 만들고 검증할 수단이 없다 |

- **표·다이어그램이 먼저다.** 내용의 모양이 표·다이어그램에 맞으면 그 형식으로 쓴다. 문장은 형식이 담지 못하는 것만 쓴다.
- **모양이 맞지 않으면 그리지 않는다.** 행이 하나인 표, 노드가 2개인 흐름도는 문장으로 쓴다. 장식용 그림은 독자의 시간만 쓴다.
- **화면은 근거가 아니다.** 위로 갈수록 읽기는 쉬워지고 검증은 어려워진다. 그래서 모든 주장에 원본 근거 번호를 달고, 사실·추정·미확인을 배지로 구분한다.

### 형식 선택

내용의 모양으로 형식을 고른다. 분량(몇 문장인지)으로 고르지 않는다.

| 내용의 모양 | 형식 |
|---|---|
| 항목 2개 이상 × 속성 2개 이상, 선택지 비교, 속성(값·상태·수치)의 전후 비교 | 표 (`.table-wrap`) |
| 구조·흐름의 전후 비교 | 같은 모양의 Mermaid `flowchart` 두 장 (같은 방향, 같은 노드 이름·순서. 바뀐 노드만 표시) |
| 분기가 있는 흐름, 3단계 이상의 인과 사슬 | Mermaid `flowchart` |
| 주체 2개 이상이 주고받는 순서 | Mermaid `sequenceDiagram` |
| 상태와 전이 | Mermaid `stateDiagram-v2` |
| 날짜가 있는 사건 | 6개 이하이고 정확한 시각이 중요하면 표, 아니면 Mermaid `timeline`·`gantt` |
| 핵심 수치 1~4개 | 수치 카드 (`.stats`: 수치·단위·비교 기준·`[n]`) |
| 독자가 따라 할 단계 | 단계 흐름 (`ol.steps`). 명령을 복사해야 하므로 다이어그램으로 그리지 않는다 |
| 경고·주의·참고 | 경고 상자 (`.callout`) |
| 이유가 둘 이상인 결정, 선택지 사이의 트레이드오프 | 표 (`.table-wrap`) |
| 한 문장으로 끝나는 인과·판단 | 문장 |

문장이 꼭 필요한 자리: 결론 박스, 표·다이어그램마다 붙는 캡션 한 줄, 한 문장으로 끝나는 이유, 안전 지시, `추정`·`미확인` 의 단서.

## 골격

템플릿 `${CLAUDE_PLUGIN_ROOT}/skills/communicate/assets/report-template.html` 을 복사해서 채운다.

Karpathy 가 제안한 대로 **ASD-STE100 을 빌려 쓴다.** 문장은 전면 수준이다 (`writing-standards.md §문장`). 구조도 STE100 이 나누는 세 가지 글을 따른다 — 설명하는 글(descriptive writing), 따라 하는 글(procedural writing), 안전 지시(safety instructions). 섹션마다 이 셋 중 하나만 담는다.

| 순서 | 영역 | STE100 글 종류 | 담는 것 | 언제 |
|---|---|---|---|---|
| 0 | 머리 (`<title>`, `<h1>`, 메타) | — | 검색어가 되는 제목 (대상·행위·시점), 절대 날짜, 대상 독자 | 항상 |
| 1 | 결론 박스 | 설명 | 결론 2~3문장 + 독자가 할 일 (없으면 "할 일 없음"). 핵심 수치가 있으면 수치 카드 | 항상 |
| 2 | 대상 설명 | 설명 | 배경, 조사·분석 결과, 바뀐 것. **주제 하나 = 카드 하나**: 제목 + 캡션 한 줄 + 형식 하나(표·다이어그램) | 항상 |
| 3 | 주의할 점 | 안전 지시 | 경고(사람·데이터가 다칠 수 있음)·주의(장비·설정이 망가질 수 있음)·참고 | 있을 때만 |
| 4 | 확인 절차 | 절차 | 사전 조건 → 번호 단계 → 기대 결과. 단계에 걸린 경고·주의는 그 단계 바로 앞에 다시 둔다 | 독자가 따라 할 것이 있을 때 |
| 5 | 결정과 버린 선택지 | 설명 | **우리가 내린** 결정과 버린 안 + 이유 | 결정이 있을 때만 |
| 6 | 상세 | 설명 | 필요한 사람만 볼 내용. 대상 설명의 카드가 6개를 넘으면 덜 중요한 카드를 여기로 옮긴다 | 있을 때만 |
| 7 | 근거 | — | 번호 목록. 본문 주장에서 `[n]` 으로 가리킨다 | 항상 |

- 쓰지 않는 섹션은 통째로 지운다. 순서는 바꾸지 않는다. 분량이 작으면 대상 설명과 확인 절차만 남겨도 된다.
- 이 순서는 HTML 소스의 순서이자 탭 순서이고 인쇄 순서다. 탭과 카드 배치는 템플릿이 한다.

### 변화형 골격

**바뀌는 것을 다루는 보고서**는 2·3·5·6번 자리를 아래로 바꿔 쓴다. 설계 검토, 장애 원인 분석과 재발 방지, 개선 제안, 이전(마이그레이션) 계획이 여기에 든다. 템플릿은 `${CLAUDE_PLUGIN_ROOT}/skills/communicate/assets/report-template-change.html` 이다.

고르는 기준: 결론을 "지금은 A 인데 B 로 바꾼다(바꾸자)"로 쓸 수 있고, 지금 구조에서 깨지는 지점을 셀 수 있으면 변화형이다. 바뀌는 것이 없는 조사 결과, 진행 보고, 인수인계, 결정 전의 선택지 비교는 기본 골격을 쓴다.

| 순서 | 영역 | STE100 글 종류 | 담는 것 | 언제 |
|---|---|---|---|---|
| 0 | 머리 | — | 기본 골격과 같다. 메타 아래에 읽는 순서 한 줄을 둔다 (§본문과 부록) | 항상 |
| 1 | 결론 박스 | 설명 | 결론·할 일. 구조가 바뀌면 전후 흐름도 한 쌍 (§전후 흐름도 한 쌍) | 항상 |
| 2 | 지금 | 설명 | 지금의 흐름과 문제 표. 깨지는 지점마다 번호를 단다 | 항상 |
| 3 | 바뀐 뒤 | 설명 | 바뀐 뒤의 흐름과 해결 표. 문제와 같은 번호로 짝을 짓는다. 우리가 내린 결정과 버린 안은 이 탭의 표 카드 하나로 둔다 | 항상 |
| 4 | 남는 위험 | 안전 지시 | 해결이 없는 번호, 바꾸면서 새로 생기는 위험, 독자에게 하는 요청. 경고·주의는 경고 상자로 쓴다 | 항상. 없으면 "남는 위험 없음" 한 줄 |
| 5 | 확인 절차 | 절차 | 기본 골격 4번과 같다 | 독자가 따라 할 것이 있을 때 |
| 6 | 부록 | 설명 | 찾아보는 값 (§본문과 부록) | 있을 때만 |
| 7 | 근거 | — | 기본 골격과 같다 | 항상 |

- 기본 골격의 대상 설명은 지금·바뀐 뒤로 나뉜다. 주의할 점은 남는 위험에, 결정과 버린 선택지는 바뀐 뒤에, 상세는 부록에 들어간다.
- 두 골격의 섹션 이름을 섞지 않는다.

#### 문제 번호

- 지금 구조에서 깨지는 지점마다 번호(❶❷❸…)를 하나 단다. 번호 하나는 문서 전체에서 문제 하나만 가리킨다.
- 같은 번호를 네 곳에 쓴다: 지금 흐름도에서 깨지는 노드, 문제 표의 첫 열, 바뀐 뒤 흐름도에서 그 문제를 푸는 노드, 해결 표의 첫 열.
- 지금 탭의 번호 집합은 (바뀐 뒤 + 남는 위험) 탭의 번호 집합과 같아야 한다. 해결이 없는 번호는 남는 위험에 같은 번호로 쓴다. 번호를 조용히 빼지 않는다.
- 버린 안을 쓸 때는 그 안이 풀지 못하는 문제를 같은 번호로 적는다.
- 번호는 노드 라벨에 넣고, 문제 이름은 표에 쓴다. 노드에 이름을 길게 쓰면 좁은 화면에서 깨진다.
- 깨지는 노드와 새로 생기거나 바뀌는 노드는 아래 `classDef` 두 줄로 구분하고, 캡션에 뜻을 쓴다 ("붉은 테두리 = 깨지는 지점"). 다이어그램 배경은 두 색 모드 모두 흰색이라 이 색을 그대로 쓴다. 색만으로 전하지 않는다 — 번호가 글자 표시다. 점선은 "추정"의 뜻이라 쓰지 않는다 (§다이어그램).

```text
classDef broken fill:#ffebe9,stroke:#cf222e,stroke-width:2px,color:#1f2328
classDef added fill:#dafbe1,stroke:#1a7f37,stroke-width:2px,color:#1f2328
```

#### 전후 흐름도 한 쌍

구조가 바뀌는 보고서는 결론 박스의 결론·할 일 문장 바로 아래에 "지금"과 "바뀐 뒤" 흐름도를 한 쌍 둔다. 결론만 읽는 독자도 무엇이 바뀌는지 본다. 문장을 먼저 두는 것은 좁은 화면에서 그림 두 장이 결론을 첫 화면 밖으로 밀지 않게 하려는 것이다.

- 결론 박스 안 `<div class="grid">` 에 카드 두 장으로 둔다. 결론 박스 밖에 섹션을 따로 만들지 않는다 — `<h2>` 없는 섹션은 탭 검사에서 실패한다.
- 두 장은 같은 방향, 같은 노드 이름과 순서로 그린다. 달라진 노드만 `classDef` 로 표시한다.
- 한 장에 노드는 3~4개다. 더 필요하면 지금·바뀐 뒤 탭에서 그린다.
- 이 한 쌍으로 구조를 다 보였으면 지금·바뀐 뒤 탭에는 흐름도를 다시 그리지 않고 표만 둔다.

#### 본문과 부록

| 자리 | 독자가 하는 일 | 담는 것 |
|---|---|---|
| 본문 (결론 ~ 남는 위험) | 이해하고 판단한다 | 흐름도, 번호로 짝 지은 문제·해결 표, 남는 위험, 요청 |
| 부록 | 필요할 때 찾아본다 | 값, 계약(입출력 형식), 설정, 결정 전문, 용어 |

- 가르는 질문: "이것을 건너뛰어도 판단할 수 있는가?" 그렇다면 부록이다.
- 본문 탭의 카드가 6개를 넘으면 부록으로 옮기지 않고 본문을 줄인다. 부록은 넘친 카드를 받는 자리가 아니다.
- 머리의 메타 아래에 읽는 순서를 한 줄로 쓴다: "지금 → 바뀐 뒤 → 남는 위험까지 읽으면 판단할 수 있어요. 부록은 찾아볼 때만 열어요." 탭 줄이 보여 주지 않는 것(어디까지 읽으면 되는지)만 쓴다.

### 탭

머리와 결론 박스는 항상 보인다. 그 아래 섹션(2~7)은 템플릿 스크립트가 `<h2>` 로 탭을 만든다. 독자는 스크롤 대신 탭을 눌러 섹션을 바꿔 본다.

| 자리 | 보이는 것 | 누가 만드나 |
|---|---|---|
| 항상 보임 | 머리, 결론 박스(수치 카드 포함), 경고·주의 건수 띠 | 작성자 (건수 띠는 스크립트) |
| 탭 | 대상 설명(기본 탭) · 주의할 점 · 확인 절차 · 결정과 버린 선택지 · 상세 · 근거. 변화형은 지금(기본 탭) · 바뀐 뒤 · 남는 위험 · 확인 절차 · 부록 · 근거 | 스크립트가 섹션의 `<h2>` 로 만든다 |
| 탭 없음 | 섹션이 2개 이하면 탭을 만들지 않고 모두 펼친다. 인쇄와 스크립트 꺼짐도 모두 펼친다 | 스크립트 |

- 섹션마다 `<section>` 바로 아래에 `<h2>` 를 둔다. 탭 이름은 고른 골격(§골격 또는 §변화형 골격)의 섹션 이름을 그대로 쓴다. 두 골격의 이름을 섞거나 새 이름을 만들지 않는다.
- 하위 탭을 만들지 않는다. 대상 설명 안의 주제는 카드로 나란히 놓는다.
- 한 탭에 카드가 6개를 넘으면 상세로 옮긴다. 변화형은 옮기지 않고 본문 카드를 줄인다 (§본문과 부록). 한 탭이 길어지면 다시 스크롤이 생긴다.
- 경고·주의가 탭 뒤에 숨지 않게, 스크립트가 건수를 탭 밖 띠와 탭 이름에 보여 준다. 단계에 걸린 경고·주의는 그 단계 바로 앞에 다시 둔다 (§골격 4).
- 본문의 `[n]` 은 스크립트가 근거 n번 링크로 바꾼다. 누르면 근거 탭이 열리고, 마우스를 올리면 근거가 보인다. 작성자는 `[n]` 만 쓴다.
- `<!-- tabs:start -->` ~ `<!-- tabs:end -->` 스크립트는 고치지 않는다.
- 외부 플랫폼(슬랙·GitHub·Confluence)에 올리는 글은 이 골격이 아니라 그 자리의 양식을 따른다 (PR 본문 4단은 `git` 스킬, 나머지는 `delivery-context.md`).

### 채우기

- `data-fill` 속성이 붙은 요소는 채울 자리다. 내용을 채우고 속성을 지운다. 남은 `data-fill` 은 검증 스크립트가 잡는다.
- **맥락 이전 4요소(왜·무엇을·어떻게·확인 방법)는 섹션 제목이 아니라 점검 목록이다.** 다 채운 뒤 네 질문의 답이 어딘가에 있는지 확인한다.
- 남이 만든 코드의 의도를 추정해 "버린 선택지"를 채우지 않는다. 추정이 필요하면 대상 설명에 `추정` 배지를 달아 쓴다.
- 근거 배지: `<span class="tag fact">사실</span>`, `<span class="tag guess">추정</span>`, `<span class="tag unknown">미확인</span>`.
- CSS 와 스크립트는 파일 안에 둔다. 외부 이미지·폰트·스크립트를 불러오지 않는다. Mermaid 로더만 예외이고, 검증 단계에서 지워진다.
- 라이트·다크 모드, 인쇄, 반응형 배치는 템플릿 CSS 가 처리한다. 스타일을 새로 짜지 않는다. `<style>` 을 더하거나 `style=` 속성을 쓰지 않는다. Mermaid 소스 안의 `classDef` 는 예외이고, §문제 번호의 두 줄만 쓴다.
- HTML 주석 안에 `<pre class="mermaid">` 나 `data-fill` 을 두지 않는다. 검증 스크립트는 주석 안도 다이어그램·자리표시자로 센다.

### 반응형 배치

템플릿이 주는 부품만 쓴다. 카드는 넓은 화면에서 한 줄에 2~3개, 좁은 화면에서 1개씩 놓인다.

| 부품 | 마크업 | 쓰는 자리 |
|---|---|---|
| 수치 카드 | `<dl class="stats">` 안에 `<div><dt>이름</dt><dd>수치<small>비교 기준 [n]</small></dd></div>` | 결론 박스 안. 1~4개 |
| 카드 배치 | `<div class="grid">` 안에 `<article class="card">` | 섹션 안. 카드마다 주제 하나 |
| 전체 폭 카드 | `<article class="card span-all">` | 열 4개 이상인 표, 노드가 많은 다이어그램, 확인 절차, 결정 표 |
| 캡션 | `<p class="caption">` | 표·다이어그램 바로 앞. 메시지 한 줄 + 배지 + `[n]` |
| 표 | `<div class="table-wrap"><table>…</table></div>` | 모든 표. 좁은 화면에서 표만 가로로 스크롤된다 |
| 상태 칸 | `<td class="ok">`·`warn`·`bad` | 표의 상태 칸. 색만으로 전하지 않고 글자도 쓴다 ("통과"·"실패") |
| 단계 흐름 | `<ol class="steps">` | 확인 절차의 단계 |
| 경고 상자 | `<p class="callout danger">`·`warn`·`note` | 주의할 점의 경고·주의·참고 |

- 표는 열을 5개 이하로 둔다. 넘으면 표를 나누거나 전체 폭 카드에 둔다.
- 같은 정보를 표·다이어그램과 문장에 두 번 쓰지 않는다. 캡션은 그림의 메시지만 말한다.

## 다이어그램

- `<pre class="mermaid">` 블록에 Mermaid 문법으로 쓴다. 여는 태그는 이 형태로 시작해야 검증 스크립트가 찾는다.
- 블록 안의 `<`, `>`, `&` 는 `&lt;`, `&gt;`, `&amp;` 로 쓴다 — `A --> B` 는 `A --&gt; B`.
- 한 다이어그램에 메시지 하나. 노드는 12개 이하로 둔다.
- 노드·엣지는 **근거에 있는 것만** 쓴다. 근거가 다른 엣지는 라벨에 `[n]` 을 단다. 추정한 엣지는 점선(`-.->`)으로 그리고 라벨에 "추정"을 쓴다.
- 다이어그램 바로 앞에 캡션(`<p class="caption">`)을 두고, 무엇을 보여 주는지 한 줄로 쓴다. 근거 번호와 배지는 캡션에 단다. 다이어그램이 그려지지 않으면 독자는 캡션과 원본(Mermaid 접기)으로 읽는다.
- 방향은 `TD`(위→아래)가 기본이다. 좁은 화면에서 읽히게 하려고 그렇다. `LR` 은 노드가 4개 이하일 때만 쓴다.
- 닫힌 `<details>` 처럼 숨겨진 자리에 넣지 않는다. 크기가 0으로 재어져 그림이 깨진다. 탭 안은 괜찮다 — 스크립트가 다이어그램을 다 그린 뒤에 탭을 만든다.
- 종류: `flowchart`(흐름·분기), `sequenceDiagram`(주체 사이 순서), `stateDiagram-v2`(상태 전이), `timeline`·`gantt`(일정).

## 렌더링 검증 (전달 전 필수)

다이어그램은 실제로 그려져야 전달된다. 파일을 쓴 쪽이 전달 전에 실행한다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/report/render-report.mjs" reports/2026-10-20-payment-retry.html
```

스크립트는 같은 입력에 같은 결과를 낸다.

1. 남은 `data-fill` 이 있으면 실패한다.
2. 헤드리스 Chromium 으로 열어 Mermaid 를 렌더링한다. 문법 오류가 있으면 실패한다.
3. 렌더링된 SVG 를 파일에 구워 넣고 로더를 지운다. Mermaid 원본은 다이어그램 아래 접기에 남는다.
4. 네트워크를 막은 채 다시 열어 외부 요청·스크립트 오류·빈 다이어그램이 없는지 확인한다.
5. 섹션이 3개 이상이면 섹션마다 탭이 있는지 확인한다.
6. 375px(휴대폰)과 1280px(데스크톱) 폭에서 탭을 하나씩 열어, 페이지가 가로로 넘치지 않는지와 크기가 0인 다이어그램이 없는지 확인한다. 넘치면 원인 요소를 출력한다.
7. 인쇄 모드에서 모든 섹션이 보이는지 확인한다.
8. 모두 통과해야 원래 파일을 바꾼다.

| 종료 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 `OK` | 네트워크 없이도 다이어그램이 보인다 | 전달한다 |
| 1 `BROKEN` | 고칠 것이 있다 (출력에 위치·이유가 있다) | 고치고 다시 실행한다. 원래 파일은 바뀌지 않았다 |
| 2 `UNVERIFIED` | 검증할 수 없었다 (playwright·Chromium 없음, Mermaid CDN 차단) | 아래 순서로 대응한다 |

`UNVERIFIED` 대응:

1. CDN 이 막힌 환경이면 `npm i mermaid@11.17.2` 로 받은 `node_modules/mermaid/dist` 를 `--mermaid-dist <dir>` 로 지정해 다시 실행한다.
2. playwright·Chromium 이 없으면 설치가 필요하다. 사용자 환경을 바꾸는 일이므로 먼저 사용자에게 묻는다 (`npm i -g playwright`, `npx playwright install chromium`).
3. 그래도 검증하지 못하면 파일은 Mermaid 를 CDN 에서 불러오는 상태로 남는다. 네트워크가 열린 브라우저에서는 그려진다. 이때는 **"다이어그램 렌더링 미검증"을 보고에 쓴다.** 검증한 것처럼 말하지 않는다.

Mermaid 버전은 템플릿 로더에 `mermaid@11.17.2` 로 고정돼 있다. 올릴 때는 템플릿과 이 절을 함께 바꾼다.

### 파일만 보고 판정

검증이 끝났는지는 파일 상태로 정한다. 검증을 통과한 파일만 다이어그램이 SVG 로 구워지고 로더가 지워진다. 그래서 브라우저가 없는 쪽(위임을 맡긴 쪽, 도구 없는 환경)도 파일만으로 판정할 수 있다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/report/render-report.mjs" --check reports/2026-10-20-payment-retry.html 2>&1 | tail -1
```

`--check` 는 브라우저를 띄우지 않고 파일을 바꾸지 않는다. 종료 코드는 위 표와 같다.

| 파일 상태 | 판정 |
|---|---|
| 로더가 없고, 남은 `<pre class="mermaid">` 가 없고, 다이어그램마다 SVG 가 있고, `data-fill` 이 없다 | 0 `OK` |
| 로더가 남아 있다 (아직 굽지 않았다) | 2 `UNVERIFIED` |
| 로더 없이 mermaid 블록이 남았다, SVG 없는 다이어그램이 있다, `data-fill` 이 남았다 | 1 `BROKEN` |

- 일반 실행과 `--check` 모두 마지막 줄이 판정이다 (`OK: <경로> (다이어그램 n개 SVG 포함. …)`). 보고에는 이 한 줄을 그대로 붙인다.
- 구운 뒤에 파일을 손으로 고쳤으면 일반 실행을 다시 한다. 파일 상태 `OK` 는 "구워졌다"만 보여 준다. 가로 넘침·탭·인쇄 검사는 일반 실행이 통과해야 파일을 바꾼다는 사실로만 보증된다.
- node 도 없으면 grep 으로 같은 것을 본다. 앞의 두 값은 0, 뒤의 두 값은 다이어그램 수로 같아야 한다.

```bash
grep -c '<!-- mermaid:start -->' <파일>
grep -c '<pre class="mermaid"' <파일>
grep -o '<figure class="diagram">' <파일> | wc -l
grep -o '<figure class="diagram"><svg' <파일> | wc -l
```

`<svg` 개수나 CDN 주소로 세지 않는다. SVG 안에 SVG 가 들어갈 수 있고, CDN 주소는 근거로 인용될 수 있다.

## 저장과 전달

- **경로**: 사용자가 정하지 않으면 작업 디렉토리의 `reports/YYYY-MM-DD-<주제>.html`. `<주제>` 는 영어 소문자와 하이픈으로 쓴다.
- **커밋**: 사용자가 요청할 때만 한다.
- **채팅 보고**: 파일 경로, 결론 2~3줄, 검증 명령의 마지막 출력 한 줄(§파일만 보고 판정)만 쓴다. 레포트 내용을 채팅에 다시 옮기지 않는다 — 같은 정보는 한 자리에 한 번만.
- **외부 게시**(위키 업로드·슬랙 첨부): `SKILL.md §외부 전송 2단계` 를 따른다. 로컬 파일을 만드는 것은 전송이 아니다.
- **위임**: sub-agent 에 맡길 때는 템플릿 경로(기본 또는 변화형), 저장 경로, 검증 명령을 prompt 에 함께 넣고, 검증 명령의 마지막 출력 한 줄을 보고받는다. 받은 쪽은 전달 전에 `--check` 로 파일 상태를 다시 본다.
