# 채널별 적응

채널이 바꾸는 것은 **포장**뿐이다. 독자 수준·해요체 단문·개조식·맥락 이전 4요소(왜/무엇을/어떻게/확인 방법)는 채널과 무관하게 유지된다 (`SKILL.md §기본값`, `§맥락 이전`).

채널을 고를 때 묻는 것은 셋이다:

1. **읽는 사람이 스크롤할 의지가 있나** → 길이 상한
2. **나중에 다시 찾을 문서인가, 흘러가는 대화인가** → 제목·구조의 필요성
3. **답을 기다리는가** → 질문·액션을 어디에 둘지

---

## Slack · Discord (흘러가는 대화)

읽는 사람은 다른 일을 하다 알림으로 본다. **첫 줄에서 판단이 끝나야 한다.**

- **첫 줄 = 결론 + 상대가 할 일.** 배경은 그 아래로 내린다.
- **길이**: 화면 한 눈에. 넘치면 스레드로 접거나 문서 링크로 뺀다 — 긴 글을 채널 본문에 쏟지 않는다.
- **구조**: 제목 계층(`##`)을 쓰지 않는다. 불릿 3~5개가 상한이다.
- **서식**: 코드·경로·명령은 인라인 코드로 감싼다. 여러 줄 코드는 코드블록으로. 표는 대체로 깨지므로 불릿으로 편다.
- **맥락 이전**: 넷 중 **왜 + 무엇을**을 본문에, 어떻게·확인 방법은 스레드나 링크로 내린다.
- **답이 필요하면 질문을 마지막 줄에 하나만** 둔다. 질문이 여러 개면 번호를 붙여 답하기 쉽게 만든다.
- 멘션은 실제로 행동이 필요한 사람에게만. 전체 멘션은 알림 피로를 만든다.

```
❌ 안녕하세요! 지난주부터 진행하던 작업 관련해서 공유드립니다. 처음에는 A 방식으로
   접근했는데 성능 이슈가 있어서 B로 바꾸었고 그 과정에서 …          # 결론이 아래에 있다

✅ 결제 목록 로딩을 3.2초 → 0.4초로 줄였어요. 오늘 배포 예정입니다.
   • 원인: 목록 100개를 열면 DB에 101번 물어보고 있었어요
   • 조치: 한 번에 모아 조회하도록 바꿨어요 (`OrderRepository`)
   • 확인: 스테이징에서 100건 기준 0.4초 (측정 3회 평균)
   배포 시간 오후 3시로 잡아도 될까요?
```

## Notion · Confluence (남는 문서)

**나중에 검색으로 도착하는 사람**이 주 독자다. 지금 읽는 사람보다 6개월 뒤 읽는 사람을 기준으로 쓴다.

- **제목이 곧 검색어.** "작업 공유"가 아니라 "결제 목록 조회 성능 개선 (2026-07)"처럼 대상·행위·시점을 담는다.
- **맨 위 3줄 요약**을 고정으로 둔다 — 본문을 안 읽고 링크만 열어본 사람을 위한 것이다.
- **제목 계층**을 쓴다. 문서가 길면 목차를, 표로 표현되는 정보는 표로 둔다.
- **날짜와 상태를 박아둔다** — "현재", "최근", "곧"은 6개월 뒤 의미를 잃는다. `2026-07-28 기준`처럼 절대 시점으로.
- **링크는 제목과 함께**: "여기 참고"처럼 대상이 안 보이는 문구 대신, 링크 텍스트에 문서 제목("결제 도메인 스펙")을 넣어 클릭 전에 무엇인지 알 수 있게 한다.
- **맥락 이전 넷 모두** 담는다. 특히 *어떻게(버린 선택지 포함)* — 문서가 남는 이유의 절반이 이것이다.
- 코드 전문을 붙이지 않는다. 핵심만 인용하고 저장소 링크(가능하면 커밋·라인 고정 링크)로 건다.

## PR · 이슈 (검토받는 글)

읽는 사람은 **승인/거절을 결정하러** 온다.

- **PR 본문은 4단 고정** — 정확한 섹션 이름과 양식은 `git` 스킬 `references/cli-reference.md` 가 단일 출처다. 섹션을 임의로 바꾸거나 생략하지 않는다.
- **확인 방법은 체크리스트로** 쓴다. 리뷰어가 그대로 따라할 수 있어야 한다.
- **큰 변경은 읽는 순서를 안내한다** — "먼저 `X.rs` 인터페이스부터 보시면 나머지가 따라옵니다".
- 이슈는 **재현 조건 → 기대 동작 → 실제 동작 → 영향 범위** 순으로 쓴다. 재현 못 하는 이슈는 고쳐지지 않는다.
- 리뷰 코멘트에 답할 때: **동의/비동의를 먼저** 밝히고 이유를 뒤에 둔다. 반박이면 근거(코드·측정)를 붙인다.

## 이메일 · 보고서 (격식 있는 전달)

- **문체를 평서체로 바꾸는 유일한 채널**이다 (대외·공식). 그래도 문장은 짧게 유지한다.
- 제목에 **결론 또는 요청**을 담는다 — "8월 배포 일정 확정 요청(회신 8/2까지)".
- **요약(결론) → 근거 → 상세 → 부록** 순. 의사결정자는 요약만 읽고 끝낼 수 있어야 한다.
- 첨부·링크는 본문에서 무엇인지 설명하고 건다.
- 회신 기한과 필요한 결정을 **명시적으로** 적는다. "확인 부탁드립니다"는 무엇을 언제까지인지 알려주지 않는다.

## 채널 선택 자체가 틀리는 경우

- **길어질 내용을 채팅에 쏟기** → 읽히지 않고 검색도 안 된다. 문서로 쓰고 링크를 공유한다.
- **결정이 필요한 사안을 문서에만 두기** → 아무도 안 읽는다. 문서를 쓰고 **채팅으로 결론과 기한을 밀어준다**.
- **논의가 필요한 것을 PR 본문에 길게 쓰기** → 리뷰가 설계 토론으로 번진다. 설계는 이슈·문서에서 합의하고 PR은 결과를 싣는다.
