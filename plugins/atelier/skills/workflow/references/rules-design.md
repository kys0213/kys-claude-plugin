# .claude/rules 설계 (rules design)

아키텍처 레이어별 규칙 매핑, `paths:` frontmatter 전략, 규칙 파일 템플릿, 다중 언어 전략, paths 범용화 원칙, 규칙 내용 범용화 원칙, 규칙 스코프 경계. rules 구조를 제안·생성·검증할 때 로드한다.

공식 사양 출처: https://code.claude.com/docs/en/memory 의 `Organize rules with .claude/rules/` 절 — 이 문서의 로딩 모드·스코프·glob 서술은 해당 사양을 따른다.

## 1. 아키텍처 레이어 → 규칙 파일 매핑

### 공통 관심사 (언어 무관)

모든 프로젝트에 적용할 수 있는 보편적 관심사:

| 관심사 | 규칙 파일명 | 핵심 원칙 |
|---|---|---|
| 진입점 (Entrypoint) | `handler.md` 또는 `controller.md` | HTTP/CLI 파싱만, 로직 위임 |
| 비즈니스 로직 | `service.md` | 인터페이스 정의, DI, 트랜잭션 조율 |
| 데이터 접근 | `repository.md` | 추상화, 쿼리 캡슐화 |
| 도메인 모델 | `entity.md` 또는 `model.md` | 불변식, 밸류 오브젝트 |
| DTO / 계약 | `dto.md` | 입출력 타입 분리, 직렬화 |
| 모듈 경계 | `module-boundary.md` | 단방향 의존, 순환 금지 |
| 테스트 | `testing.md` | mock 전략, 테스트 구조 |
| 에러 처리 | `error-handling.md` | 에러 타입, 전파 규칙 |

### 프론트엔드 전용 관심사

| 관심사 | 규칙 파일명 | 핵심 원칙 |
|---|---|---|
| 컴포넌트 | `component.md` | props 설계, 합성, 접근성 |
| 훅/컴포저블 | `hook.md` | 상태 캡슐화, 재사용 |
| 상태 관리 | `store.md` | 전역/로컬 분리, 구독 패턴 |
| 페이지/라우팅 | `page.md` | 데이터 페칭, 레이아웃 |

## 2. `paths:` Frontmatter 전략

### 두 가지 로딩 모드 — 둘 다 정상

| 모드 | 로딩 시점 | 용도 |
|---|---|---|
| `paths:` 있음 (조건부) | 매칭되는 파일을 읽거나 수정할 때 (Lazy Context Injection) | 레이어·언어 한정 컨벤션 — 토큰 낭비 방지 |
| `paths:` 없음 (상시) | 세션 시작 시, `.claude/CLAUDE.md`와 동일 우선순위 | 모든 세션에서 유지돼야 하는 규칙 — 빌드 명령, 프로젝트 구조, "always do X" |

```yaml
---
paths:
  - "**/*handler*.go"        # 파일명 패턴
  - "**/*.controller.ts"     # 확장자 + 접미사 패턴
  - "**/controllers/**"      # 디렉토리 패턴
---
```

### 재주입 한계

조건부 규칙(과 하위 디렉토리의 nested CLAUDE.md)은 `/compact` 이후 자동 재주입되지 않습니다 — 매칭되는 파일을 다시 읽어야 재로드됩니다. 따라서 **"절대 하지 마라" 류의 안전·금지 규칙, 세션 내내 유지돼야 하는 규칙은 `paths:` 없이 두거나 `CLAUDE.md`에 남깁니다** (`paths:` 부여는 레이어·언어 한정 컨벤션에만). 실제 로드 여부의 실증 수단은 §4(검증)를 참조합니다.

### 패턴 작성 가이드

위 3가지 패턴(파일명 접미사·파일명 포함·디렉토리 기반) 중 프로젝트의 명명 규칙에 맞는 것을 고르고, 혼용 프로젝트라면 배열로 복합 지정합니다. 명명 규칙이 있는 프레임워크(NestJS 등)는 접미사 패턴이, Go처럼 접미사 규칙이 없는 언어는 파일명 포함 패턴이 적합합니다.

모노레포에서의 범용화 패턴은 §6 (paths 범용화 원칙)을 참조합니다.

## 3. 규칙 파일 템플릿

### 표준 구조

모든 규칙 파일은 다음 구조를 따릅니다:

```markdown
---
paths:
  - "<glob pattern>"
---

# <레이어명> Convention

> 한 줄 요약

## 원칙

1. **원칙 1**: 설명
2. **원칙 2**: 설명

## DO

- 원칙 서술 (+ 필요 시 구조 수준 패턴)

## DON'T

- 원칙 위반 서술 (+ 필요 시 구조 수준 패턴)

## 체크리스트

- [ ] 확인 항목 1
- [ ] 확인 항목 2
```

DO/DON'T 항목에 실제 코드 조각·실제 식별자를 담을지 여부는 §7 (규칙 내용 범용화 원칙)을 따릅니다.

### DO/DON'T 예시 (레이어별)

#### Handler / Controller

```markdown
## DO

- HTTP 파싱과 응답 변환만 담당
- 에러를 적절한 HTTP 상태 코드로 매핑
- 입력 유효성 검사는 DTO/스키마에 위임

## DON'T

- 비즈니스 로직을 핸들러에 직접 구현
- 데이터베이스를 직접 호출
- 다른 핸들러를 호출
```

Service, Repository 등 다른 레이어도 같은 추상화 수준(역할 서술 + 위반 사례)으로 DO/DON'T를 작성합니다 — 예: Service는 "인터페이스 우선 정의·생성자 주입" DO와 "HTTP 객체 의존·구체 구현 의존" DON'T, Repository는 "데이터 접근만 캡슐화" DO와 "비즈니스 로직 포함" DON'T.

## 4. Gap 분석 모드

기존 `.claude/rules/` 파일이 있을 때 gap 분석을 수행합니다.

### 분석 기준

1. **누락된 레이어**: 코드베이스에 해당 레이어가 존재하지만 규칙이 없는 경우
2. **로딩 모드 불일치** (§2): (a) 레이어 한정 컨벤션이 `paths:` 없이 상시 로드되는 경우 (토큰 낭비), (b) 안전·금지 규칙이 `paths:`로 내려가 있는 경우 (`/compact` 후 유실 위험). 그 외 조합 — 안전·"always do X" 규칙의 `paths:` 없음 — 은 의도된 선택이며 gap이 아님
3. **과도한 범위**: `paths:` 패턴이 너무 넓어 불필요하게 자주 로드되는 경우
4. **언어 미지원**: 모노레포에서 특정 언어의 규칙이 누락된 경우
5. **구현 결합**: 규칙에 실제 코드 조각·실제 식별자가 포함되어 코드 변경 시 규칙이 stale해질 위험이 있는 경우

### 검증 — 정적 분석 + 실제 로드 관측

Glob 교차검증(§6)은 "패턴이 의도한 파일을 매칭하는가"까지만 봅니다. "규칙이 실제로 로드되는가"는 별개 질문이며 두 수단으로 실증합니다:

- **`InstructionsLoaded` 훅**: 어떤 instruction 파일이 언제, 왜 로드됐는지 로그로 남깁니다 — 조건부 규칙과 하위 디렉토리 lazy 로드 디버깅 수단. gap 분석 결과를 확정하기 전, 의심 규칙이 기대 시점에 로드되는지 이 훅으로 확인합니다.
- **`/context`**: 세션의 Memory files 목록에서 규칙 파일 등재 여부를 즉석 확인합니다 (조건부 규칙은 매칭 파일을 읽기 전까지 안 보입니다).

## 5. 다중 언어/프레임워크 레포 전략

### 하위 디렉토리 전략 (기본)

`.claude/rules/`는 모든 `.md` 파일을 **재귀적으로 탐색**하므로, 2개 이상의 언어/프레임워크가 혼용된 레포에서는 하위 디렉토리로 구분하는 것이 기본입니다:

```
.claude/rules/
├── module-boundary.md      # 공통
├── error-handling.md       # 공통
├── go/
│   ├── service.md
│   └── testing.md
└── ts/
    ├── controller.md
    └── testing.md
```

디렉토리는 조직 수단일 뿐 로딩 조건이 아닙니다 — 로딩 조건은 각 파일의 `paths:`가 정합니다 (§2).

### Prefix 전략 (대안)

평평한 구조를 유지하고 싶다면 파일명 prefix(`go-`, `ts-`, `py-`, `rs-`)로 구분합니다. 파일 수가 적을 때만 권장 — 늘어나면 하위 디렉토리로 전환합니다.

### 심볼릭 링크로 공용 룰셋 공유

`.claude/rules/`는 심볼릭 링크를 지원합니다. 여러 레포가 같은 룰셋을 쓴다면 공용 룰셋 저장소를 하나 두고 각 레포의 `.claude/rules/` 안에 링크합니다 — scaffold로 레포마다 생성·복제하는 대신 한 곳에서 유지보수하는 배포 수단입니다.

### 모노레포 로딩 제어

다른 팀·다른 파트의 규칙을 걷어내야 할 때 쓰는 공식 설정 두 가지:

- **`--setting-sources`**: `project`를 빼면 프로젝트 규칙 전체가 로드되지 않습니다 (v2.1.211 이전에는 조건부 로딩 규칙이 제외해도 로드됐으므로 구버전에서는 의존하지 않습니다).
- **`claudeMdExcludes`**: 특정 규칙 디렉토리를 glob으로 제외합니다 — 모노레포에서 자기 파트와 무관한 규칙 디렉토리를 걷어내는 수단.

## 6. paths 범용화 원칙

### 핵심 원칙

paths는 **레이어 구조**(역할)를 표현해야 하며, **위치**(컨테이너 경로)를 표현해서는 안 됩니다.

### 판별 기준

- **레이어**: 파일의 역할을 나타내는 디렉토리 (`core/`, `commands/`, `handlers/`, `service/` 등)
- **위치**: 레이어가 속한 컨테이너 (`plugins/atelier/`, `packages/api/`, `apps/web/` 등)
- paths에는 레이어만 남기고, 위치는 `**/`로 대체합니다.

### 범용화 알고리즘

1. **레이어 식별**: 수집된 경로에서 역할을 나타내는 디렉토리를 구분
2. **컨테이너 추상화**: 레이어 상위의 컨테이너 경로를 `**/`로 대체
3. **교차 검증**: 범용 패턴이 동일 레이어의 파일만 매칭하는지 Glob 테스트 — 매칭 0건이면 좁히기 전에 아래 glob 함정부터 의심
4. **범위 조정**: 의도하지 않은 파일이 포함되면 패턴을 좁히거나 예외 명시

### glob 함정 — 에러 없이 조용히 0건 매칭되는 두 경우

생성·검증 단계에서 잡지 않으면 규칙이 죽은 채 배포됩니다:

- **brace 확장 예산**: 한 규칙의 `paths:` 목록 전체가 확장 패턴 1,000개 / 4 MiB 예산을 공유합니다. 초과하면 패턴이 확장되지 않은 채 사용되고, 리터럴 중괄호는 아무 파일도 매칭하지 않습니다. `{a,b,c}` 항이 많은 패턴은 배열 항목으로 풀어 쓰거나 항 수를 줄입니다.
- **잘못된 `[`**: glob은 `[`를 bracket expression 시작으로 읽습니다. `photos [2024/**`처럼 해석 불가능한 `[`가 있으면 그 패턴은 아무것도 매칭하지 않습니다. 리터럴 `[`는 `photos \[2024/**`로 이스케이프합니다.

### 예시 (원칙 적용)

| 수집된 경로 | 레이어 | 컨테이너 | 범용 패턴 |
|---|---|---|---|
| `plugins/atelier/src/core/git.ts` | `core/` | `plugins/atelier/src/` | `**/core/**/*.ts` |

### 예외 (범용화하지 않는 경우)

의도적으로 범위를 제한해야 하는 paths는 특정 경로를 그대로 사용합니다:

- 자동 생성 코드 (`generated/`, `__generated__/`)
- 마이그레이션 파일 (`migrations/`)
- 루트 설정 파일 (`*.config.ts`, `*.toml`)

### 체크리스트

- [ ] paths가 레이어(역할)를 표현하는가, 위치(컨테이너)를 표현하는가?
- [ ] 컨테이너 경로가 `**/`로 대체되었는가? (예외 제외)
- [ ] 동일 레이어가 복수 위치에 존재할 때 하나의 패턴으로 통합되었는가?
- [ ] Glob 테스트로 의도한 파일만 매칭되는지 확인했는가?
- [ ] brace 확장(`{...}`)이 규칙당 1,000개 / 4 MiB 예산 안인가?
- [ ] 리터럴 `[`를 `\[`로 이스케이프했는가?
- [ ] 의도적 범위 제한이 필요한 경우 예외로 명시했는가?

## 7. 규칙 내용 범용화 원칙

### 핵심 원칙

규칙 본문은 **역할·계약·불변식**을 표현해야 하며, **현재 구현 스냅샷**(실제 코드 조각·실제 식별자·실제 경로)을 표현해서는 안 됩니다.

### 판별 기준

"구현 디테일이 바뀌면 이 문장이 깨지는가?"를 묻습니다. 깨진다면 일반화 대상입니다.

### 예시 수준 규정

- **허용**: 의사코드, 형태 패턴 (예: `findBy<조건>` 형태 표기)
- **금지**: 실제 파일에서 복사한 코드 블록, 실제 클래스명, 실제 경로 인용

### 예외 (구체 표기를 허용하는 경우)

**형식이 곧 계약**인 경우는 구체 표기를 허용합니다. frontmatter 스키마, CLI 출력 포맷 등은 구현 디테일이 아니라 스펙 그 자체이기 때문입니다.

### 체크리스트

- [ ] 규칙 문장이 구현이 아닌 역할·계약·불변식을 표현하는가?
- [ ] "구현이 바뀌면 깨지는 문장"이 남아있지 않은가?
- [ ] 예시가 의사코드·형태 패턴 수준을 넘어 실제 코드를 복붙하지 않았는가?
- [ ] 실제 클래스명·실제 경로가 원칙 설명이 아닌 예시로 등장하지 않는가?
- [ ] 형식 자체가 계약인 예외 항목만 구체 표기를 사용했는가?

## 8. 규칙 스코프 경계 (개인 / 레포 / auto-memory)

레포 안에서의 CLAUDE.md vs `.claude/rules/` 배치 기준은 `value-interview.md` §2가 단일 출처입니다. 이 절은 그 위의 **스코프 축** — 규칙이 누구에게, 어디까지 적용되는가 — 를 다룹니다:

| 자리 | 스코프 | 담는 것 | 관리 주체 |
|---|---|---|---|
| `~/.claude/rules/` | 개인 — 이 머신의 모든 프로젝트 | 개인 작업 습관 중 **모든 프로젝트에 적용되는 규칙** (예: 선호 커밋 스타일) | 사용자 본인 (버전 관리 밖) |
| `.claude/rules/` | 레포 — 이 프로젝트의 모든 세션 | **레포 정책** — 팀이 합의한 컨벤션·아키텍처 규칙 | 팀 (레포에 커밋, 리뷰 대상) |
| auto-memory | 개인 × 프로젝트 | 세션에서 학습된 **개인 취향·상황 맥락** | Claude가 축적 |

내용 성격과 자리가 어긋나면 표에 맞게 승격·강등합니다 — 팀 정책이 개인 스코프에만 있으면 다른 팀원 세션에는 없으므로 `.claude/rules/`로 승격, 개인 취향이 레포 스코프에 있으면 팀 전체에 강제되므로 개인 스코프로 강등. scaffold(자동 생성)의 대상은 항상 레포 스코프 `.claude/rules/`이며, 개인 스코프 파일을 생성·수정하지 않습니다.
