# Advisory Consult (자문 조회)

에스컬레이션 직전에 **상위 역량 tier 모델의 관점만 사오는** 경로다. 집행 위임(코드를 만드는
sub-agent)과 달리 산출물이 권고이고, 결정권은 메인에 100% 남는다. 집행/자문 분리와 tier 예외
원칙 자체는 `SKILL.md §모델 라우팅 전략`이 단일 출처다 — 이 문서는 **언제·어떻게 소집하고 무엇을
주고받는지**를 소유한다.

## 전제 — 두 조건이 모두 충족돼야 사용 가능

자문은 opt-in 경로다. 진입 시 1회 확정된 가용성 판정(`SKILL.md §진입 시 체크`)을 그대로 따른다.

1. **agent team 실험 플래그가 켜져 있을 것** — 자문자는 team member 로만 실행한다.
2. **정책에 `advisor` 역할이 선언돼 있을 것** — 미선언이면 경로 자체가 없다 (`SKILL.md §역할별 모델 정책 설정`).

둘 중 하나라도 빠지면 **자문 경로는 사용 불가**다. 이때 트리거 지점에 도달하면 자문을 건너뛰고
원래 하려던 에스컬레이션(사용자 보고)으로 그대로 진행한다 — 오케스트레이션 전체를 멈추지
않는다. 폴백은 금지다 (§안티패턴 1).

### 왜 team member 전용인가

자문은 본질이 왕복이다 — 권고 → 메인 반문 → 재답변. 단발 subagent 는 매 왕복마다 패킷을
재합성해야 하고 직전 라운드를 기억하지 못한다. 협의체 tie-break 로 투입할 때는 더 분명해서,
생성자·검증자와 **같은 대화 공간**에 있어야 상호 반박이 성립한다. team 의 격리 특성과 spawn
패턴은 `delegation-patterns.md §Agent team 사용 패턴`이 단일 출처다.

## 언제 소집하는가 (트리거 — 단일 출처)

상시 자문은 비용·지연을 늘리고 메인 컨텍스트를 태운다. 자문은 정상 루프의 참여자가 아니라
**에스컬레이션 경로의 한 단계**다. 다음 네 지점에서만 소집한다:

| # | 트리거 | 소집 시점 |
|---|--------|-----------|
| 1 | 협의체 `max_council_rounds` 소진 — pass 못 함 | 에스컬레이션 직전 tie-break (`architect-council.md`) |
| 2 | 게이트 reject → 재위임이 반복되는 루프 감지 | 같은 자리를 맴돌 때 (`autonomous-driving.md §리뷰어·QA 게이트`) |
| 3 | 되돌리기 비용이 큰 결정 | 스키마 마이그레이션·공개 API 변경·토폴로지 변경의 계획 승인 전 |
| 4 | 사용자 명시 요청 | 즉시 |

- 자문 횟수는 계약의 `max_advisory_consults`(기본 2)를 소모한다. 소진 시 자문 없이 에스컬레이션.
- 자문은 **재위임이 아니므로** `max_redispatch_per_task` 를 소모하지 않는다.

## 역할 제한은 계약이지 도구 보장이 아니다 (알고 쓰는 한계)

자문자는 teammate 다. **teammate 는 도구 권한을 제한할 수단이 없다** — 별도 agent 정의를 지정하는 경로(`subagent_type`)는 단발 subagent 의 것이고, team spawn 과 결합하는 선례가 없다. 따라서 자문자는 실제로는 편집도 `SendMessage` 도 가능한 상태이며, 아래 제한은 전부 **프롬프트 계약**이다.

| 금지 | 성격 | 어겼을 때 |
|---|---|---|
| 편집 (`Edit`/`Write`) | 계약 | 토폴로지 가드가 공유 checkout 오염을 탐지 → 복구 + 에스컬레이션 |
| 다른 teammate 에게 지시 (`SendMessage`) | 계약 | 메인이 조율 단일 창구임을 계약에 명시 — 자문자는 메인하고만 대화 |
| 능동적 스코프 확장·재위임 | 계약 | 출력 계약 위반으로 처리, 해당 권고를 기각하고 기록 |

- **자문 소집 전후로 토폴로지 가드를 실행한다** (`merge-coordinator.md §토폴로지 가드`). 사전 차단이 아니라 **사후 탐지**이므로 생략하면 오염을 놓친다.
- 도구 수준 보장이 꼭 필요하면 그것은 team 이 아니라 단발 subagent 의 영역이다 — 왕복 조율(자문의 실질)과 도구 보장은 현재 **동시에 얻을 수 없다**. 이 경로는 왕복을 택했다.
- 계약 위반이 실제로 발생하면 그 자문 결과를 채택하지 않고 decision log 에 남긴다 (권고의 신뢰도 자체가 깨진 것).

## 정책·메커니즘 분리 — 고정하는 것은 계약뿐

협의체와 같은 원리로(`architect-council.md §설계 원칙`) 골격만 고정하고 역할 구성은 런타임에 주입한다.

| | 고정 (메커니즘) | 주입 (정책) |
|---|---|---|
| 무엇 | 위 금지 계약, 출력 계약, 결정권 없음 | 관점, 이름, **자문자 수**, 질문 범위, 모델 |
| 왜 | 이게 흔들리면 자문이 실질 오케스트레이터가 된다 | 어떤 관점이 필요한지는 문제마다 다르다 |

따라서 **자문자는 하나가 아니어도 된다.** 같은 계약을 관점만 바꿔 여러 번 spawn 하면 자문 스웜이 된다 — 성능·보안·마이그레이션 안전성처럼 서로 다른 렌즈를 병렬로 붙이고, 권고가 갈리는 지점 자체를 메인의 판단 재료로 쓴다. 관점 조합·인원은 문제를 보고 메인이 정한다 (기본값 답습 금지 — §안티패턴 8).

## 소집 절차

```
require(flag_on AND policy.advisor.allow_models)   # 없으면 자문 없이 원래 에스컬레이션으로
assert_topology()                                  # 소집 전 기준선 (clean 확인)

perspectives = main_decides_lenses(question)       # 정책 — 문제에 맞춰 1개 이상 (스웜 가능)
for p in perspectives:                             # 같은 계약, 관점만 다름
    Agent({
      name: f"advisor-{p.slug}",                   # team member — 세션 내 유니크
      model: policy.roles.advisor.allow_models[0], # 정책에서 주입 (문서에 모델명 없음)
      run_in_background: true,
      description: "<무엇에 대한 자문인가>",
      prompt: "<자문 패킷 — 관점 p + 금지 계약 명시, 아래 입력 계약>"
    })
advices = await_completion_notifications()         # 병렬 — 서로 기다리지 않음
assert_topology()                                  # 소집 후 — 계약 위반(편집) 탐지
# 필요하면 SendMessage({to: "advisor-<slug>", ...}) 로 반문 — 왕복도 예산을 소모
decision = main_decides(advices)                   # 채택 / 부분채택 / 기각 — 메인의 판단
                                                   # 권고가 갈리면 그 대립 자체를 근거로 기록
log_decision("자문 요청 + 채택 판단", advices, decision)
```

- 자문자 수와 무관하게 **예산은 소집 1회당 `max_advisory_consults` 1을 소모**한다 — 관점을 나눈 것이지 왕복을 늘린 것이 아니다.
- 권고가 서로 충돌하면 메인이 임의로 평균 내지 말고 **대립 지점을 decision log 에 남기고** 판단한다. 갈린다는 사실 자체가 정보다.

## 입력 계약 (자문 패킷)

advisor 는 메인 대화를 보지 못한다. 패킷은 자기완결적이어야 한다.

```
## 자문 요청
- 관점:        이 자문자가 맡을 렌즈 (예: 마이그레이션 안전성) — 스웜이면 자문자마다 다르다
- 배경:        지금 무엇을 하고 있는가 (epic 목표 1~2문장)
- 막힌 지점:   무엇 때문에 자문을 요청하는가 (트리거 번호 포함)
- 질문:        답을 원하는 구체적 질문 (모호한 "봐주세요" 금지)
- 제약:        바꿀 수 없는 조건 (토폴로지·품질 게이트·도메인 규칙)
- 근거 자료:   .orchestrator/<epic>/decisions/... 경로 (전문을 붙여넣지 말 것)
- 기대 출력:   아래 출력 계약
- 금지 계약:   편집하지 말 것 / 다른 teammate 에게 지시하지 말 것 (메인하고만 대화)
               / 재위임하지 말 것 / 관점 밖으로 스코프를 넓히지 말 것
```

**금지 계약은 패킷에서 생략하지 않는다.** teammate 는 도구로 막을 수 없으므로(위 §역할 제한은
계약이지 도구 보장이 아니다) 이 문구가 유일한 사전 장치다.

- **긴 근거는 경로로 넘긴다** — advisor 는 `Read`/`Glob`/`Grep` 을 가지므로 decision log 와
  코드베이스를 직접 읽는다. 메인이 전문을 패킷에 복사하면 메인 컨텍스트가 포화된다
  (`autonomous-driving.md §메인 컨텍스트 격리`).
- 질문이 여러 개면 우선순위를 매겨 넘긴다 — advisor 가 스스로 스코프를 넓히지 않도록.

## 출력 계약

```markdown
## 자문 결과
### 요약
[한 문장]

### 권고
1. [권고] — 근거: [왜] / severity: critical | important | optional
   - 대안: [택하지 않은 선택지와 이유]

### 질문 자체에 대한 지적 (있을 때만)
[질문의 전제가 틀렸다고 보면 여기에 — 행동은 메인이 정한다]

### 확신도
[높음/보통/낮음 + 판단을 흔드는 미확인 사실]
```

- **권고와 근거만**이다. 명령형 지시(`~하라`), `pass`/`reject` 판정, 다른 agent 에 대한 작업
  지시는 출력에 넣지 않는다.
- 확신도가 낮으면 낮다고 쓴다 — 상위 tier 라도 틀릴 수 있고, 메인이 가중치를 정해야 한다.

## 메인의 처리 의무

자문을 받은 뒤 메인이 반드시 하는 것:

- **채택 / 부분채택 / 기각 + 사유**를 decision log 에 남긴다. **기각도 정당한 결과다** — 상위
  tier 라는 이유로 자동 채택하면 메인이 고무도장이 된다 (§안티패턴 2).
- **severity: critical 은 에스컬레이션 트리거로 승격**한다. advisor 는 게이트가 아니라 자동
  머지를 막을 수 없으므로, 중대 지적은 사람에게 올려 판단받는다.
- 채택한 권고를 실행할 때는 **평소대로 집행 위임**한다 — advisor 는 편집 권한이 없고, 메인도
  편집하지 않는다 (`SKILL.md §사고 모드`).

## 수명

- 자문 세션 단위로 spawn 한다. 협의체 tie-break 이면 협의체 팀과 함께 끝난다.
- team 은 session 종료 시 자동 정리되므로 별도 정리 단계가 없다.
- 자문이 끝나면 메인은 **권고 요약 + 채택 판단만** 컨텍스트에 유지하고, 전문은 decision log 에 둔다.

## 안티패턴

1. **플래그 꺼진 상태에서 자문 흉내**: 단발 subagent 1회 왕복으로 대체하거나, 메인이 스스로 상위
   tier 관점을 흉내 내 "자문 결과"로 보고 → 실질 없이 기록만 남는다. 경로는 비활성이고, 그
   시점의 판단은 **메인 자신의 판단으로 명시**해 기록한다.
2. **고무도장 메인**: 권고를 검토 없이 그대로 채택 → 실질 오케스트레이터가 advisor 가 되고 메인은
   전달자로 전락한다. 채택도 기각도 사유와 함께 기록한다.
3. **advisor 에게 결정권 부여**: 자문 결과를 게이트 승급 조건에 넣거나 pass/reject 를 받게 함 →
   게이트 AND 조건이 오염되고 자문이 검증 없는 우회로가 된다.
4. **상시 자문**: 트리거 없이 매 판단마다 소집 → 비용·지연 폭증, 메인 컨텍스트 포화. 트리거 4개와
   `max_advisory_consults` 를 지킨다.
5. **패킷에 전문 복사**: 설계 전문·전체 diff 를 패킷에 붙여넣음 → 메인 컨텍스트 포화. 경로를 넘겨
   advisor 가 직접 읽게 한다.
6. **모호한 질문**: "전체적으로 봐주세요" → 스코프가 advisor 손에 넘어가고 답도 뭉툭해진다. 답을
   원하는 구체적 질문을 넘긴다.
7. **정책 미선언인데 임의 모델로 소집**: 문서나 메인 판단으로 모델명을 골라 자문 → 정책 우회.
   `advisor` 미선언은 "경로 없음"이지 "아무 모델이나"가 아니다.
8. **도구가 막아줄 거라 가정**: teammate 라서 편집도 `SendMessage` 도 실제로는 가능한데, 패킷에서
   금지 계약을 빼거나 소집 전후 토폴로지 가드를 생략 → 사전 장치도 사후 탐지도 없는 상태가 된다.
   "정의 파일로 도구를 제한했다"는 문장을 문서에 쓰는 것도 같은 실패다 — 없는 보장을 기록하면
   다음 사람이 그것을 믿고 가드를 생략한다.
9. **관점을 고정으로 답습**: 어떤 문제든 자문자 1명·같은 렌즈로 소집 → 정의 파일이 권한 shell 이
   아니라 페르소나로 굳는다. 관점·인원은 정책이므로 문제를 보고 정한다 (§정책·메커니즘 분리).
   반대로 관점을 잘게 쪼개 무의미하게 늘리는 것도 비용만 늘린다 — 판단이 갈릴 축으로만 나눈다.
