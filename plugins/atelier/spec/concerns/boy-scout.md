# 보이스카웃 원칙

> atelier로 한 작업은 손댄 파일을 프로젝트 규칙에 맞는 상태로 남겨요. 손대지 않은 파일은 바꾸지 않아요.

## 역할

규칙이 생기기 전에 쓰인 코드 위에 기능을 더할 때, 에이전트가 기존 패턴을 그대로 따라 해서 규칙 위반이 늘어나는 것을 막아요.

## 정책

1. **우선순위** — 프로젝트 규칙(CLAUDE.md·`.claude/rules/`)이 기존 코드 패턴보다 우선해요. 기존 패턴은 규칙이 말하지 않는 영역에서만 따라요.
2. **범위** — 이번 작업이 편집하는 파일 전체가 정리 대상이에요.
3. **범위 밖** — 아래는 정리하지 않고 보고만 해요.
   - 공개 계약(다른 파일이 쓰는 시그니처·export·CLI 출력·스키마)을 바꿔야 하는 정리
   - 편집하는 파일 밖으로 번지는 정리
   - 동작을 바꾸는 정리
4. **동작 고정 테스트** — 정리할 파일의 현재 동작을 고정하는 테스트 추가는 범위 안이에요.
5. **순서** — 정리는 기능 변경보다 먼저, 동작을 보존하는 변경으로 따로 커밋해요. 흐름은 선행 정리 → 기능 → 마무리 정리예요.
6. **프로젝트 규칙 우선** — 프로젝트 규칙이 정리 범위를 명시적으로 좁히면 그 규칙을 따라요.
7. **YAGNI와 구분** — 편집 파일의 정리는 설계 단계에서 계획하는 작업이에요. YAGNI는 요구되지 않은 새 일반화를 막는 원칙이라 이 정리와 충돌하지 않아요.

## 적용 지점

| 지점 | 동작 |
|---|---|
| 작업 원칙 (모든 세션) | atelier가 주입하는 작업 원칙에 위 정책이 들어 있어요. 위임받은 agent도 같은 원칙을 받아요 |
| 설계 생성 (grill) | 편집 대상 파일의 규칙 위반을 설계에 정리 항목으로 넣어요 |
| 분해 (orchestrator) | 편집 대상 파일마다 규칙 위반을 조사하고, 있으면 선행 정리 task를 만들어요. 한 파일에 정리 task는 하나이고, 그 파일을 편집하는 모든 task보다 먼저 순차로 실행해요 |
| 검토 게이트 | 규칙 준수 관점이 편집한 파일 전체를 대조해요. 범위 밖으로 보고한 항목을 뺀 나머지 위반은 reject해요. reviewer의 "초과 구현" 판정은 선행 정리 task와 범위 안 정리를 제외해요 |
| 선행 정리 task의 게이트 | 기존 테스트 green + 공개 계약 변화 없음 |
| 종료 보고 | 범위 밖 위반을 핸드오프 항목으로 남겨요 |

## 실패 처리

- 정리 task가 동작을 바꿈(테스트 red) → 정리 task를 reject하고 재위임해요. 그 파일의 기능 task는 시작하지 않아요.
- 동작 고정 테스트를 쓸 수 없음(테스트 하네스 없음) → 그 파일 정리는 범위 밖으로 보고하고, 기능 task는 진행해요.

## 제약 조건

- 경량 경로(tracked 편집이 없는 런)에는 적용하지 않아요.
- 편집하지 않는 파일은 규칙 위반이 있어도 바꾸지 않아요.
