# 11 — orchestrator 축소 설계 (L2)

> **Plan — 이 시점의 결정 기록.** 현재 정책의 신뢰 소스가 아니다. 축소가 실행되면 "지금 어떻게 동작해야 하는가"는 `plugins/atelier/skills/orchestrator/` 의 문서와 `.claude/rules/` 가 갖는다.
> 입력: 분류 조사(85개 항목 · L1) · `plans/atelier/09-orchestrator-graph-restructure.md`(그래프 구조 설계) · `plans/atelier/09d-orchestrator-external-contracts.md`(외부 계약 표면) · `plans/atelier/10-orchestrator-rationale-archive.md`(사고 기원 A01~A49).
> 범위: `plugins/atelier/skills/orchestrator/` 전체 + 외부 참조 7곳 + `.claude/rules/decision-graph.md` + `scripts/check-decision-graph.sh`. **승인 전이며 구현은 별도 라운드다.**

## 1. 배경과 목표
### 1.1 이전 구조가 실측에서 보인 것
plan 09 의 결정 그래프 구조(항목 85개 · 파일 11개 · 2,388줄)를 블라인드 실런(T18 계열)으로 재면서 나온 사실 셋 — 비용(로드 줄수)은 그래프가 부담하는데 이득(정지·불변식의 강제)은 그래프 형식이 아니라 **내용**에서 나왔다.

- **무거운 경로 한 런이 문서 2,200줄대를 로드한다.** 필수 로드 3파일 + 결정 라우팅이 지목하는 파일이 연쇄로 열리고, 항목 간 참조가 그 연쇄를 끊어 주지 못한다.
- **판단 대본이 hard stop 을 한 번도 만들지 않았다.** 세 시나리오 모두에서 그래프의 판정 노드는 모델이 이미 내렸을 결론을 다시 밟았고, 정작 런을 멈춰 세워야 할 상황은 그래프 밖에서 왔다.
- **같은 판정이 사본으로 흩어져 모순이 남는다.** 시나리오별 모순 관측치 7 / 5 / 6.

### 1.2 사용자 결정 (그대로 인용)
- 자율주행 규칙은 "처음 계획과 다르게 치명적 결함이 발견되어 HITL 이 필요한 상황, 외부 환경 이슈로 모든 요청이 실패하는 상황" 같은 **정지 조건 중심**이어야 한다.
- tier · team 등급 · 병렬/순차는 **표**로. fan-out 복원력은 불필요.
- "테이블 형태면 사람이 읽어도 가독성이 좋고 불필요한 텍스트가 없어 토큰 효율적".

### 1.3 원칙
**판단은 모델에, 규칙은 문서에.** 문서가 소유하는 것은 넷뿐이고, 그 밖의 분기(위험도 · 원인→액션 · 축 분해 · 가설 랭킹 · 취합 위생)는 모델 판단으로 되돌린다 — 판단을 대본으로 적어 둔 것이 이전 구조의 비용 대부분이었다.

| 문서가 소유 | 이유 |
|---|---|
| 불변식 | 위반하면 조용히 오염되고 사후에 되돌리기 어렵다 |
| 정지 조건 | 자율 런이 스스로 멈춰야 하는 지점은 모델이 낙관적으로 판단한다 |
| 환경 계약 | 런타임 사실 · 이 repo 고유 규약이라 추론으로 복원되지 않는다 |
| 기본값 | 매번 판단하면 편차가 생기고, 표로 두면 예외만 판단하면 된다 |

## 4. 불변식 표 (20행)
형식: **금지 → 대신**. 한 행 = 한 줄. 금지만 있고 출구가 없는 행은 두지 않는다(재발을 부른다).
| # | 금지 | 대신 |
|---|---|---|
| 1 | 메인이 tracked 파일을 직접 편집 | 위임한다. 예외는 통합 검증·머지·복구·정리 명령과 repo 밖 기록뿐 |
| 2 | 원문·전체 diff·리뷰 전문을 메인 컨텍스트로 반입 | 작업 id·변경 파일 목록·verdict·기록 경로만 받는다 |
| 3 | 메인이 worktree 또는 다른 브랜치로 진입 | worktree 경로를 지정해 읽거나 read-only 로 위임한다 |
| 4 | 저장소 안 tracked 편집을 격리 없이 위임 | 언제나 worktree 격리. 공유 checkout 을 쓰는 teammate 가 편집하면 격리 subagent 로 형태 전환 |
| 5 | 편집 도구의 파일 경로에 부모 repo 절대경로 | worktree 절대경로만 — 어긋나면 worktree 경로로 재지정 |
| 6 | 격리 위임을 한 메시지에 여러 건 싣거나 생성 확인 전에 다음 건을 싣는 것, 가드 명령을 worktree 안에서 실행 | 한 건씩 싣고 worktree 목록에 등장했는지 확인한 뒤 진행. 가드 세 명령은 메인 working tree 에서 |
| 7 | 브랜치·tree 가 어긋난 채로 진행 | 복구 절차를 먼저 돌리고(변경은 보존한다) 그다음 정지·보고 |
| 8 | 머지 직후 가드 생략 | 매 머지 직후 넷을 확인 — 브랜치가 epic 이고 tree clean · HEAD 가 방금 통합한 후보의 tip · author 방침 판정을 거침 · in-flight worktree 가 epic 최신 HEAD 기준 |
| 9 | epic 브랜치를 rebase, 또는 작업 브랜치를 그냥 merge | 통합은 rebase 후 fast-forward 전용 머지로 고정. 역방향 drift 흡수도 merge 로 하고 흡수 패킷에 "이것은 merge 다"를 명시 |
| 10 | 메인이 충돌을 직접 편집, task 를 갈아치워 충돌 카운터를 리셋 | 전담 위임(해결 전략의 단일 출처는 `git` skill 의 충돌 해결 문서). 카운터는 파일 기준으로 누적 |
| 11 | 개별 worktree·중간 브랜치의 green 으로 완료 선언, red 를 메인이 직접 고쳐 green | epic 최종 HEAD 의 전체 스위트 green + 그 HEAD sha 명시. 회귀 원인은 수정 위임 |
| 12 | 계획 밖 tracked 편집을 선-dispatch 후-체크 | 편집 dispatch 전에 토폴로지·격리를 late gate 로 먼저 세우고 전환 사유를 기록 |
| 13 | 빈 자리를 silent fallback 으로 메움 | inert 구현 또는 미구현 예외로 드러내고, 미결 seam 을 결정 기록과 종료 보고에 깃발로 남긴다 |
| 14 | 증거 없는 claim 을 취합, 같은 전략 반복을 교차 검증으로 인정 | 모든 claim 에 실행 명령 원문과 `file:line`, 없으면 `NOT FOUND — searched with <명령>`. 부재 주장은 축을 바꾼 둘 이상의 전략으로 |
| 15 | 한 차원만 pass 인데 승급, 구현 agent 가 게이트를 겸임 | 세운 모든 차원이 pass 여야 승급. 차원마다 다른 agent 를 병렬로. reject 는 `요구사항·spec 위치 ↔ 파일:라인` 을 지목한 findings 를 실어 재위임 |
| 16 | 승인 이벤트 없이 implementer dispatch, 마커만 만드는 자기 승인 | 협의체 pass·심문 합의·사용자 승인 중 하나를 만들거나, 자명한 작업이면 면제 판정을 근거와 함께 기록 |
| 17 | 자기 설계를 자기가 심문, 검증 pass 전 dispatch | 검증자와 생성자를 다른 agent 로. 두 자세를 모두 거친 뒤 dispatch |
| 18 | 자문 권고를 게이트로 사용, 갈린 권고를 평균 | 결정권은 메인에 100% — `critical` 은 에스컬레이션 트리거로 승격, 대립 지점을 기록하고 메인이 고른 뒤 채택·부분채택·기각을 사유와 함께 남긴다 |
| 19 | 편집 목적 dispatch 의 성공을 보고만으로 수령, 격리 worktree 재사용 | diff 또는 커밋 해시 실존으로 실제 변경 확인(변경 0건은 성공이 아니라 prompt 결함). 재위임은 언제나 새 격리 dispatch |
| 20 | 완료 대기에 sleep·폴링 루프, 메인의 체감을 완료 판정 입력으로 사용 | 도착하는 완료 알림으로 진행. 완료 판정 입력은 명령 결과와 산출물 수용뿐 |

| 2 | 계획 밖 tracked 편집 | 경량으로 판정한 런에서 계획에 없던 tracked 편집이 필요해짐 | 편집 dispatch 를 시작하지 않는다 | 토폴로지·격리를 late gate 로 세운 뒤 무거운 경로로 전환(역방향 없음) |
| 3 | 토폴로지 위반 | 메인의 브랜치가 확보한 epic 과 다름 / tree dirty / dispatch 직후 worktree 미등장 / HEAD 가 통합 후보 tip 과 다름 | 복구 후 정지. 후속 dispatch 중단 | 복구 성공 + 발생 지점을 붙여 보고 → 사용자 결정 |
| 4 | 되돌리기 어렵거나 epic 경계 밖 행위 | 강제 push · 기본 브랜치 머지 · 배포 · 외부 서비스 호출 · 데이터 삭제 / 의도가 갈리는 충돌 / 도메인 의미 결정 / 계획 승인 불가 / authorship 방침을 지금 처리로 지킬 수 없음 | 즉시 정지·보고 — 예산이 남아 있어도. 자문 권고가 멈추는 판단을 대체하지 않는다 | 사용자 승인 또는 결정. 부분 머지 상태를 함께 보고 |
| 5 | 통합 검증 실패 | 계약이 지정한 시점의 검증이 red / 최종 HEAD 전체 스위트 red | 머지 전 시점이면 그 머지를, 머지 후 시점이면 후속 루프를 중단. 완료 선언 금지 | 원인 파악 → 수정 위임 → 최종 HEAD 재실행, HEAD sha 와 함께 보고 |
| 6 | 예산 소진 / 무진전 | 루프·시간·턴 상한 도달 / 연속 무진전이 한도 도달(진전 = 머지된 브랜치 수·통과 테스트 수·종료 조건 충족 항목 수) / 재위임 예산 소진 | 예산 소진 종료 — 진전 없는 재분해 반복 금지 | 사용자가 예산을 올리거나 범위를 좁힌다. 진전 측정값과 남은 작업 제출 |
| 7 | 협의체 라운드 소진 | 라운드 예산 소진 후에도 심문 verdict 가 pass 아님 / verdict 에 도메인 의미 결정 포함 | 검증되지 않은 분해로 dispatch 하지 않는다 — 예산 소진은 통과가 아니라 정지다 | 사용자 결정 또는 tie-break 자문 1회 후 그 결과를 근거로 보고 |
| 8 | 공유 전제 실패 (외부 환경) | 위임·머지 경로가 실제로 거치는 공유 의존(CLI 인증·필수 외부 서비스 도달)의 read-only 확인 실패 | dispatch 를 시작하지 않고 즉시 보고. 부분 dispatch 로 밀어붙이지 않는다 | 무엇을 확인하다 실패했는지 + 해제 방법을 함께 내고, 전제 복구 후 재진입 |
| 9 | 같은 원인으로 연속 실패 (외부 환경) | 여러 dispatch 가 동일 외부 원인(gateway 오류·API 오류·rate limit)으로 반복 실패 | 루프를 멈춘다. 추정으로 prompt 를 고쳐 다시 던지지 않는다 | 환경 복구 확인 후 재개, 또는 사용자가 다른 경로를 지시 |
| 10 | 계획과 다른 치명적 결함 → HITL 전환 | 자율 런 중 spec·설계의 전제를 무너뜨리는 결함 발견(도메인 의미 오염 · 데이터 손상 위험 · 아키텍처 전제 붕괴) | 자율을 중단하고 HITL 로 전환. 남은 계획을 자율 재량으로 재설계하지 않는다 | 결함·영향 범위·산출물 상태·선택지를 한 번에 보고 → 사용자가 계획 갱신·재개 승인 |

**공통**: 정지 보고는 `현재 상태 + 남은 작업 + 막힌 지점 + 선택지` 를 한 번에 담고, 종료로 이어지면 3분류 판정과 핸드오프를 남긴다.

## 6. 기본값 표 6개
문장 없이 행만. 값 열의 수치는 전부 예산 값 표가 소유하고 여기에는 이름만 둔다.
### 표 1 — 집행 tier
| 작업 유형 | 시작 tier |
|---|---|
| 요구사항 분해 · 설계 심문 · 복잡한 설계 · 어려운 디버깅 · 아키텍처 판단 | 최상위 |
| 일반 구현 · 코드 리뷰 · 테스트 작성 | 중간 |
| 문서 작성 · 보고서 정리 (산출물이 문서 자체) | 중간 |
| 리서치 · 조사 — 코드베이스 파악 · 영향 범위 수집 · 자료 조사 | 경량 (판단이 섞이면 중간, 최상위로 올리지 않는다) |
| 단순 분류 · 포맷 변환 · 짧은 추출 | 경량 |
| 자문 소집 | 메인보다 상위 — 집행 위임 tier 상한의 유일한 예외 |

> 모델은 매 dispatch 명시(상속 금지) · 문서에는 모델명이 아니라 역량 수준 · 집행 위임은 자문의 여집합

### 표 2 — team 등급
| 경로 | 등급 | 비가용이면 |
|---|---|---|
| 아키텍트 협의체 | 필수 | 폴백 금지 — 즉시 에스컬레이션 (정지 #7) |
| 자문 소집 | 필수 | 자문을 생략하고 원래 하려던 에스컬레이션으로. 흉내 금지 |
| spec-driven 리뷰 게이트 (검토자·QA 2차원) | 선호 | 단발 subagent 2개 폴백 — 두 차원은 유지 |
| 그 밖의 왕복 위임 | 선호 | 단발 폴백 허용 |

> 필수 등급에는 가드 둘이 붙는다 — 첫 spawn 후 왕복 확인 1회 · 기록의 `실행 형태`·`판정 근거` 필드

### 표 3 — 병렬 · 순차
| 상황 | 판정 |
|---|---|
| 변경 파일 집합이 disjoint 이고 작업 간 의존성 없음 | 병렬 |
| 작업 간 의존성 있음 | 순차 |
| overlap 이 전부 hot-spot (의도는 안 겹치는데 같은 라인 근처에 항목 추가) | 병렬 유지 + 통합 task 1개를 순차로 분리 |
| overlap 이 내용 충돌 | 순차 |
| read-only 조사 (충돌 축에 걸리는 것이 없음) | 병렬 기본 — 관점이 하나뿐이라는 근거가 없으면 3관점 이상 |
| 1턴에 닫히는 단발 조회 | fan-out 하지 않는다 — 메인이 그 자리에서 답한다 |
| 경량 경로 | 충돌 축이 파일 집합이 아니라 외부 리소스 · rate limit |
| 격리 불가 (편집 대상이 repo 밖) | 순차로 낮추고 보고 |

> 겹치는 파일 집합은 메인이 epic 브랜치에서 직접 만든다. 병렬의 이득은 시간이고 비용은 사람이 푸는 머지 충돌이라 손해가 비대칭 — 의심스러우면 순차

### 표 4 — 위임 형태
| 신호 | 형태 |
|---|---|
| 결과가 단일이고 단발 | 단발 subagent — 병렬 fan-out 도 단발 여러 개다 |
| 진행 중 개입 · 라운드 누적이 필요 | agent team — 지목자를 보관하고 배경으로 띄운다 |
| team 인데 파일 편집이 필요 | 편집만 격리 subagent 에 한 단계 위임 |

> 위임 계층은 오케스트레이터 → 작업 agent 한 단계. 예외는 위 3행뿐이며 prompt 의 재위임 금지 항목이 이를 강제한다

### 표 5 — 격리 여부
| 위임 성격 | 격리 | prompt 에 싣는 것 |
|---|---|---|
| 파일 수정 · 대상이 저장소 안 | worktree 격리, 작업 브랜치 규약 적용 | base epic 이름 · 격리 준수 · base 확인 + 규약 브랜치 생성 |
| 읽기 전용 분석 | 격리 없음 — 현재 브랜치에서 위임 | 산출 경로 계약 |
| 공유 checkout 을 쓰는 teammate 가 편집 | 격리되지 않는다 — 격리 subagent 로 형태 전환 후 재판정 | — |
| 수정 대상이 저장소 밖 | 격리 불가 — 보고하고 fan-out 을 순차로 | — |
| 경량 경로 (계획된 tracked 변경 없음) | 격리 없음 · 토폴로지 가드 · 충돌 사전 분석 · 머지 조정 생략 | 산출 경로 계약 — 파일이 꼭 필요하면 repo 밖 scratchpad 로 한정 |

### 표 6 — 검토 게이트
| 산출물 · 경로 | 게이트 | 검증 기준선 |
|---|---|---|
| 무거운 경로 · tracked 편집 | 산출물 성격에 맞는 관점별 게이트를 세운다. 각 관점은 작성 agent 와 다른 agent 가 맡고, 세운 전부가 pass 여야 승급 | spec 있고 미결 0 → spec / 없음 → 요구사항·flow·엣지케이스 |
| 문서 · 설정 (테스트 대상 아님) | 요구사항↔산출물 관점 1개 이상 (테스트 관점 생략, 사유 기록) | 요구사항 |
| 경량 · 되돌리기 비용 있는 외부 쓰기 | 쓰기 전 검토 1회 | 요구사항 |
| 경량 · 그 밖 | 비발동 (생략 판정 기록) | — |

> 관점 예시 — reviewer(요구사항↔구현·회귀·설계 원칙) · qa(요구사항↔검증 테스트·빈 assert) · dba(DB 접촉 시 스키마·마이그레이션 안전성) · 그 밖에 보안·성능·접근성·API 호환성 등 작업 성격이 요구하는 관점. 어떤 관점을 세울지는 메인이 분해 시점에 정해 기록한다.

### 표 7 — 모드 · 등록 · 경로 (보조 — 진입 1회 확정)
| 축 | 판정 |
|---|---|
| 단계별 확인 명시 / 종료 조건 판정 가능 / 판정 불가 | HITL / 자율(기본값) / 진입 보류 — 합의 전까지 HITL 규칙 |
| 산출물(tracked 변경·문서·외부 시스템 쓰기) 있음 / read-only 조사·분석 | Task 등록 / 미등록 |
| 계획된 산출물에 tracked 변경 있음 / 없음 / repo 밖 편집 | 무거운 경로 / 경량 경로 / 격리 불가·순차로 낮춤·보고 |

## 부록 A — `SKILL.md` 초안 전문
> frontmatter 의 `name` · `description` · `version` 은 현행 그대로 둔다 — 트리거 키워드 60여 개를 `description` 이 이미 소유하므로 본문에 트리거 절을 다시 두지 않는다. 아래는 frontmatter 이후 본문이다.

````markdown
# Orchestrator Skill
여러 단위로 벌어지는 일을 분해 · 위임 · 통합한다. **적용 범위는 작업의 종류가 아니라 규모로 갈리고, 사용자가 명시한 위임 요구가 규모 판정보다 앞선다** — 구현이냐 문서냐 조사냐로 가르면 read-only 리서치가 부당하게 빠진다. 판단은 모델이 한다 — 이 문서가 소유하는 것은 넷뿐이다: 불변식 · 정지 조건 · 환경 계약 · 기본값.

## 불변식
위반하면 조용히 오염되고 사후에 되돌리기 어려운 것들. 한 행 = 금지 → 대신.
| # | 금지 | 대신 |
|---|---|---|
| 1 | 메인이 tracked 파일을 직접 편집 | 위임한다. 예외는 통합 검증·머지·복구·정리 명령과 repo 밖 기록뿐 |
| 2 | 원문·전체 diff·리뷰 전문을 메인 컨텍스트로 반입 | 작업 id·변경 파일 목록·verdict·기록 경로만 받는다 |
| … | (§4 의 20행 전체가 여기에 들어간다) | |

## 정지 조건
신호가 관측되면 예산이 남아 있어도 멈춘다. 정지 보고는 `현재 상태 + 남은 작업 + 막힌 지점 + 선택지` 를 한 번에 담고, 종료로 이어지면 3분류 판정과 핸드오프를 남긴다.
| # | 조건 | 신호 | 행동 | 출구 |
|---|---|---|---|---|
| 1 | **spec 확정 게이트** | 미결 섹션에 `없음` 아닌 항목 / 본문의 미확정 표지가 기각되지 않음 | hard stop — 계약도 세우지 않는다 | 심문 → spec 반영 → 재판정 후 재진입 |
| … | (§5 의 10행 전체가 여기에 들어간다) | | | |

## 표준 절차
```
0. 진입      도구 스키마 확보 → 경로 · 모드 판정 → epic 브랜치 확보 → preflight
1. 분해      복잡 · 모호하면 아키텍트 협의체, 미결 0 확정 spec 이면 메인이 직접
2. 계획      병렬 · 순차, 위임 형태, 격리 여부, 리뷰 차원을 기본값 표로 정한다
3. 위임      한 건씩 — 격리 dispatch 는 생성 확인 전에 다음 건을 싣지 않는다
4. 모니터    기대 완료 시간을 정해 두고 도착하는 완료 알림으로 진행한다
5. 게이트    세운 모든 차원이 pass 여야 승급, 차원마다 다른 agent
6. 머지      한 후보씩 rebase 후 fast-forward 전용 머지, 매 머지 직후 가드
7. 최종      epic 최종 HEAD 전체 스위트 green + HEAD sha 명시
8. 보고      종료 사유 · 3분류 건수 · 핸드오프 · 머지 결과 · 결정 요약
```

경로 · 모드에 따른 단계의 유지 · 생략은 기본값 표가 정한다.

## 기본값
매번 판단하지 않고 표에서 읽는다. 표를 벗어난다고 판단한 경우에만 근거를 기록한다. 표는 전부 `references/contracts.md §기본값 표` 에 있다.
| 무엇을 정하는가 | 표 |
|---|---|
| 어느 tier 로 dispatch 하는가 · 자문을 부르는가 | 표 1 집행 tier |
| 왕복 조율이 필수인가 선호인가 / 병렬인가 순차인가 | 표 2 team 등급 / 표 3 |
| 단발인가 team 인가 / worktree 로 격리하는가 | 표 4 위임 형태 / 표 5 |
| 게이트를 몇 차원으로 세우는가 | 표 6 검토 게이트 |
| 자율인가 HITL 인가 · Task 로 등록하는가 · 무거운 경로인가 | 표 7 |

## 계약과 절차
````
