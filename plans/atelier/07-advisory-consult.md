# Orchestrator — 상위 tier 자문 경로 (Advisory Consult)

> **상태**: 설계 (구현 반영됨)
> **계기**: 메인 오케스트레이터보다 강한 모델을 "어드바이저"로 활용하고 싶다는 요청
> **선행**: `orchestrator/SKILL.md §모델 라우팅 전략`, `references/architect-council.md`

메인 오케스트레이터가 **자신보다 상위 역량 모델에게 의견을 구하되, 결정권과 편집권은 메인에
남기는** 경로를 정의한다. 기존 위임 체계를 바꾸지 않고 에스컬레이션 직전에 한 단계를 얹는다.

---

## 1. 요구사항

| ID | 요구사항 |
|---|---|
| FR-1 | 메인이 자신보다 상위 역량 tier 모델에게 자문을 요청할 수 있다 |
| FR-2 | 자문 에이전트는 **결정하지 않는다** — 권고와 근거만 반환하고 pass/reject 권한이 없다 |
| FR-3 | 자문 에이전트는 **반드시 team member 로 실행**한다 (단발 subagent 폴백 금지) |
| FR-4 | 자문 에이전트는 편집·조율·재위임을 할 수 없다 — 역할을 도구 권한으로 강제한다 |
| FR-5 | `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 가 꺼져 있으면 자문 경로를 **사용 불가**로 만든다 |
| FR-6 | 자문에 쓸 모델은 문서가 아니라 `orchestrator-policy.yaml` 의 `advisor` 역할로 선언한다 |
| NFR-1 | 자문은 상시 경로가 아니다 — 트리거를 좁혀 비용·지연·메인 컨텍스트 소모를 억제한다 |
| NFR-2 | 자문 채택 여부가 사후 검토 가능해야 한다 (decision log) |

## 2. 사이드이펙트 조사

### 2.1 역할 기준 원칙과의 충돌 (SKILL.md §모델 라우팅 전략)

> 오케스트레이터(메인)는 위임되는 어떤 sub-agent보다 낮은 역량 tier로 내려가지 않는다.

문구 그대로면 상위 tier 자문은 금지다. 그러나 이 원칙의 근거는 "메인의 판단이 스웜 결과의
**상한**을 결정한다"이고, 자문은 그 상한을 **올리는** 방향이므로 근거와 모순되지 않는다.
원인은 "위임"이 **집행**과 **자문**을 뭉뚱그린 데 있다 → 개념 분리로 해소한다 (§3.1).

### 2.2 team 은 공유 checkout — 격리가 없다 (delegation-patterns.md §Agent team 사용 패턴)

teammate 는 per-teammate worktree 격리가 없다. 자문자를 팀원으로 앉히는 순간 그 agent 는
**메인 epic 브랜치를 직접 편집할 수 있는 상태**가 된다. 프롬프트로만 금지하면 같은 문서가
경고하는 "격리가 도구 보장에서 프롬프트 희망으로 격하"에 정확히 해당한다
→ tools 화이트리스트로 강제한다 (§3.2).

### 2.3 실험 플래그 의존 — 협의체와 반응이 달라야 한다

`architect-council.md` 메커니즘 5 는 플래그 부재 시 **즉시 에스컬레이션(hard stop)** 이다.
검증 없는 분해가 스웜 전체를 잘못 밀기 때문이다. 자문은 **필수 통과 조건이 아니라 에스컬레이션
직전 보강**이므로 같은 반응을 쓰면 없던 차단이 생긴다 → 자문은 **비활성**(경로만 차단),
협의체는 종전대로 hard stop (§3.3).

### 2.4 위임 깊이 제한 (flat delegation)

자문은 `메인 → advisor` 1단계라 상한을 넘지 않는다. 또한 advisor 의 tools 에 `Agent` 가 없어
**재위임이 구조적으로 불가능**하므로 "작업 agent 는 재위임하지 않는다" 규칙이 자동으로 지켜진다.

### 2.5 게이트·예산에 미치는 영향

- 검토·QA·DBA 의 **AND 게이트 조건은 불변**이다. advisor 는 게이트가 아니므로 승급 조건에
  들어가지 않는다 (FR-2).
- 자문은 `max_redispatch_per_task` 를 소모하지 않는다 — 재위임이 아니기 때문. 대신 자체 상한
  (`max_advisory_consults`)을 계약에 둬 왕복 폭주를 막는다.

### 2.6 정책 파일 스키마 확장

`orchestrator-policy.yaml` 에 `advisor` 역할이 추가된다. 기존 역할(reviewer/qa/…)의
exclude/allow 해석은 그대로고, `advisor` 만 "**미선언 = 경로 비활성**"이라는 반대 기본값을
갖는다 (다른 역할은 미선언 시 기본 heuristic 사용). 이 비대칭은 자문이 opt-in 기능이기 때문이다.

### 2.7 레이어 의존 방향 (Command → Agent → Skill)

`tools/validate` 의 아키텍처 검사는 **skill 이 agent 경로를 참조하는 것**을 오류로 잡는다
(역방향 의존). 따라서 skill 문서에서는 자문 에이전트를 **파일 경로가 아니라 `agentType` 이름
(`advisor`)으로만** 지칭한다. "이 정의가 오케스트레이터 자문 경로에서 쓰인다"는 포인터는
반대 방향(agent → skill)이라 허용되므로 **agent 정의 파일의 description 에 둔다**.

### 2.8 보고·기록

자율 계약 보고에 자문 가용 여부가 추가되고, decision log 기록 시점에 "자문 요청/채택 판단"이
추가된다. 정책에 `advisor` 가 선언됐는데 플래그가 꺼져 있으면 **진입 보고에 1회 명시**한다
(조용히 끄면 사용자가 기대와 어긋난 이유를 알 수 없다).

## 3. 설계

### 3.1 위임의 두 종류

| | 집행 위임 (executive) | 자문 조회 (advisory) |
|---|---|---|
| 산출물 | 코드·문서 (편집) | 권고 + 근거 (read-only) |
| 결정권 | 메인이 머지 판단 | **메인에 100% 잔류** — pass/reject 없음 |
| tier 규칙 | 메인 ≥ sub-agent (기존 원칙) | 메인 < advisor **허용** (유일한 예외) |
| 실행 형태 | isolated subagent | **team member 전용** |

기존 역할 기준 원칙은 "**집행** 위임에 한한다"로 좁혀지고, 자문이 명시적 예외가 된다.

### 3.2 역할 제한을 도구 권한으로 강제

advisor 를 인라인 prompt 로 spawn 하지 않고 **agent 정의 파일**(`agents/orchestrator/advisor.md`)
로 두고 tools 를 화이트리스트한다. 화이트리스트 하나가 세 리스크를 동시에 막는다:

| 리스크 | 차단 근거 |
|---|---|
| 공유 checkout 오염 | `Edit`/`Write` 없음 |
| 다른 teammate 에게 직접 지시 → 결정권 이탈 | `SendMessage` 없음 → 메인하고만 대화하는 star 토폴로지가 구조적으로 강제 |
| 능동적 스코프 확장 | push 수단이 없어 **메인이 물을 때만 답하는 pull-only** |
| 재위임 체인 | `Agent` 없음 (§2.4) |

`model` 은 정의 파일에 박지 않는다 — dispatch 시점에 정책에서 주입한다 (FR-6).

**정의는 페르소나가 아니라 권한 shell 이다.** `Agent` 호출에는 도구를 제한하는 인자가 없어
정의 파일이 tools 를 고정하는 유일한 수단이다. 그러나 고정하는 것은 **권한 경계와 출력 계약뿐**이고,
관점·이름·인원·질문 범위는 런타임에 주입한다 — 협의체의 정책·메커니즘 분리와 같은 구조다.
따라서 같은 shell 을 관점만 바꿔 여러 번 소집하는 **자문 스웜**이 성립하며, 권고가 갈리는 지점
자체가 메인의 판단 재료가 된다. 관점을 하나로 굳히면 정의가 페르소나로 변질된다
(`architect-council.md` 안티패턴 7 과 같은 실패).

### 3.3 가용성 게이팅 (플래그 off → 사용 불가)

판정을 **오케스트레이터 진입 시 1회**로 앞당긴다. 자문 트리거 시점(협의체 예산 소진 등)에 가서
확인하면 이미 다른 경로를 다 태운 뒤라 늦다. 부수 이득으로 협의체 가용성도 같은 체크에서
확정된다.

```
진입 체크 4: printenv CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS
  off → advisor 비활성 (자문 경로 차단) / 협의체는 소집 시 에스컬레이션
```

- **비활성의 범위**: 자문 경로만 닫는다. 트리거 지점에 도달하면 원래 하려던 에스컬레이션으로
  그대로 진행한다 — 오케스트레이션 전체를 멈추지 않는다.
- **폴백·흉내 금지**: 단발 subagent 1회 왕복 대체, 메인의 자문 흉내 모두 금지. 왕복 없는 1회
  답변은 자문의 실질을 잃고 "물어봤다"는 기록만 남긴다.

### 3.4 트리거 (좁게 고정)

상시 자문은 비용·지연만 늘리고 메인 컨텍스트를 태운다. **에스컬레이션 경로의 한 단계**로 둔다:

1. 협의체 `max_council_rounds` 소진 — 에스컬레이션 직전 tie-break
2. 게이트 reject → 재위임이 반복되는 루프 감지
3. 되돌리기 비용이 큰 결정 (스키마 마이그레이션, 공개 API 변경, 토폴로지 변경)
4. 사용자 명시 요청

### 3.5 계약

- **입력**: 자기완결 패킷. advisor 는 메인 대화를 못 보므로 목표·제약·질문을 명시하고, 긴 근거는
  **decision log 경로를 넘겨 advisor 가 직접 Read** 하게 한다 (메인 컨텍스트 절약).
- **출력**: 권고 + 근거 + severity. 명령형 지시·pass/reject 금지.
- **메인의 의무**: 채택/부분채택/기각 + 사유를 decision log 에 남긴다. 기각도 정당한 결과다.
- **승격**: advisor 가 critical 을 지적하면 게이트가 아니라 **에스컬레이션 트리거**로 승격한다.

### 3.6 수명

자문 세션 단위로 spawn 하고, 협의체 tie-break 이면 협의체 팀과 함께 끝난다. team 은 session
종료 시 자동 정리되므로 별도 정리 단계가 없다.

### 3.7 정책 스키마

```yaml
orchestrator:
  roles:
    advisor:
      allow_models: [<model-name>]   # 미선언 시 자문 경로 자체가 비활성
```

## 5. 검증

- `make validate-ci` — 신규 reference 는 50~500줄, agent 는 `description` 필수, `tools` 배열,
  skill → agent 역방향 참조 없음(§2.7).
- 단일 출처 규율: 원칙은 `SKILL.md`, 절차는 `advisory-consult.md`, 명세는 agent 파일. 중복 서술
  금지 (유사도 검사 대상).
- 하위 호환: 정책 파일에 `advisor` 미선언 + 플래그 off 이면 기존 동작과 완전히 동일하다.

## 6. 대안과 기각 사유

| 대안 | 기각 사유 |
|---|---|
| 단발 subagent 로 자문 | 왕복마다 패킷 재합성 + 직전 라운드 망각. 협의체 좌석에 앉힐 수 없다 |
| 플래그 off 시 hard stop | 자문은 통과 조건이 아니다 — 없던 차단이 생긴다 (§2.3) |
| advisor 에게 reject 권한 부여 | 결정권이 메인을 떠나 메인이 고무도장이 된다 (FR-2) |
| 정책 없이 항상 최상위 모델 자문 | 상시 자문은 비용·지연·컨텍스트 낭비 (NFR-1) |
| 문서에 모델명 명시 | 세대 교체 시 문서가 즉시 낡는다 — 기존 원칙 위반 (FR-6) |
