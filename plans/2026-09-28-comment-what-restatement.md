# 새 코드의 what 재서술 주석을 걷어내고 규칙에 판별 문장을 더한다

> **Plan — 이 시점의 결정 기록.** 현재 정책의 신뢰 소스가 아니다.
> 날짜: 2026-09-28 · 브랜치: claude/ecstatic-hawking-e8ov7q · 이슈: 없음 (기존 코드는 #901) · 승인 출처: 사용자 승인

## 요구사항

1. 이 브랜치에서 새로 쓴 코드(orchestrator CLI, hooks 모듈, 두 쪽 테스트)에서 시그니처·반환 타입·분기 구조가 이미 말하는 동작을 다시 적은 주석을 지운다.
2. `payload.rs` 의 `Option<Option<String>>` 을 이름 있는 enum 으로 바꿔, 바깥 None(거부)과 안쪽 None(미지정)의 구분을 시그니처가 말하게 한다. 동작은 바꾸지 않는다.
3. `.claude/rules/comments.md` 에 "시그니처·반환 타입·분기 구조가 이미 말하는 동작을 doc 주석으로 다시 적지 않는다. private 함수의 doc 주석은 이름과 시그니처로 부족할 때만 쓴다" 를 더한다.

## 현재 상태

- 직전 정리(규칙 도입 커밋)는 이슈 번호·문서 포인터처럼 grep 으로 잡히는 위반에 집중해, 한 줄씩 읽어야 보이는 what 재서술을 놓쳤다. 검토 게이트도 같은 축으로 봤다.
- 사용자가 `payload.rs` 의 helper doc 주석을 지적했다 — 바로 아래 `match` 분기를 문장으로 다시 적은 것이다. `parse_spawn_facts` doc 의 필드별 스키마 목록도 본문 다섯 줄의 반복이고, "파싱 실패 시 빈 경고" 는 호출부 동작의 재서술, "엄격하게 파싱하는 이유" 는 결정 근거다(오타입 입력 테스트 8개가 이미 고정한다).
- 규칙에는 "지우고 코드만 읽어도 같은 결론인가" 판별 항목이 이미 있다. 적용이 약했다.

## 검토한 대안

| 대안 | 판단 |

| 주석을 남기고 규칙만 강화 | 버림 — 사용자가 지적한 실제 위반이 남는다 |
| `Option<Option<String>>` 을 두고 주석으로 설명 | 버림 — 주석이 시그니처를 대신하는 전형. rust-core 규칙 "타입으로 제약을 표현하라" |
| 기존 코드까지 what 재서술을 정리 | 버림 — #901 소관. 필요하면 이슈에 기준만 더한다 |

## 결정

1. 새 코드 파일 전수에서 what 재서술 doc·inline 주석을 지운다. 남기는 것은 규칙 1절 DO(코드만 봐서는 모르는 함정, 여러 곳에 흩어진 계약)뿐이다. 판단이 갈리는 줄은 지운다.
2. `payload.rs`: 필드 읽기 결과를 `Absent | Null | Value(String) | WrongType` 같은 enum 이나, 거부를 `Result`/`Option` 의 바깥 층으로 두고 값은 enum 으로 표현하는 형태 중 호출부가 가장 읽기 쉬운 쪽으로 바꾼다. 공개 API `parse_spawn_facts` 의 시그니처와 모든 테스트 결과는 그대로다.
3. 규칙: 1절 DON'T 의 what 항목을 위 문장으로 구체화하고 판별 체크리스트와 맞춘다.
4. 커밋 type 은 `refactor(atelier)`.
