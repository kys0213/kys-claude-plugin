# orchestrator 자율 런에 spec·plan 기준 최종 수용 게이트를 둔다

> **Plan — 이 시점의 결정 기록.** 현재 정책의 신뢰 소스가 아니다.
> 날짜: 2026-11-12 · 브랜치: claude/pensive-bardeen-e3q9b3 · 이슈: 없음 · 승인 출처: 없음 (승인 지점 없음 — 사용자가 게이트 추가를 직접 요청)

## 배경

사용자 보고: 자율주행 런이 "완료"로 끝났는데 실제로는 제대로 끝나지 않은 작업이 있었다. 요청은 "오케스트레이터가 모두 결정하기보다 spec / plan 기반으로 최종 검토하는 게이트"다.

## 원인 분석 (현재 문서 기준)

완료를 판정하는 지점과 그 입력을 따라가면, 끝에서 "요구한 것을 다 했는가"를 메인 말고 아무도 보지 않는다.

| 지점 | 무엇을 보는가 | 놓치는 것 |
|---|---|---|
| task 게이트 (`SKILL.md` 표 6) | task description ↔ 그 task 산출물 | 분해 단계에서 빠진 요구사항 · 조용히 접힌 task · task 사이에 걸친 요구사항 |
| 최종 통합 검증 게이트 (`procedures.md`) | epic HEAD 에서 `integration_verify` green | "깨지지 않았다"만 증명한다. 테스트가 없는 요구사항은 통과한다 |
| 자율 루프 9 "종료 조건 재평가" | 메인이 남은 작업을 재계산 | 기준이 메인이 만든 task 목록이다 — 자기 채점 |
| 종료 보고 3분류 DONE | 검증 증거(테스트·커밋) | 요구사항 대비 커버리지가 증거 항목에 없다 |

설계 단계에는 생성자 ≠ 검증자(협의체)를, task 단계에는 구현자 ≠ 게이트를 강제하면서 런 단위 완료 판정에는 그 분리가 없다.

## 요구사항

1. 완료 선언 직전에 spec·plan 을 기준선으로 epic 전체 산출물을 대조하는 게이트를 둔다.
2. 그 판정은 메인(오케스트레이터)이 아니라 다른 agent 가 내린다. 메인은 verdict 를 뒤집어 완료를 선언하지 못한다.
3. 누락·부분이 나오면 완료가 아니다 — 예산이 남으면 메꾸고, 없으면 미완으로 정직하게 보고한다.

## 사이드이펙트 조사

- orchestrator 문서는 `scripts/check-decision-graph.sh` 의 줄수 상한과 `##` heading 화이트리스트를 따른다. 새 절차 절 `최종 수용 게이트` 를 화이트리스트에 등재한다. 현재 SKILL 178/200 · contracts 245/250 · procedures 104/160 이라 contracts 는 행 추가 없이 기존 행을 고친다.
- 예산 수치는 `contracts.md §예산과 가드레일 값` 에만 둔다. 새 예산 이름은 만들지 않는다 — 게이트가 낸 gap 은 루프를 한 번 더 도는 것이라 `max_loops` · no-progress 가 이미 상한이다.
- 다른 스킬·룰은 orchestrator 를 이름으로만 부르므로(규약 §7) 외부 문서 수정이 없다. `grep` 으로 `최종 통합 검증 게이트` 외부 참조는 검사 스크립트 화이트리스트뿐임을 확인했다.
- 테스트(`plugins/atelier/tests/*`)는 orchestrator 문구를 검사하지 않는다.
- 편집 대상 파일에 정리할 규칙 위반이 없다. 선행 정리 0건.

## 결정과 근거

### 1. 위치 — 최종 통합 검증 green 뒤, 완료 선언 전

통합 검증이 red 면 어차피 완료가 아니므로 그 뒤에 둔다. 수용 게이트가 gap 을 내면 gap task 를 머지한 뒤 통합 검증부터 다시 돈다.

### 2. 기준선 — spec > plan > 요청 원문. 메인의 task 목록은 기준선이 아니다

task 목록은 메인이 plan 에서 도출한 것이라, 그걸 기준으로 삼으면 분해 누락이 그대로 통과한다. 사용자 요청도 메인의 요약이 아니라 원문을 싣는다. 기준선 항목 추출도 검토자가 직접 한다 — 메인이 항목을 뽑아 주면 같은 누락이 생긴다. 상충(spec 과 plan 이 다름)은 검토자가 판정하지 않고 상충으로 보고한다 → 정지 조건 1/10 경로.

### 3. 검토자 — 메인·구현·task 게이트와 다른 agent, 최상위 tier `high`

틀린 것이 사용자가 결과를 받은 뒤에야 드러나는 일이라 표 1 기준으로 최상위다. 집행 위임 상한은 그대로 지킨다(자문 tier 아님). read-only 라 격리 없음, 단발 subagent. 메인의 완료 주장·task 상태·게이트 이력은 싣지 않는다 — anchoring 을 막는다.

### 4. verdict — 항목별 `충족 | 부분 | 누락 | 해당 없음`, 증거 필수

불변식 14(claim 에 명령·`file:line`, 부재 주장은 두 전략)를 그대로 적용한다. 기준선에 없는 변경(초과)도 따로 보고한다.

### 5. 판정권 — 게이트다, 자문이 아니다

전 항목이 충족(또는 근거 있는 해당 없음)이어야 DONE 이다. 메인이 verdict 에 동의하지 않으면 뒤집지 않고 사용자에게 올린다(정지 조건 4 의 "의도가 갈림"). 자문(불변식 18)과 반대로 결정권이 게이트에 있다는 점을 명시한다.

### 6. 적용 범위 — 자율 · 무거운 경로

- 경량 경로(tracked 변경 없음)는 산출물이 응답 텍스트라 사용자가 바로 본다 — 생략을 기록한다.
- HITL 은 종료 확인 지점에서 사용자가 이 역할을 한다 — 사용자가 요청한 범위("자율주행시")에 맞춰 넣지 않는다.

### 7. 종료 보고·핸드오프

- `done_when` 에 "자율 무거운 경로는 최종 수용 게이트 전 항목 충족 포함"을 더한다.
- 종료 보고에 수용 게이트 건수(충족·부분·누락·해당 없음)와 verdict 경로를 싣는다. 부분·누락 항목은 핸드오프의 BLOCKED/NOT-STARTED 로 남긴다.

## 버린 대안

| 대안 | 이유 |
|---|---|
| 기존 최종 통합 검증 게이트에 항목을 덧붙임 | 그 게이트는 결정적 명령 1회다. 판단이 섞인 대조를 섞으면 "명령 green = 완료"라는 단순한 계약이 흐려진다 |
| 메인이 직접 plan 체크리스트를 대조 | 자기 채점 그대로다. 요청의 핵심이 판정 주체 분리다 |
| 자문(Fable) 에게 검토를 맡김 | 자문은 결정권이 없는 입력이다(불변식 18). 게이트로 쓰면 그 불변식과 충돌한다 |
| 수용 게이트 전용 라운드 예산 신설 | gap 메꾸기는 루프 한 바퀴라 `max_loops` · no-progress 가 이미 막는다. 이름이 늘면 문서 줄수만 는다 |
| HITL 에도 적용 | 요청 범위 밖이고, HITL 은 종료 시 사용자 확인이 있다. 필요하면 후속으로 넓힌다 |
| 같은 검토자를 재검토에 재사용 | 이전 verdict 에 anchoring 된다. 재검토는 새 agent 가 전 기준선을 다시 본다 — gap 수정이 다른 항목을 깨뜨릴 수 있다 |
