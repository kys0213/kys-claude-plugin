# 내 판단을 닮아 가며 결정을 준비해 보고하는 로컬 분신 doppel 을 만든다

> **Plan — 이 시점의 결정 기록.** 현재 정책의 신뢰 소스가 아니다.
> 날짜: 2026-10-21 · 브랜치: claude/pensive-maxwell-bu1ivi · 이슈: 없음 · 승인 출처: 사용자 승인 (2026-10-21 설계안 제시 후 이름 `doppel`, 위치 "areum-lab-tools 에 넣자", 골든 확정 "주기적 묶음 리뷰", 검색 "FTS5 + 카테고리 필터", 시드 카테고리 3종 + "로컬 클로드 세션 기반으로 초기 데이터" 선택, 이어서 "모든 판단을 직접 처리하기보다 배경과 함께 가장 유사했던 선택 또는 새로운 의견을 먼저 공유 — doppel 이 살펴보고 보고하는 형태")

## 요구사항

1. 로컬에서 실행 중인 Claude 세션을 내가 찾아다니지 않는다. doppel 이 세션들을 살펴보고 나에게 보고한다.
2. 결정이 필요한 지점마다 doppel 이 직접 처리하기보다, 결정할 내용의 배경과 함께 과거 내 판단과 가장 유사했던 선택 또는 새로운 의견을 먼저 공유한다. 결정은 내가 한다.
3. 판단 이력을 카테고리별 골든셋으로 로컬에서 관리해, 쓸수록 doppel 의 추천이 내 판단과 닮아 가게 한다.
4. 멘션·이슈 등 들어온 요청을 칸반 카드로 만들고, 지정한 프로젝트 경로에서 Claude 를 띄워 처리한다.
5. 외부 메시징 채널(Slack·Discord·mail 등)은 doppel 에 등록된 만큼 fanout 하고, 수신은 WebSocket 으로 받는다 — `claude <> doppel <> slack, discord, mail`.
6. `discord-connector` 는 Discord 에 특화돼 있으므로 건드리지 않는다.

## 현재 상태 (사이드이펙트 조사)

- **이미 있는 부품**
  - `discord-connector` 런처: 메시지당 `claude -p` 실행, 스레드별 잠금, `--resume <session_id>`, 채널→디렉토리 매핑 (`plans/2026-10-04-discord-connector.md`).
  - `AskUserQuestion` 가로채기: `tool.call` hook 이 `next` 없이 `{ result: { questions, answers } }` 를 돌려주면 Claude 가 이어간다. 대기는 `ask create` → `$.process.run(ask wait)` 로 한다 (`plugins/discord-connector/hooks/register.ts`).
  - 결정적 판정은 CLI, hook 은 어댑터라는 선례: atelier `hooks/register.ts` + `atelier orchestrator spawn-check` (`plans/2026-09-28-atelier-function-hooks-dispatch-guard.md`).
  - 세션 JSONL 을 SQLite 로 인덱싱하는 설계: `plugins/suggest-workflow/V3-DESIGN.md`.
  - 데몬 + SQLite 를 CLI 와 공유하는 구조: areum-lab-tools 의 `discord` CLI.
- **판단 시드가 이미 있는 곳**: 이 저장소 `plans/` 의 헤더 "승인 출처" 와 "버린 선택지" 절이 내가 고른 것·버린 것·이유를 담고 있다 (예: #904 plan 의 "자율에선 면제 금지 선택").
- **제약**
  - function hooks 는 early access 다 (`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`). API 가 바뀔 수 있다.
  - hook 예산은 10초, `$.process.run` 대기는 최대 10분이다. hook 안에서 장수 소켓을 여는 것은 확인되지 않았다. 내가 10분 안에 답하지 못하는 결정이 흔할 것이다.
  - 터미널 세션에 바깥에서 입력을 넣는 수단은 확인되지 않았다. 바깥에서 이어갈 수 있는 것은 `--resume` 으로 다시 띄우는 headless 세션이다.
  - 같은 Discord 봇 토큰으로 게이트웨이를 두 곳에서 열면 interaction 응답이 경쟁한다.
  - `orchestrator` 는 atelier 의 skill 이름이자 CLI 그룹 이름이라 새 CLI 이름으로 쓰지 않는다.
  - `discord-connector` hook 은 `DISCORD_CONNECTOR_*` env 가 있는 세션에만 개입한다. doppel hook 이 같은 세션의 `AskUserQuestion` 을 함께 가로채면 이중 처리가 된다.
  - 세션 원문에는 토큰·키가 섞인다.

## 결정

1. **정체성은 오케스트레이터가 아니라 참모형 분신이다.** doppel 은 세션을 살펴보고, 결정할 거리를 모아, 배경과 추천을 붙여 보고한다. 결정은 내가 하고, 내 결정이 다시 골든셋으로 쌓인다. 세션 관찰·칸반·실행(몸)과 채널 어댑터(입·귀)는 이 루프를 위한 수단이다.

   ```
   살펴보기(sweep) → 결정 지점 수집 → 브리프 작성 → 보고(inbox·채널) → 내가 결정 → 세션에 전달 + 원장 기록 → 골든 리뷰
   ```
2. **배치**
   - CLI·데몬 `doppel` (Rust, SQLite, 로컬 웹 UI): areum-lab-tools.
   - 얇은 plugin `plugins/doppel` (hook 모듈, 브리프·분류 skill·agent): 이 저장소.
   - 데몬 수명이 plugin 버전에 묶이지 않게 하려는 것이다.
3. **책임 경계** (CLAUDE.md, `.claude/rules/tool-layer-boundary.md`)

   | doppel CLI·데몬 (결정적) | plugin 의 skill·agent (판단) |
   |---|---|
   | 세션 상태 집계, 결정 지점 수집(결정적 신호만), 배경 사실·판례 검색 번들 생성, 원장 기록, 골든 상태 전이, 일치율 집계, 보고 큐 정렬, 세션 실행·resume, fanout, 먼저 온 답 판정, 스레드 매핑 | 브리프 작성(배경 요약·추천·새 의견), 세션 진행 보고 요약, 카테고리 분류·분류 체계 제안, 골든 후보 추천, rule 승격 제안, 인입 요청 triage |

   브리프가 필요하면 데몬이 브리프 agent 를 `claude -p` 로 띄우고 검색 번들을 넘긴다. 판단 내용은 agent 프롬프트에 있고, 데몬은 실행만 한다 (`discord-connector` 런처와 같은 위치).
4. **살펴보기 (sweep)** — doppel 이 hook 이벤트와 세션 JSONL 로 세션별 상태를 갖는다 (진행 중·결정 대기·막힘·완료). 결정 지점은 결정적 신호로만 잡는다.
   - 대기 중인 `AskUserQuestion`, 권한 거부(`PermissionDenied`), 턴이 끝나 내 입력을 기다리는 세션(`Stop`), 들어온 멘션·이슈.
   - `Stop` 세션의 마지막 메시지가 나에게 묻는 것인지는 판단이라 브리프 agent 가 해석한다.
5. **브리프** — 결정 지점마다 한 장. 항목:
   - 무엇을 결정해야 하나 (질문, 선택지)
   - 배경 (세션이 무엇을 하던 중인지, 지금까지 흐름, 관련 파일·PR·이슈·rules·spec)
   - 과거 유사 판단 (판례 top-k 와 그때의 내 답·근거, 서로 충돌하면 표시)
   - doppel 의견: 판례와 가장 가까운 선택을 추천하거나, 판례가 맞지 않으면 "새 의견" 으로 라벨을 붙여 제시한다. 확신도와 가역성을 함께 적는다.
6. **보고** — 브리프와 세션 진행 요약을 하나의 inbox 로 묶어 웹 UI 와 등록된 채널에 낸다.
   - 정렬: 내 답을 기다리며 멈춘 세션 → 되돌릴 수 없는 결정 → 대기 시간.
   - 응답: 추천 수락 / 다른 선택 / 직접 답. doppel 이 답을 세션에 전달한다.
   - 10분 안에 답이 없으면 hook 은 "사용자 판단 보류 중" 을 답으로 돌려주고 세션은 턴을 끝낸다. 내가 나중에 답하면 headless 세션은 그 답으로 `--resume` 한다. 터미널 세션은 브리프와 답을 기록만 하고, 이어가기는 내가 터미널에서 한다.
7. **수집** — 판단 순간을 원본 레코드로 남긴다. 필드: 맥락 요약, 질문, 선택지, 내 답, 근거, 프로젝트, 모드(HITL/자율), 가역성, 출처, 그때의 브리프 추천과 수락 여부.
   - 실시간: inbox 응답, hook 의 `AskUserQuestion` 답, 권한 허용·거부.
   - 과거: `doppel ingest` 가 로컬 세션 JSONL 과 `plans/` 를 읽는다. 세션 중 정정 발화("아니 그거 말고")도 후보로 뽑는다.
   - 수집 단계에서 redaction 한다. 데이터는 로컬에만 둔다.
8. **카테고리** — 초기 분류 체계는 로컬 세션 데이터에서 만든다.
   - `doppel ingest` (결정적) → 분류 skill 이 체계를 제안 → 묶음 리뷰에서 내가 확정한다.
   - 시드: 설계 승인·범위 자르기 / 네이밍·API·테스트 전략 / 의존성·리뷰 판정.
   - 분류 체계는 버전을 갖는다.
9. **골든셋** — 상태는 `candidate → confirmed → retired`, 뒤집힌 판단은 `superseded_by` 로 잇는다.
   - 확정은 주기적 묶음 리뷰(`doppel review`)로 한다. 추천을 내가 뒤집은 사례를 큐 앞에 둔다.
   - 같은 판단이 판례로 반복되면 rule 승격을 제안한다. 승격은 내가 승인한다.
10. **검색** — SQLite FTS5 + 카테고리 필터 + 맥락 필드(프로젝트·가역성·모드). 충돌하는 판례가 함께 걸리면 번들에 표시한다. 임베딩은 데이터가 쌓인 뒤 붙인다.
11. **평가** — 모든 브리프가 곧 예측이라 별도 shadow 모드 없이 평가 데이터가 쌓인다.
    - 지표는 카테고리별 추천 수락률이고, 다수 답 baseline 대비 향상폭(lift)으로 본다. 거절·정정 사례는 따로 집계한다 — 늘 "진행" 을 추천하는 분신이 높은 점수를 얻지 못하게.
    - "새 의견" 은 따로 집계한다 (채택률).
    - 골든셋 leave-one-out 재현으로 프롬프트·골든셋 변경의 회귀를 잰다.
    - 브리프 레코드마다 골든셋 버전과 브리프 프롬프트 버전을 남긴다.
12. **자동 처리는 기본으로 하지 않는다.** 기본 동작은 브리프 보고다.
    - 내가 카테고리별로 명시적으로 켰을 때만 doppel 이 추천안으로 바로 답하고 사후 보고한다. 켤 수 있는지는 측정값과 내가 설정한 기준값으로 CLI 가 판정하고, 기준값을 자동 조정하지 않는다.
    - 되돌릴 수 없는 행동(push·merge, 삭제, 외부 게시, 비용 발생)은 켤 수 없다.
13. **세션 프로토콜 (Claude ↔ doppel)** — hook 이 CLI 를 호출한다.
    - `doppel session register|end`, `doppel event emit`: 보내고 잊는다. 데몬이 없으면 아무것도 하지 않는다.
    - `doppel ask create` → `doppel ask wait --timeout 600`: hook 이 `{ result: { questions, answers } }` 로 답한다 (보류 처리는 결정 6).
    - doppel 이 띄운 세션과 터미널 세션이 같은 hook 경로를 탄다.
    - `DISCORD_CONNECTOR_*` env 가 있으면 관찰만 하고 질문은 가로채지 않는다.
14. **채널 프로토콜 (어댑터 ↔ doppel, WebSocket)**
    - 어댑터는 접속 시 `{channel, capabilities}` 를 등록한다. localhost + 토큰.
    - 나가는 `report | ask | update` 는 등록된 어댑터 전부에 fanout 하고, 어댑터가 capability 에 맞게 렌더링한다.
    - 들어오는 봉투 `{channel, thread_ref, author, text, reply_to}` 는 `(channel, message_id)` 로 멱등 처리한다.
    - `ask_id` 단위로 먼저 온 답을 채택하고, 나머지 채널에는 "다른 곳에서 답변됨" `update` 를 보낸다. 답할 권한(allowlist)은 doppel 이 판정한다.
    - `card/session ↔ (channel, thread_ref)` 매핑은 doppel 이 갖는다. 어댑터는 상태가 없다.
    - 웹 UI 도 같은 프로토콜의 클라이언트다.

## 버린 선택지

- **오케스트레이터(hub) 중심 정체성** — 실행·fanout 은 도구라 쉽게 대체된다. 쌓이는 가치는 판단 이력이고, 그것을 1급으로 두어야 쓸수록 좋아진다.
- **doppel 이 판단을 직접 처리하는 대리인 중심** — 사용자가 원한 것은 결정을 준비해 먼저 공유받는 것이다. 대리 처리는 카테고리별 opt-in 으로만 남긴다.
- **별도 shadow 모드** — 브리프 보고가 기본이면 모든 브리프가 예측이고 내 응답이 정답이라, 따로 둘 이유가 없다.
- **`discord-connector` 를 확장** — Discord 특화 로직(스레드 생성·이력 조립·분할 게시)이 섞여 있다. 채널 특화는 어댑터로 빼고 중심은 채널을 모르게 한다.
- **파인튜닝으로 닮게 하기** — 로컬에서 재현·감사가 어렵다. 판례 검색 + 인용이면 왜 그렇게 추천했는지 사람이 검토할 수 있다.
- **CLI 가 브리프까지 직접 작성** — 같은 입력에 다른 출력이 나오는 판단이 CLI 로 들어간다. 데몬은 브리프 agent 를 실행만 한다.
- **결정 지점 감지를 자연어 해석으로** — 감지가 비결정적이 된다. 감지는 결정적 신호로 하고, 해석은 브리프 agent 가 한다.
- **골든 건별 즉시 확정** — 작업 흐름이 자주 끊긴다.
- **처음부터 로컬 임베딩** — 모델 의존성과 버전 고정 부담이 데이터가 적은 초기에 비해 크다.
- **hook 이 doppel 과 WebSocket 을 직접 유지** — hook 안 장수 소켓이 확인되지 않았다. 확인된 `$.process.run` 대기 패턴을 쓴다.
- **어댑터가 스레드 상태를 소유** — 어댑터 재시작 때 대화가 끊긴다.
- **위험·권한·우선순위를 시드 카테고리에 포함** — 이번 선택에서 빠졌다. 되돌릴 수 없는 행동의 자동 처리 금지는 카테고리와 무관하게 유지한다.

## 열린 질문

- **설계 승인 카테고리의 자동 처리와 atelier 승인 출처의 관계** — atelier 는 자율 런의 설계 승인을 협의체 pass 또는 사용자 승인으로만 인정한다 (#904). 브리프를 보고 내가 수락한 것은 사용자 승인이다. doppel 이 자동 처리한 답을 승인 출처로 인정할지는 정하지 않았다. 정하기 전까지 이 카테고리는 자동 처리를 켤 수 없다.
- 자동 처리를 켤 수 있는 기준값(표본 수·lift)의 초기값.
- 보고 주기 — 결정 지점이 생길 때마다 즉시 낼지, 묶어서 낼지, 둘을 섞을지.
- Discord 어댑터의 봇 토큰을 `discord-connector` 와 분리할지, 기존 `discord` 데몬 위에 어댑터를 올릴지.
