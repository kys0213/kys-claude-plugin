## 요구사항

1. 로컬에서 실행 중인 Claude 세션을 내가 찾아다니지 않는다. doppel 이 세션들을 살펴보고 나에게 보고한다.
2. 결정이 필요한 지점마다 doppel 이 직접 처리하기보다, 결정할 내용의 배경과 함께 과거 내 판단과 가장 유사했던 선택 또는 새로운 의견을 먼저 공유한다. 결정은 내가 한다.
3. 판단 이력을 카테고리별 골든셋으로 로컬에서 관리해, 쓸수록 doppel 의 추천이 내 판단과 닮아 가게 한다.
4. 여러 곳에서 들어오는 외부 작업(멘션·이슈 등)을 받아 라벨링하고 칸반으로 관리하며, 지정한 프로젝트 경로에서 Claude 를 띄워 작업을 분배한다. 이 컴퓨터를 기반으로 내 대신 비서 역할을 하고, UI 가 있다.
5. 세션과 doppel 은 N:1 WebSocket 으로 잇는다. 외부 메시징 채널(Slack·Discord·mail 등)은 doppel 뒤가 아니라 각자 별도 plugin 으로 세션에 N:1 로 붙는다. `AskUserQuestion` 과 그 답은 function hook 으로 터미널·doppel·채널 모두에 반영한다.

   ```
   claude sessions  N:1  doppel
                    N:1  slack
                    N:1  discord …
   ```
6. `discord-connector` 는 Discord 에 특화돼 있으므로 건드리지 않는다.
7. doppel 은 OS 별 바이너리를 지원하고, 설치 스크립트도 OS 별로 둔다. 지금은 macOS(arm64·x64)만, 다른 OS 로 넓힐 여지를 남긴다.

## 현재 상태 (사이드이펙트 조사)

- **이미 있는 부품**
  - `discord-connector` 런처: 메시지당 `claude -p` 실행, 스레드별 잠금, `--resume <session_id>`, 채널→디렉토리 매핑 (`plans/2026-10-04-discord-connector.md`).
  - `AskUserQuestion` 가로채기: `tool.call` hook 이 `next` 없이 `{ result: { questions, answers } }` 를 돌려주면 Claude 가 이어간다. 대기는 `ask create` → `$.process.run(ask wait)` 로 한다 (`plugins/discord-connector/hooks/register.ts`).
  - 결정적 판정은 CLI, hook 은 어댑터라는 선례: atelier `hooks/register.ts` + `atelier orchestrator spawn-check` (`plans/2026-09-28-atelier-function-hooks-dispatch-guard.md`).
  - 세션 JSONL 을 SQLite 로 인덱싱하는 설계: `plugins/suggest-workflow/V3-DESIGN.md`.
  - 데몬 + SQLite 를 CLI 와 공유하는 구조: areum-lab-tools 의 `discord` CLI.
- **areum-lab-tools 현황** (`b57c59b` 기준)
  - Cargo workspace (`tools/*`, edition 2024, Rust 1.96). 도구는 `discord`·`hello`·`kanban`.
  - `tools/kanban` 이 이미 있다: 유입 이슈를 로컬 LLM 으로 프로젝트에 배정하는 보드, 점유(`next`)·완료·해제, 사람이 고친 판정만 골든셋으로 쌓아 few-shot 으로 되먹이는 분류기 (`docs/kanban-board.md`, `docs/kanban-classifier.md`). 에이전트 실행은 별도 레포 belt 가 kanban 의 소비자로 맡는다고 적혀 있다.
  - 릴리스(`release.yml`)는 모든 도구 공용이고 `aarch64-apple-darwin` 하나만 빌드한다. `scripts/install.sh` 도 Darwin/arm64 가 아니면 실패한다. 체크섬 계약은 `<tarball>.sha256` + `shasum -a 256 -c`.
  - `ci.yml` 은 ubuntu 전용이고, macOS 러너는 릴리스 빌드에만 쓴다 (`.claude/rules/ci-release.md`).
  - workspace 의존성 `libc` 는 `discord` 데몬의 Unix 시그널용이다. Windows 빌드는 지금 어느 도구도 하지 않는다.
- **판단 시드가 이미 있는 곳**: 이 저장소 `plans/` 의 헤더 "승인 출처" 와 "버린 선택지" 절이 내가 고른 것·버린 것·이유를 담고 있다 (예: #904 plan 의 "자율에선 면제 금지 선택").
- **제약**
  - function hooks 는 early access 다 (`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`). API 가 바뀔 수 있다.
  - hook 예산은 10초, `$.process.run` 대기는 최대 10분이다 (진행 중인 `$` 호출은 예산에 세지 않는다). 내가 10분 안에 답하지 못하는 결정이 흔할 것이다.
  - hook 런타임 (Claude Code 2.1.306 `claude-code.d.ts` 확인):
    - WebSocket API 는 없다. 네트워크는 `$.http.fetch` 요청-응답뿐이고, `socketPath` 로 Unix socket 을 탈 수 있다.
    - `$.process.spawn` 은 `session.start` 에서 띄운 자식을 세션 수명 동안 유지하고 stdout 을 조각 스트림으로 준다 (타입 문서 예시가 `bridge watch` 패턴). stdin 은 시작 때 한 번 쓰고 닫힌다.
    - `$.prompt.submit` 은 idle 세션에 새 턴을 시작시키고, `$.session.append` 는 진행 중 턴에 사용자 역할 meta 행을 넣는다. 터미널 세션에도 바깥에서 답을 넣을 수 있다.
    - `$.clock.every`·`$.clock.after` 타이머는 취소되거나 모듈이 다시 로드될 때까지 돈다. 모듈 변수는 재로드 때 초기화되고 `$.state`·`$.store` 는 남는다.
    - 모듈은 plugin 안의 파일만 import 한다. Node·npm 해석이 없어 rxjs 같은 라이브러리는 번들한 파일로 넣어야 한다.
    - 대기 신호: `tool.call {tool:'AskUserQuestion'}`, `classic.PermissionRequest`, `classic.Notification` (`notification_type: string` — 값 목록은 선언에 없다), `turn.start`·`turn.complete` (main 은 `agentId` 없음), `classic.PostToolUseFailure`, `session.end`.
  - 같은 Discord 봇 토큰으로 게이트웨이를 두 곳에서 열면 interaction 응답이 경쟁한다.
  - `orchestrator` 는 atelier 의 skill 이름이자 CLI 그룹 이름이라 새 CLI 이름으로 쓰지 않는다.
  - `discord-connector` hook 은 `DISCORD_CONNECTOR_*` env 가 있는 세션에만 개입한다. doppel hook 이 같은 세션의 `AskUserQuestion` 을 함께 가로채면 이중 처리가 된다.
  - 세션 원문에는 토큰·키가 섞인다.

## 결정

1. **정체성은 오케스트레이터가 아니라 참모형 분신이다.** doppel 은 세션을 살펴보고, 결정할 거리를 모아, 배경과 추천을 붙여 보고한다. 결정은 내가 하고, 내 결정이 다시 골든셋으로 쌓인다. 세션 관찰·칸반·실행(몸)과 채널 어댑터(입·귀)는 이 루프를 위한 수단이다.

   ```
   살펴보기(sweep) → 결정 지점 수집 → 브리프 작성 → 보고(inbox·채널) → 내가 결정 → 세션에 전달 + 원장 기록 → 골든 리뷰
   ```
2. **배치**
   - CLI·데몬 `doppel` (Rust, SQLite, 로컬 웹 UI): areum-lab-tools.
   - 얇은 plugin `plugins/doppel` (hook 모듈, 브리프·분류 skill·agent): 이 저장소.
   - 데몬 수명이 plugin 버전에 묶이지 않게 하려는 것이다.
3. **책임 경계** (CLAUDE.md, `.claude/rules/tool-layer-boundary.md`)

   | doppel CLI·데몬 (결정적) | plugin 의 skill·agent (판단) |
   |---|---|
   | 세션 상태 집계, 결정 지점 수집(결정적 신호만), 배경 사실·판례 검색 번들 생성, 원장 기록, 골든 상태 전이, 일치율 집계, 보고 큐 정렬, 세션 실행·resume, 세션 연결(WebSocket) | 브리프 작성(배경 요약·추천·새 의견), 세션 진행 보고 요약, 카테고리 분류·분류 체계 제안, 골든 후보 추천, rule 승격 제안, 인입 요청 triage |

   브리프가 필요하면 데몬이 브리프 agent 를 `claude -p` 로 띄우고 검색 번들을 넘긴다. 판단 내용은 agent 프롬프트에 있고, 데몬은 실행만 한다 (`discord-connector` 런처와 같은 위치).
4. **살펴보기 (sweep)** — doppel 이 세션별 이벤트 스트림을 접어(scan) 상태를 만든다. hook 은 사실만 보내고 상태 판정은 doppel 이 한다. 신호는 결정적인 것만 쓰고, 시간·횟수 기준값은 설정으로 받는다.

   | 상태 | 신호 |
   |---|---|
   | 진행 중 | `turn.start` 이후 `turn.step`·도구 이벤트가 이어짐 |
   | 대기·질문 | `tool.call {AskUserQuestion}` 이 답을 받지 못함 |
   | 대기·권한 | `classic.PermissionRequest`, `classic.Notification` 의 권한 유형, auto 모드의 `PermissionDenied` |
   | 대기·턴 종료 | main `turn.complete` 뒤 `prompt.submit` 이 없음 (`classic.Notification` idle 유형은 보조) |
   | 정체 | 턴 진행 중인데 마지막 이벤트 이후 N분 |
   | 반복 실패 | `PostToolUseFailure` 연속 K회 |
   | 끊김 | `session.end` 없이 attach 스트림 종료 또는 heartbeat 누락 |
   | 완료 | `session.end` |

   - 턴 종료 대기가 나에게 묻는 것인지 완료 보고인지는 판단이라, 브리프 agent 가 `turn.complete` 의 답 텍스트로 해석한다.
   - 들어온 멘션·이슈도 결정 지점이다.
5. **브리프** — 결정 지점마다 한 장. 항목:
   - 무엇을 결정해야 하나 (질문, 선택지)
   - 배경 (세션이 무엇을 하던 중인지, 지금까지 흐름, 관련 파일·PR·이슈·rules·spec)
   - 과거 유사 판단 (판례 top-k 와 그때의 내 답·근거, 서로 충돌하면 표시)
   - doppel 의견: 판례와 가장 가까운 선택을 추천하거나, 판례가 맞지 않으면 "새 의견" 으로 라벨을 붙여 제시한다. 확신도와 가역성을 함께 적는다.
6. **보고** — 브리프와 세션 진행 요약을 doppel 웹 UI 의 inbox 하나로 묶어 낸다. 같은 질문은 세션에 붙은 채널 plugin 들이 각자 자기 채널에도 올린다 (결정 14).
   - 정렬: 내 답을 기다리며 멈춘 세션 → 되돌릴 수 없는 결정 → 대기 시간.
   - 응답: 추천 수락 / 다른 선택 / 직접 답. doppel 이 답을 세션에 전달한다.
   - 중계 범위와 먼저 온 답 판정은 결정 18 이다.
   - 터미널이 없는 세션(doppel 이 띄운 headless 세션)은 설정한 시간 동안 답이 없으면 hook 이 "사용자 판단 보류 중" 을 답으로 돌려주고 턴을 끝낸다. 내가 나중에 답하면 doppel 이 attach 스트림으로 답을 보내고, hook 이 `$.prompt.submit` 으로 그 세션에 새 턴을 연다. 세션 프로세스가 이미 끝났으면 `--resume` 으로 다시 띄운다. 터미널이 있는 세션은 터미널 대화상자가 떠 있으므로 보류하지 않고 계속 기다린다.
7. **수집** — 판단 순간을 원본 레코드로 남긴다. 필드: 맥락 요약, 질문, 선택지, 내 답, 근거, 프로젝트, 모드(HITL/자율), 가역성, 출처, 그때의 브리프 추천과 수락 여부.
   - 실시간: inbox 응답, hook 의 `AskUserQuestion` 답, 권한 허용·거부.
   - 과거: `doppel ingest` 가 로컬 세션 JSONL 과 `plans/` 를 읽는다. 세션 중 정정 발화("아니 그거 말고")도 후보로 뽑는다.
   - 수집 단계에서 redaction 한다. 데이터는 로컬에만 둔다.
8. **카테고리** — 초기 분류 체계는 로컬 세션 데이터에서 만든다.
   - `doppel ingest` (결정적) → 분류 skill 이 체계를 제안 → 묶음 리뷰에서 내가 확정한다.
   - 시드: 설계 승인·범위 자르기 / 네이밍·API·테스트 전략 / 의존성·리뷰 판정.
   - 분류 체계는 버전을 갖는다.
9. **골든셋** — 상태는 `candidate → confirmed → retired`, 뒤집힌 판단은 `superseded_by` 로 잇는다.
   - 확정은 주기적 묶음 리뷰(`doppel review`)로 한다. 추천을 내가 뒤집은 사례를 큐 앞에 둔다.
   - 같은 판단이 판례로 반복되면 rule 승격을 제안한다. 승격은 내가 승인한다.
10. **검색** — SQLite FTS5 + 카테고리 필터 + 맥락 필드(프로젝트·가역성·모드). 충돌하는 판례가 함께 걸리면 번들에 표시한다. 임베딩은 데이터가 쌓인 뒤 붙인다.
11. **평가** — 모든 브리프가 곧 예측이라 별도 shadow 모드 없이 평가 데이터가 쌓인다.
    - 지표는 카테고리별 추천 수락률이고, 다수 답 baseline 대비 향상폭(lift)으로 본다. 거절·정정 사례는 따로 집계한다 — 늘 "진행" 을 추천하는 분신이 높은 점수를 얻지 못하게.
    - "새 의견" 은 따로 집계한다 (채택률).
    - 골든셋 leave-one-out 재현으로 프롬프트·골든셋 변경의 회귀를 잰다.
    - 브리프 레코드마다 골든셋 버전과 브리프 프롬프트 버전을 남긴다.
12. **자동 처리는 기본으로 하지 않는다.** 기본 동작은 브리프 보고다.
    - 내가 카테고리별로 명시적으로 켰을 때만 doppel 이 추천안으로 바로 답하고 사후 보고한다. 켤 수 있는지는 측정값과 내가 설정한 기준값으로 CLI 가 판정하고, 기준값을 자동 조정하지 않는다.
    - 되돌릴 수 없는 행동(push·merge, 삭제, 외부 게시, 비용 발생)은 켤 수 없다.
13. **세션 프로토콜 (Claude ↔ doppel)** — 세션도 WebSocket 으로 붙되, hook 런타임에 WebSocket 이 없으므로 `doppel attach` 자식 프로세스가 연결을 대신 든다.

    ```
    hook 모듈 ──$.http.fetch (Unix socket POST)──────────▶ doppel 데몬   (나가는 방향: 이벤트·질문)
    hook 모듈 ◀──stdout JSON lines── doppel attach ◀──WS── doppel 데몬   (들어오는 방향: 답·맥락·지시)
    ```

    - `session.start` 에서 `$.process.spawn(['doppel', 'attach', '--session', <id>])` 로 띄우고 세션 수명 동안 둔다. 끊기면 `$.clock.after` 로 다시 띄운다.
    - 나가는 이벤트는 보내고 잊는다. 데몬이 없으면 아무것도 하지 않는다 (fail-open).
    - 들어오는 메시지: `answer` (대기 중 질문이면 그 hook 이 답하고, 보류된 질문이면 `$.prompt.submit`), `context` (`$.session.append`), `prompt` (`$.prompt.submit`).
    - 질문·권한 대기는 예산에 세지 않는 `$.process.run(['doppel', 'ask', 'wait', ...])` 로 한다 (호출당 최대 10분이라 끝날 때까지 다시 부른다). 결정 6 의 보류로 넘어가는 시간은 설정값이다.
    - plugin 을 설치하면 모든 세션이 연결된다. doppel 이 띄운 세션과 터미널 세션이 같은 hook 경로를 탄다.
    - `DISCORD_CONNECTOR_*` env 가 있으면 관찰만 하고 질문은 가로채지 않는다.
14. **채널은 doppel 의 어댑터가 아니라 세션에 붙는 별도 plugin 이다.** 세션 하나에 doppel plugin, slack plugin, … 이 함께 깔리고, 각 plugin 은 자기 채널의 로컬 프로세스에 N:1 로 붙는다.
    - 채널마다 외부 연결은 로컬 프로세스 하나가 갖는다. Slack Socket Mode 는 이벤트를 연결 중 하나에만 보내고, Discord 게이트웨이는 같은 토큰으로 두 군데서 열면 응답이 경쟁하므로, 세션마다 직접 연결하면 안 된다 (`discord` CLI 데몬과 같은 구조).
    - 채널 plugin 들은 같은 relay 계약을 따른다: 질문을 자기 채널에 올리고, 자기 채널의 답 스트림을 내놓고, 최종 답으로 자기 채널 글을 갱신한다. 계약과 리액티브 최소 구현은 plugin 끼리 공유하는 TypeScript 모듈로 둔다.
    - doppel 은 그 계약을 따르는 채널 중 하나이면서, 세션 상태 집계·브리프·원장을 더 갖는다. doppel 이 다른 채널로 fanout 하지 않는다.
15. **리액티브 스트림으로 짠다** — 양쪽 모두 "이벤트 스트림 → 변환 → 구독" 하나의 모양으로 둔다.
    - hook 모듈: `on(...)` 콜백들이 나가는 스트림 하나로 합쳐지고, attach stdout 이 들어오는 스트림이 된다. 들어오는 스트림은 `kind` 로 갈라 `answer`·`context`·`prompt` 처리로 보낸다. hook 은 판단을 하지 않으므로 파이프가 짧다.
    - doppel 데몬: 세션 이벤트 스트림을 세션별로 접어 상태(결정 4)를 만들고, 상태 변화 스트림에서 결정 지점을 뽑아 브리프·보고 스트림으로 잇는다. 연결된 세션·UI 로 내보내는 것은 broadcast 다.
    - hook 모듈 (TypeScript): rxjs 를 번들하지 않는다. 개념(Observable·Subject·map·filter·merge·scan)을 빌린 최소 구현을 plugin 안에 둔다.
    - doppel 데몬 (Rust): `futures::Stream` 조합과 `tokio::sync::broadcast` 로 같은 모델을 쓴다.
16. **OS 별 배포** — 지금은 `aarch64-apple-darwin`·`x86_64-apple-darwin` 만 낸다.
    - 릴리스 대상 target 을 도구별로 선언한다. 공용 `release.yml` 의 matrix 를 일괄로 넓히면 다른 도구까지 그 target 으로 빌드된다.
    - 설치 스크립트는 OS 별 파일로 둔다. `scripts/install.sh` 는 macOS 의 arch → target 매핑으로 일반화한다. 다른 OS 는 그 OS 를 지원할 때 매핑을 더하거나(Linux) 파일을 더한다(Windows `install.ps1`). 둘 다 기존 체크섬 계약을 따르고, 해당 target 산출물이 없으면 설치 전에 실패한다.
    - 로컬 연결은 transport trait 하나로 감싼다. macOS 구현은 Unix socket(파일 권한이 인증)이다. Windows 를 지원할 때 loopback TCP + 토큰 구현을 더한다.
17. **doppel 이 수신·라벨링·칸반·분배를 모두 갖는다.** `kanban`·belt 를 소비하지 않는다.
    - 골든셋과 피드백 루프를 한 엔진에서 관리하려는 것이다. 이슈 라벨링·우선순위·분배도 내 판단 카테고리로 같은 원장·골든셋·평가에 들어간다.
    - `kanban` 의 설계 원칙은 개념으로 가져온다: 불변식은 DB `CHECK` 로, 점유는 한 SQL 문으로 원자적으로, 확정적으로 알 수 있는 중복은 `UNIQUE(source, external_id)` 로, 사람이 손댄 판정만 골든으로. 코드는 의존하지 않는다.
    - 기존 `tools/kanban` 은 이번에 건드리지 않는다.
18. **먼저 온 답은 hook 체인이 고르고, 모든 곳에 반영한다.** 연결된 모든 세션에 기본으로 적용한다.
    - `AskUserQuestion` 의 `tool.call` 은 plugin 들의 hook 을 차례로 지나 core(터미널 기본 대화상자)에 닿는다. 각 채널 plugin 의 hook 은 질문을 자기 채널에 올리고 `Promise.race([next(e), 내 채널의 답])` 을 한다.
      - 내 채널 답이 이기면 `{ result: { questions, answers } }` 로 답한다. `next` 가 걸린 채 돌아가면 그 아래가 중단된다는 타입 문서의 계약으로, 안쪽 plugin 들과 터미널 대화상자가 함께 중단된다.
      - `next(e)` 가 이기면(안쪽 채널 또는 터미널이 먼저 답함) 그 결과를 그대로 돌려준다. 바깥 plugin 들도 같은 결과를 받는다.
      - 경주에 진 plugin 은 최종 답을 `session.append` 의 tool-result 행(같은 `tool_use_id`)에서 읽어 자기 채널 글을 "○○에서 답변됨: …" 으로 갱신한다. 위에서 중단된 plugin 도 이 행으로 답을 안다.
      - 경주는 대칭이라 plugin 순서와 무관하게 먼저 온 답 하나가 확정된다. 판정 서버가 따로 없다.
    - doppel plugin 은 같은 경주에 참여하면서, 확정된 답과 어디서 왔는지를 원장에 기록한다.
    - 브리프(배경·추천)를 다른 채널에도 보이려면 doppel plugin 이 바깥에서 질문 입력을 `next({ ...e, input })` 으로 보강한다 — 브리프가 준비될 때까지 질문이 늦어지므로 기본은 보강 없이 올리고, doppel UI·터미널 band 에만 브리프를 붙인다.
    - **권한 확인** — 엔진 판정이 `ask` 일 때 같은 경주를 한다. 원격 답이 거부면 `{ deny }` 로 끝난다. 원격 답이 허용이면 프롬프트 없이 도구를 실행시켜야 하므로, 걸린 `next` 를 버리고 그 `tool_use_id` 를 `tool.check` 가 `allow` 로 답하게 한 뒤 `next(e)` 를 다시 부른다. 이 재호출이 되는지는 spike 로 확인하고, 안 되면 터미널 기본 프롬프트 대신 doppel band(`AbovePrompt` 의 허용·거부 버튼)를 터미널 surface 로 쓴다.
    - 어느 채널도 닿지 않으면 hook 은 `next(e)` 만 부른다 (기존 동작).

## 버린 선택지

- **채널을 doppel 의 WebSocket 어댑터로 두고 doppel 이 fanout·먼저 온 답 판정** — 판정 서버와 어댑터 계약이 하나 더 생긴다. 세션의 hook 체인이 이미 경주를 고를 수 있으므로 채널을 세션 plugin 으로 붙이는 쪽이 단순하다 (사용자 제안).
- **오케스트레이터(hub) 중심 정체성** — 실행·fanout 은 도구라 쉽게 대체된다. 쌓이는 가치는 판단 이력이고, 그것을 1급으로 두어야 쓸수록 좋아진다.
- **doppel 이 판단을 직접 처리하는 대리인 중심** — 사용자가 원한 것은 결정을 준비해 먼저 공유받는 것이다. 대리 처리는 카테고리별 opt-in 으로만 남긴다.
- **별도 shadow 모드** — 브리프 보고가 기본이면 모든 브리프가 예측이고 내 응답이 정답이라, 따로 둘 이유가 없다.
- **`discord-connector` 를 확장** — Discord 특화 로직(스레드 생성·이력 조립·분할 게시)이 섞여 있다. 채널 특화는 어댑터로 빼고 중심은 채널을 모르게 한다.
- **파인튜닝으로 닮게 하기** — 로컬에서 재현·감사가 어렵다. 판례 검색 + 인용이면 왜 그렇게 추천했는지 사람이 검토할 수 있다.
- **CLI 가 브리프까지 직접 작성** — 같은 입력에 다른 출력이 나오는 판단이 CLI 로 들어간다. 데몬은 브리프 agent 를 실행만 한다.
- **결정 지점 감지를 자연어 해석으로** — 감지가 비결정적이 된다. 감지는 결정적 신호로 하고, 해석은 브리프 agent 가 한다.
- **골든 건별 즉시 확정** — 작업 흐름이 자주 끊긴다.
- **처음부터 로컬 임베딩** — 모델 의존성과 버전 고정 부담이 데이터가 적은 초기에 비해 크다.
- **hook 이 doppel 과 WebSocket 을 직접 유지** — hook 런타임에 WebSocket API 가 없다 (2.1.306). `doppel attach` 자식이 연결을 든다.
- **들어오는 방향을 `$.http.fetch` long-poll 로** — 요청마다 타이머를 다시 거는 폴링 루프가 되고, 응답 지연이 폴링 간격에 묶인다. spawn 스트림은 push 다.
- **나가는 방향도 attach 자식의 stdin 으로** — stdin 은 시작 때 한 번 쓰고 닫힌다.
- **CLI 호출만으로 연결 (`doppel event emit` 을 이벤트마다 `$.process.run`)** — 이벤트마다 프로세스가 뜨고, 들어오는 방향이 없어 늦게 온 답을 세션에 넣을 수 없다.
- **막힘을 자연어로 판정** — 상태 판정이 비결정적이 된다. 시간·횟수 기준값을 둔 신호로 판정하고, 해석이 필요한 부분(턴 종료 대기의 의미)만 브리프 agent 에 넘긴다.
- **어댑터가 스레드 상태를 소유** — 어댑터 재시작 때 대화가 끊긴다.
- **hook 모듈에 rxjs 번들** — 모듈 런타임에 npm 해석이 없어 번들 파일을 plugin 에 넣어야 하고, hook 의 짧은 파이프에 비해 크다 (사용자 선택: 개념만 차용).
- **doppel 을 TypeScript 로 (rxjs 그대로 사용)** — 사용자 선택은 Rust. areum-lab-tools 의 `discord` CLI 와 같은 언어다.
- **`kanban` 을 보드로, belt 를 실행기로 소비** — 판단이 세 도구에 흩어져 골든셋·피드백 루프를 한 곳에서 관리할 수 없다 (사용자 선택: doppel 이 모두 갖는다).
- **처음부터 Linux·Windows 까지 배포** — 지금 필요한 것은 macOS 다. 넓힐 자리(도구별 target 선언, OS 별 설치 스크립트, transport trait)만 남긴다.
- **터미널 세션의 질문은 가로채지 않고 브리프만** — 한때 결정했으나 사용자가 고쳤다. 연결된 세션의 질문·권한은 모두 중계해야 한다 (결정 18).
- **터미널 세션의 질문을 doppel inbox 로만 받기** — 터미널 앞에 있을 때도 inbox 에서 답해야 한다. 터미널을 surface 하나로 두고 fanout 한다.
- **위험·권한·우선순위를 시드 카테고리에 포함** — 이번 선택에서 빠졌다. 되돌릴 수 없는 행동의 자동 처리 금지는 카테고리와 무관하게 유지한다.

## 열린 질문

- **설계 승인 카테고리의 자동 처리와 atelier 승인 출처의 관계** — atelier 는 자율 런의 설계 승인을 협의체 pass 또는 사용자 승인으로만 인정한다 (#904). 브리프를 보고 내가 수락한 것은 사용자 승인이다. doppel 이 자동 처리한 답을 승인 출처로 인정할지는 정하지 않았다. 정하기 전까지 이 카테고리는 자동 처리를 켤 수 없다.
- 자동 처리를 켤 수 있는 기준값(표본 수·lift)의 초기값.
- 보고 주기 — 결정 지점이 생길 때마다 즉시 낼지, 묶어서 낼지, 둘을 섞을지.
- Discord 채널 plugin 을 만들 때 기존 `discord` 데몬을 로컬 연결 프로세스로 쓸지 (`discord-connector` 와 같은 봇 토큰을 쓰면 응답이 경쟁한다).
- 기존 `tools/kanban` 을 doppel 이 자리 잡은 뒤 어떻게 할지 (유지·폐기).
- Windows 를 지원할 때: function hook 의 `$.http.fetch` 가 loopback TCP 로 doppel 에 붙는 데 문제가 없는지, `$.process.spawn` 이 같은 방식으로 도는지.
- spike 결과 (2026-10-21, headless `claude -p --input-format stream-json --permission-prompt-tool stdio`): 세션 수명 `$.process.spawn` 자식, Unix socket `$.http.fetch`, `next` 를 건 채 원격 답으로 끝내는 질문 경주, 권한 허용 시 `tool.check` allow + `next(e)` 재호출, idle 세션 `$.prompt.submit` 이 모두 동작했다. 남은 것은 대화형 세션에서만 볼 수 있는 두 가지 — 터미널 대화상자가 화면에서 닫히는지, `classic.Notification` 의 `notification_type` 값.
- 중첩 실행 주의: Claude 세션 안에서 띄운 `claude` 는 부모의 session id 를 이어받았다 (이 환경의 `CLAUDE_CODE_SESSION_ID` 등). doppel 이 세션을 띄우는 런처(P1b)는 이 상속을 끊어야 한다.
