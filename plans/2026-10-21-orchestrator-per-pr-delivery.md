# orchestrator 에 작업 단위별 PR 전달 방식(per-pr)을 더한다

> **Plan — 이 시점의 결정 기록.** 현재 정책의 신뢰 소스가 아니다.
> 날짜: 2026-10-21 · 브랜치: claude/pensive-dirac-dl2rkj · 이슈: 없음 · 승인 출처: 사용자 승인 (방향은 대화, 세부는 이 문서 리뷰)

## 배경

서로 겹치지 않는 자잘한 이슈 여러 개를 한 번에 처리하고 싶어요. 하나의 피쳐가 아니라서 epic 브랜치로 모아 PR 하나로 내는 지금 방식이 맞지 않아요. 사용자가 원하는 흐름은 이래요.

1. 메인이 이슈를 분석하고, 어떤 이슈를 묶고 어떤 의존이 있는지 메인과 사람이 함께 정한다.
2. 정해진 그룹표대로 병렬 작업하고, 그룹마다 기본 브랜치로 PR 을 동시에 낸다.
3. 머지는 사람이 한다.

지금 orchestrator 는 작업 브랜치를 epic 에 rebase + fast-forward 로 모으고, 작업 브랜치에는 PR 을 만들지 않아요. `git` skill 의 PR 단위 원칙(요청 1건 = PR 1개)도 같은 전제예요.

## 결정

1. **별도 스킬을 만들지 않고 orchestrator 에 축 하나를 더한다** (사용자 동의)
   - 이슈 분석은 분해, 그룹·의존 결정은 사용자 승인, 겹침 판정은 병렬·순차 표, 격리 실행과 게이트는 기존 절차로 이미 덮인다. 새로운 것은 "결과를 epic 에 모으지 않고 작업 단위마다 PR 로 낸다" 하나뿐이다.
   - 그룹을 어떻게 묶을지는 판단이라 문서에 대본으로 적지 않는다. 그러면 새 스킬에 남는 내용이 없다.
2. **축 이름은 전달 방식, 값은 `converge`(기본값) · `per-pr`**
   - 사용자 쪽 이름은 "이슈 배치"로 부를 수 있다. 다만 스킬 안에서 fan-out 은 이미 병렬 dispatch 를 뜻하므로 "fanout" 은 쓰지 않는다.
   - `per-pr` 은 사용자가 작업 단위별 PR 을 명시했을 때만 고른다. 모델이 상황을 보고 추측해 고르지 않는다.
3. **그룹 하나 = task 하나 = PR 하나**
   - 그룹에는 연결 이슈 번호와 예상 변경 파일을 싣는다. PR 본문은 연결 이슈를 닫는 형태로 쓴다(형식은 `git` skill).
4. **의존이 있거나 hot-spot 이 겹치면 같은 그룹으로 묶거나 다음 배치로 미룬다. stacked PR 은 만들지 않는다**
   - 이 레포는 squash merge 를 쓴다. squash 로 머지하면 그 위에 쌓은 PR 의 base 가 깨진다.
   - converge 의 "hot-spot 은 병렬 유지 + 통합 task 를 순차로 분리" 는 per-pr 에 쓸 수 없다. 모을 통합 지점이 없다.
5. **epic 은 남기되 머지 대상이 아니다**
   - 메인이 점유하는 브랜치, plan 커밋의 자리, 작업 브랜치 이름의 접두로 그대로 쓴다. 진입 절차·토폴로지 가드·브랜치 규약을 바꾸지 않아도 된다.
   - epic 은 기본 브랜치 최신 위에서 시작하고, epic 자체로는 PR 을 만들지 않는다.
6. **plan 은 모든 그룹 PR 에 같은 커밋으로 실린다** (사용자 제안)
   - 메인이 epic 에 plan 을 `docs` 커밋 하나로 남기고, 모든 작업 브랜치가 그 커밋에서 갈라진다. converge 와 같은 순서다.
   - 첫 그룹 PR 이 머지될 때 plan 이 기본 브랜치에 들어간다. 나머지 PR 은 같은 경로에 같은 내용을 더하는 것이라 git 이 충돌 없이 합치고, squash 결과에서도 변화가 없다.
   - 성립 조건: 어떤 작업자도 plan 파일을 고치지 않는다. 고치면 PR 끼리 충돌한다. prompt 의 범위에 plan 경로를 편집 금지로 싣는다.
   - 머지 전까지는 각 PR diff 에 plan 파일이 함께 보인다. PR 본문에 그 사실을 적는다.
7. **PR 은 메인이 만든다**
   - 작업자는 worktree 에서 커밋까지만 한다. 메인은 게이트 통과를 확인한 뒤 메인 working tree 에서 작업 브랜치를 push 하고 PR 을 만든다. 브랜치 ref 는 worktree 끼리 공유되므로 worktree 에 들어가지 않아도 된다.
   - 외부 쓰기가 메인 한 곳에만 있고, 게이트가 PR 생성 앞에 선다.
8. **PR 생성 직전에 겹침을 다시 확인한다**
   - 그룹마다 `git diff --name-only <epic>...<branch>` 를 대조해 다른 그룹과 파일이 겹치면 그 PR 을 만들지 않고 보고한다.
   - 작업자가 그룹의 예상 파일 밖을 고쳐야 하게 되면 그 그룹만 멈추고 보고한다. 범위가 겹쳤다는 신호다.
9. **최종 검증은 그룹 브랜치 HEAD 마다 한다. PR 끼리의 상호작용은 검증하지 않는다**
   - 그룹끼리 겹치지 않는다는 것은 그룹표 승인 때 사람이 확인한다. 그 뒤에는 PR 마다 도는 CI 가 게이트다.
   - 메인은 worktree 에 들어가지 않으므로 integration_verify 실행은 read-only 위임으로 하고, 결과에 명령 원문과 HEAD sha 를 받는다.
10. **PR 을 만든 뒤 CI·리뷰 대응은 범위 밖이다** (사용자 결정)
    - 런은 그룹별 PR 링크와 head sha 를 보고하고 끝난다.
11. **push·PR 권한은 preflight 대상이다**
    - 하네스가 지정 브랜치 밖 push 를 막는 환경이면 per-pr 은 성립하지 않는다. 공유 전제 실패로 보고 dispatch 를 시작하지 않는다.

## 버린 대안

| 대안 | 이유 |
|---|---|
| 별도 스킬 `issue-batch` | orchestrator 와 `git` 을 부르는 얇은 껍데기만 남는다. 그룹을 묶는 판단을 적으면 판단 대본이 된다 |
| orchestrator 에 reference 파일 추가 | 줄수 상한이 세 파일에만 걸려 있어 상한을 비켜 가는 통로가 된다 |
| 축 이름 "fanout" | 스킬 안에서 이미 병렬 dispatch 를 뜻한다. 두 방식의 차이는 분배가 아니라 전달이다 |
| 그룹표를 `log_dir` 에만 기록 | 설계 승인 마커의 근거는 커밋된 plan 이어야 한다. repo 밖 기록은 런이 끝나면 남지 않는다 (사용자도 plan 이 있어야 한다고 판단) |
| plan 만 담은 별도 docs PR | 배치마다 PR 이 하나 더 생긴다. 모든 그룹 PR 에 같은 커밋으로 싣는 쪽이 더 단순하다 (사용자 제안) |
| 의존 이슈를 stacked PR 로 | squash merge 에서 base 가 깨진다 |
| PR 을 작업자가 생성 | 게이트를 PR 앞에 둘 수 없고 외부 쓰기가 흩어진다 |
| PR 끼리의 통합 검증 | 겹치지 않음을 사람이 승인한 배치에서 얻는 것보다 비용이 크다 |
| PR 이후 CI·리뷰까지 런 안에서 | 런이 길어지고 종료 조건·예산을 새로 정해야 한다 (사용자 결정) |

## 범위 밖

- PR 이후 CI red · 리뷰 코멘트 대응.
- 이슈 목록을 받아 파일 겹침 행렬을 만드는 결정적 CLI. 필요해지면 그때 별도 진입점을 검토한다.
- 슬래시 커맨드(`/issue-batch` 등). 필요해지면 스킬이 아니라 orchestrator 를 `per-pr` 로 부르는 command 하나로 둔다.
- 기존 plan 은 고치지 않는다.

## 가정

- 기본 브랜치 머지는 squash 또는 merge commit 이다. 결정 6 의 "같은 내용 추가는 충돌 없이 합쳐진다"는 이 전제에 기댄다. rebase merge 에서는 plan 커밋이 빈 커밋이 되므로 다시 확인한다.
